# ADR-0022: Client SDKs and CLI

- **Status:** Accepted (documents the current implementation).
- **Decision date:** 2026-11-19.
- **Author:** Apicurio Registry maintainers.
- **Tracking:** the SDK modules ([`java-sdk/`](../java-sdk/), [`go-sdk/`](../go-sdk/),
  [`python-sdk/`](../python-sdk/), [`typescript-sdk/`](../typescript-sdk/)) and the CLI
  ([`cli/`](../cli/)); open work in [#11261](https://github.com/Apicurio/apicurio-registry/issues/11261)
  and [#10923](https://github.com/Apicurio/apicurio-registry/issues/10923).
- **Scope:** How the registry's clients are produced and kept in step with the REST API: generation
  with Kiota, the Java SDK's options and HTTP adapters, the error model, the client facade the serdes
  use, the `acr` CLI, and the Maven plugin as a client. Not covered: serdes behaviour
  ([ADR-0007](0007-kafka-serdes.md)), how the server authenticates callers
  ([ADR-0009](0009-authentication.md)), reference registration in the Maven plugin
  ([ADR-0008](0008-artifact-references.md)), and what import and export do
  ([ADR-0012](0012-import-export-and-migration.md)).

## Context

The registry is used from Java applications, Kafka serializers, build tools, Go services, Python
and TypeScript scripts, CI pipelines and terminals. Each needs a client that covers the whole v3 REST
API, follows it as it grows (new endpoints, new fields, new error shapes), and authenticates and
speaks TLS the way the deployment requires. Hand-maintaining five clients would put each one behind
the API by a different amount. The OpenAPI document in
[`common/src/main/resources/META-INF/openapi.json`](../common/src/main/resources/META-INF/openapi.json)
is already the contract the server is checked against, so it is the natural source for clients.

## Decision

1. **Every SDK is generated by Kiota from the registry's OpenAPI document.** The v3 client comes from
   `openapi.json`; v2 clients (Java, Go) come from `openapi-v2.json`. One Kiota version (1.35.0)
   is pinned per toolchain: `kiota.version` in the root [`pom.xml`](../pom.xml), the
   `Microsoft.OpenApi.Kiota.Builder` version in `go-sdk.csproj` and `python-sdk.csproj`, and
   `KIOTA_VERSION` in [`typescript-sdk/package.json`](../typescript-sdk/package.json).
2. **Generation happens where each ecosystem expects it.**

   | SDK | Generated by | Committed? | Published as |
   |---|---|---|---|
   | Java | `kiota-maven-plugin` in [`java-sdk/client`](../java-sdk/client/pom.xml) at build time | No | `io.apicurio:apicurio-registry-java-sdk` |
   | Java v2 | Same plugin, from a filtered copy of `openapi-v2.json` ([`client-v2`](../java-sdk/client-v2/pom.xml)) | No | `apicurio-registry-v2-java-sdk` (deprecated) |
   | Go | [`generate.sh`](../go-sdk/generate.sh) (`make generate format`), v2 and v3 packages | Yes, `go-sdk/pkg/` | Go module `github.com/apicurio/apicurio-registry/go-sdk/v3` |
   | Python | [`kiota-gen.py`](../python-sdk/kiota-gen.py), run by `make generate` before the Poetry build | No | `apicurioregistrysdk` on PyPI |
   | TypeScript | `npm run generate-sources` | No | `@apicurio/apicurio-registry-sdk` on npm |

3. **CI keeps the SDKs in step with the spec.** Java is regenerated in every Maven build, so it can
   not drift. Go is committed, so the `go-sdk-freshness` job in
   [`verify.yaml`](../.github/workflows/verify.yaml) regenerates it and fails on any diff, and
   [`generate-go-sdk.yaml`](../.github/workflows/generate-go-sdk.yaml) regenerates and commits it when
   the spec changes on `main` or `3.3.x`. [`verify-sdk.yaml`](../.github/workflows/verify-sdk.yaml)
   runs the Python and Go SDK tests, and `verify-extras.yaml` the TypeScript ones, against the
   registry image built from the same commit. Python, Go and TypeScript are released together by
   [`release-sdks.yaml`](../.github/workflows/release-sdks.yaml) with the registry's version; the Java
   SDK is released with the Maven artifacts.
4. **The Java SDK adds a thin, hand-written layer on top of Kiota.** `RegistryClientFactory.create(
   RegistryClientOptions)` returns the generated `RegistryClient`; the options carry everything the
   generated code does not know about: authentication, TLS, proxy, retry, timeouts, HTTP logging,
   OpenTelemetry propagation and the HTTP adapter. The generated request builders are the API; there
   is no second, idiomatic API to keep in step.
5. **Two HTTP adapters, chosen at runtime.** `adapter-vertx` (Kiota's Vert.x adapter) and
   `adapter-jdk` (`java.net.http`) are separate modules, both dependencies of the SDK by default.
   `HttpAdapterType.AUTO` picks Vert.x when it is on the classpath, then the JDK adapter
   (`AdapterDetector`); a consumer can exclude one, for example the JDK adapter for GraalVM native
   images or Vert.x to avoid Netty.
6. **Errors are typed by the spec.** The OpenAPI document declares error responses as
   `ProblemDetails` (RFC 7807) and rule violations as `RuleViolationProblemDetails`; Kiota maps them to
   exceptions of those types, which extend Kiota's `ApiException` and carry the HTTP status
   (`getResponseStatusCode()`). A response the spec does not describe becomes a plain `ApiException`.
7. **The serdes do not depend on the generated client directly.** The schema resolver talks to a
   small internal `RegistryClientFacade` (fetch a schema by global ID, content ID, content hash or
   coordinates; references; register). `RegistryClientFacadeFactory` builds the v2 implementation when
   the configured endpoint version is 2, and the v3 one when it is 3. Only when no version is
   configured does it look at the URL: v2 if it contains `/apis/registry/v2`, v3 otherwise. An explicit
   version wins over the URL.
8. **The CLI is a Java SDK application.** `acr` is a Quarkus picocli application built on the Java
   SDK (Vert.x adapter), distributed as a native executable per platform, and marked dev preview: its
   arguments and behaviour may change incompatibly.

### Why Kiota

One generator for Java, Go, Python and TypeScript, driven by the spec CI already validates, keeps
every SDK complete by construction: a new endpoint reaches all of them in the next build. The price
is that the SDKs look like their spec (request-builder chains, generated model names) rather than
hand-designed libraries, and inherit Kiota's runtime behaviour, including its gaps (see
[limitations](#limitations-and-open-work)).

## Java SDK options

| Concern | `RegistryClientOptions` | Notes |
|---|---|---|
| URL | `registryUrl`, `rawRegistryUrl` | `registryUrl` adds a missing protocol or API path (`localhost:8080` works); `rawRegistryUrl` uses the URL as given |
| Authentication | `basicAuth`, `oauth2(tokenEndpoint, clientId, secret[, scope])`, `bearerToken` | OAuth2 is the client-credentials flow; anonymous by default |
| Trust | `trustStorePkcs12`, `trustStoreJks`, `trustStorePem`, `trustStorePemContent`, `trustAll`, `verifyHost` | `trustAll` and `verifyHost(false)` are for tests |
| Client certificate (mTLS) | `keystorePkcs12`, `keystoreJks`, `keystorePem`, `keystorePemContent` | |
| Proxy | `proxy`, `proxyAuth` | |
| Retry | `retry(...)`, `disableRetry` | Off by default. `retry()` allows 3 retries after the first call (4 attempts), 250 ms initial delay, ×2 backoff, 10 s cap. Retries only connection failures (`ConnectException`, `SocketTimeoutException`, Vert.x `HttpClosedException`, an `IOException` with "Connection reset"), never an HTTP error status; a non-idempotent request can therefore be sent more than once |
| Timeouts | `requestTimeout(connectMs, readIdleMs)` | No timeout by default with Vert.x |
| Diagnostics | `enableHttpLogging`, `enableOpenTelemetry` | Logging writes to `io.apicurio.registry.client.http` at `FINE`. It redacts known credential headers and query parameters only, not bodies or custom headers, so it must not be enabled where requests carry secrets in those (as the method's Javadoc warns) |
| Adapter | `httpAdapter(AUTO \| VERTX \| JDK)`, `vertx(...)`, `customWebClient(...)` | |

`java-sdk/references` (`ReferenceRegistrar`) is an optional helper that registers a schema and its
references in dependency order. The v2 client (`RegistryV2ClientFactory`) is deprecated; see
[`MIGRATING_FROM_V2.md`](../java-sdk/MIGRATING_FROM_V2.md).

**Compatibility.** The SDKs share the registry's version and are generated from that version's spec.
The v3 REST API is versioned by path (`/apis/registry/v3`), so an SDK talks to registries of the
same major API version; a field or endpoint added in a later release is only available from an SDK
of that release.

## The CLI

| Concern | Behaviour |
|---|---|
| Commands | Groups, artifacts, versions, comments, rules, role mappings, search, server configuration, admin import and export, GitOps status, sync and validate, MCP tool import (experimental) |
| Contexts | Named contexts hold the registry URL, a default group and artifact, and authentication; `acr context` manages them |
| Configuration | `config.json` in the CLI's home directory, managed with `acr config`. The `acr` launcher picks that directory, and exports it as `ACR_CURRENT_HOME`: its own directory if the CLI binary is next to it (an unpacked ZIP), otherwise `ACR_HOME`. The installer puts it in `$HOME/.apicurio/apicurio-registry-cli` |
| Credentials | `acr login` (basic, or OAuth2 client credentials with OIDC discovery); the password or client secret goes to the OS keychain (macOS Keychain, Linux Secret Service, Windows Credential Manager), or an encrypted file with `--allow-unsafe-credential-storage`; tokens are requested per invocation, never stored |
| Output | `--output-type table` (default) or `json`; JSON on stdout, diagnostics on stderr; `--verbose` logs raw HTTP |
| Exit codes | `0` success, `1` application error, `2` invalid input, `3` a `ProblemDetails` or any other `ApiException` (an HTTP error status) from the registry |
| Timeouts | Registry calls: 30 s connect, 120 s read idle; import: 1 h read idle |
| Updates | Checks once a day; `acr update` installs, `--check`, `--postpone`, `update.check-enabled=false` |
| Distribution | Native ZIPs for Linux x86_64, macOS aarch64, Windows x86_64; `acr install` sets up `PATH` and completions |

## The Maven plugin as a client

The plugin ([`utils/maven-plugin`](../utils/maven-plugin/)) builds a Java SDK client from its
parameters: `username`/`password` or OAuth2 client credentials, trust and key stores (JKS, PKCS12,
PEM), `trustAll` and `verifyHost`. A failure names the HTTP status (`HttpStatusMessageTest`).
What it registers is [ADR-0008](0008-artifact-references.md) and the
[Maven documentation](../docs/modules/ROOT/pages/getting-started/assembly-managing-registry-artifacts-maven.adoc).

## Limitations and open work

1. A response whose body is neither a `ProblemDetails` nor JSON reports badly: an HTML error page
   from a proxy reaches the caller without a usable message, and a 401 without a body is a plain
   `ApiException` (`service returned status code401 but no response body was found`), not a
   `ProblemDetails` ([#11261](https://github.com/Apicurio/apicurio-registry/issues/11261)).
2. For a `ProblemDetails` the CLI prints the problem's detail, not the HTTP status. A plain
   `ApiException` (such as that 401) exits with code 3 and its message names the HTTP status
   ([#11338](https://github.com/Apicurio/apicurio-registry/issues/11338)).
3. The JDK adapter ignores `enableHttpLogging`. It applies `requestTimeout` (default connect timeout
   30 s), but the JDK `HttpClient` has no read-idle timeout, so the read value bounds the wait for
   the response headers rather than idle time between reads.
4. The Kiota version is pinned in four places and must be bumped together
   ([#10923](https://github.com/Apicurio/apicurio-registry/issues/10923)); the Java build downloads
   the Kiota binary from GitHub releases, which is a CI dependency.
5. The v2 Java SDK and the v2 serdes facade remain until REST API v2 is removed
   ([#7336](https://github.com/Apicurio/apicurio-registry/issues/7336),
   [#7330](https://github.com/Apicurio/apicurio-registry/issues/7330)).
6. The CLI is a dev preview: no Windows on ARM, no PowerShell completions, unsigned Windows binaries,
   and commands do not yet cover every API (for example branches,
   [#9920](https://github.com/Apicurio/apicurio-registry/issues/9920)).

## Alternatives

| Alternative | Decision and trade-off |
|---|---|
| Hand-written clients | Not selected: idiomatic, but each language lags the API by a different amount and needs its own tests for every endpoint |
| OpenAPI Generator | Not selected: also multi-language, but its generators differ in quality per language; Kiota gives one runtime model (request adapters, parse nodes) across the four languages |
| Idiomatic wrappers over the generated code | Not selected beyond the Java options layer and helpers such as `ReferenceRegistrar`: a full wrapper is a second API to keep in step |
| Committing generated code for every language | Only Go, because Go modules are consumed from source; elsewhere build-time generation removes a drift risk |
| A CLI in Go, sharing the Go SDK | Not selected: the Java SDK carries the auth and TLS options already, and GraalVM gives a native binary |

## Consequences

- **Benefits:** every SDK covers the full API of its release; new endpoints need no client work; one
  options model for Java auth and TLS shared by the SDK, serdes, Maven plugin and CLI; a scenario
  check that the clients agree.
- **Costs:** generated, spec-shaped APIs; Kiota's runtime limits become ours; the Kiota version and
  generation scripts are maintained per language; the native CLI build adds CI time on three
  platforms.
