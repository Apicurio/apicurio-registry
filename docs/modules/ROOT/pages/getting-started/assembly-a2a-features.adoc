// con-a2a-overview
[id="a2a-overview_{context}"]
== A2A protocol overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
With the A2A protocol, AI agents can discover and communicate with each other through standardized endpoints. {registry} serves as both an A2A agent and an agent registry.

{registry} as an A2A agent:: {registry} provides its own capabilities, including schema validation, search, and artifact management.
{registry} as an agent registry:: {registry} stores and discovers other agents' Agent Cards.

.{registry} dual-role A2A architecture
[cols="1,1",options="header"]
|===
|{registry} as an A2A agent
|{registry} as an agent card registry

a|Endpoint: `/.well-known/agent.json`

Built-in skills:

* `schema-validation`
* `schema-search`
* `artifact-management`
* `compatibility-check`
* `agent-discovery`

a|Endpoints:

* `/.well-known/agents`
* `/.well-known/agents/\{groupId}/\{artifactId}`

Capabilities:

* Store agent cards as `AGENT_CARD` artifacts
* Search by skill, capability, or input/output mode
* Version management and compatibility checking
|===

// ref-a2a-well-known-endpoints
[id="a2a-well-known-endpoints_{context}"]
== A2A well-known endpoints

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} provides the following well-known endpoints for A2A agent discovery and retrieval.

GET /.well-known/agent.json::
Retrieves the Agent Card for the {registry} instance. This endpoint requires no authentication. The same card is available at `/.well-known/agent-card.json`.
+
Response: Agent Card JSON document
+
[source,json]
----
{
  "name": "Apicurio Registry",
  "description": "API and Schema Registry with A2A Agent support",
  "version": "3.3.3",
  "protocolVersion": "1.0",
  "supportedInterfaces": [
    {
      "url": "http://localhost:8080",
      "protocolBinding": "http+json",
      "protocolVersion": "1.0"
    }
  ],
  "provider": {
    "organization": "Apicurio",
    "url": "https://www.apicur.io"
  },
  "capabilities": {
    "streaming": false,
    "pushNotifications": false,
    "extendedAgentCard": false
  },
  "skills": [
    {
      "id": "schema-validation",
      "name": "Schema Validation",
      "description": "Validate schemas against format specifications (Avro, JSON Schema, Protobuf, OpenAPI, etc.)",
      "tags": ["schema", "validation", "avro", "json-schema", "protobuf", "openapi"]
    },
    {
      "id": "schema-search",
      "name": "Schema Search",
      "description": "Search for schemas and APIs in the registry by name, description, labels, or content",
      "tags": ["schema", "search", "discovery"]
    }
  ],
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "securitySchemes": {
    "bearer": {
      "type": "httpAuth",
      "scheme": "Bearer"
    }
  }
}
----
+
The example shows two of the five built-in skills. The `securitySchemes` object lists only the mechanisms that are enabled: `bearer` when OIDC authentication is enabled, `basic` when basic authentication is enabled, and `apiKey` when `apicurio.a2a.agent.auth.api-key.enabled` is `true`. The Agent Card includes `documentationUrl` and `iconUrl` only when you configure the corresponding properties.

GET /.well-known/agents::
Searches for registered Agent Cards with filtering support. This endpoint requires no authentication. When OIDC or basic authentication is enabled, the search returns only the Agent Cards that the caller has permission to view, based on the `apicurio.agent.visibility` label.
+
.Query parameters for /.well-known/agents
[cols="1,1,3",options="header"]
|===
|Parameter |Type |Description

|`name`
|string
|Filter by artifact name or artifact ID. A value without `*` matches anywhere in the name or ID. Use `*` as a prefix or suffix wildcard, for example `weather*`.

|`skill`
|string (repeatable)
|Filter by skill ID

|`capability`
|string (repeatable)
|Filter by capability (for example, `streaming:true`). Append `:false` to require that a capability is absent or disabled.

|`inputMode`
|string (repeatable)
|Filter by input mode (for example, `text`, `image`)

|`outputMode`
|string (repeatable)
|Filter by output mode

|`offset`
|integer
|Pagination offset (default: 0)

|`limit`
|integer
|Pagination limit (default: 20, maximum: 500)
|===
+
.Example request
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?skill=translation&capability=streaming:true"
----
+
.Example response: AgentSearchResults
[source,json]
----
{
  "count": 1,
  "agents": [
    {
      "groupId": "ai-agents",
      "artifactId": "translator-agent",
      "name": "Translation Agent",
      "description": "Translates text between languages",
      "owner": "alice",
      "createdOn": 1756720530000,
      "supportedInterfaces": [
        {
          "url": "http://translator:9001",
          "protocolBinding": "http+json",
          "protocolVersion": "1.0"
        }
      ],
      "skills": ["translation"],
      "capabilities": {
        "streaming": true,
        "pushNotifications": false
      }
    }
  ]
}
----
+
The `count` field is the total number of matching Agent Cards, not the number of entries in the current page. The `skills` array lists skill IDs only. To get skill names and descriptions, retrieve the full Agent Card from `/.well-known/agents/\{groupId}/\{artifactId}`.

GET /.well-known/agents/\{groupId}/\{artifactId}::
Retrieves a specific registered Agent Card.
+
*Path parameters*
+
* `groupId` - The group containing the agent card
* `artifactId` - The artifact ID of the agent card
+
*Query parameters*
+
* `version` (optional) - Specific version (defaults to latest)
+
Response: Agent Card JSON document

// ref-a2a-visibility-model
[id="a2a-visibility-model_{context}"]
== Agent visibility model

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Agent Cards support three visibility levels, controlled by the `apicurio.agent.visibility` artifact label. When OIDC or basic authentication is enabled, `GET /.well-known/agents` and the AI Catalog and ARD endpoints described in xref:getting-started/assembly-ai-catalog-ard.adoc[AI Catalog and ARD discovery] enforce visibility.

.Agent visibility levels
[cols="1,3",options="header"]
|===
|Visibility |Behavior

|`public`
|Visible to everyone, including unauthenticated clients

|`entitled`
|Visible to any authenticated user (this is the default)

|`private`
|Visible only to the artifact owner and registry administrators
|===

.Visibility label example
[source,bash]
----
curl -X PUT "http://localhost:8080/apis/registry/v3/groups/my-agents/artifacts/my-agent" \
  -H "Content-Type: application/json" \
  -d '{"labels": {"apicurio.agent.visibility": "public"}}'
----

*How entitlements work:* {registry} maps the A2A community entitlement concept to its existing RBAC model:

* *Groups* act as organizational namespaces
* *Entitling a client* = granting read access to the group containing the Agent Card artifacts
* *Client authentication* happens in an external identity provider, such as {keycloak} or another OIDC provider
* No new authorization primitives are required

.Discovery and entitlement configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`apicurio.a2a.default-visibility`
|`entitled`
|Default visibility for new Agent Card artifacts (`public`, `entitled`, or `private`)
|===

Visibility labels control which Agent Cards appear in `/.well-known/agents` search results and in the AI Catalog and ARD responses. When you retrieve a card by ID through `/.well-known/agents/\{groupId}/\{artifactId}` or the core REST API, only read authorization applies. {registry} does not check the visibility label.

NOTE: When neither OIDC nor basic authentication is configured, {registry} skips visibility filtering and all agents are visible to all users.

// ref-a2a-agent-card-artifact-type
[id="a2a-agent-card-artifact-type_{context}"]
== Agent Card artifact type

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} stores Agent Cards as artifacts with type `AGENT_CARD`. You can create Agent Cards by using the REST API and you can validate them against the A2A specification JSON schema.

.Agent Card creation example
[source,bash]
----
curl -X POST "http://localhost:8080/apis/registry/v3/groups/ai-agents/artifacts" \
  -H "Content-Type: application/json" \
  -d '{
    "artifactId": "my-agent",
    "artifactType": "AGENT_CARD",
    "firstVersion": {
      "version": "1.0.0",
      "content": {
        "contentType": "application/json",
        "content": "{\"name\": \"My Agent\", \"skills\": [{\"id\": \"task\", \"name\": \"Task Execution\"}]}"
      }
    }
  }'
----

Agent Cards must conform to the A2A specification:

.Agent Card JSON schema
[source,json]
----
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "required": ["name"],
  "properties": {
    "name": {"type": "string"},
    "description": {"type": "string"},
    "version": {"type": "string"},
    "url": {"type": "string", "format": "uri"},
    "provider": {
      "type": "object",
      "properties": {
        "organization": {"type": "string"},
        "url": {"type": "string", "format": "uri"}
      }
    },
    "capabilities": {
      "type": "object",
      "properties": {
        "streaming": {"type": "boolean"},
        "pushNotifications": {"type": "boolean"}
      }
    },
    "skills": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["id", "name"],
        "properties": {
          "id": {"type": "string"},
          "name": {"type": "string"},
          "description": {"type": "string"},
          "tags": {"type": "array", "items": {"type": "string"}},
          "examples": {"type": "array", "items": {"type": "string"}}
        }
      }
    },
    "defaultInputModes": {"type": "array", "items": {"type": "string"}},
    "defaultOutputModes": {"type": "array", "items": {"type": "string"}},
    "authentication": {
      "type": "object",
      "properties": {
        "schemes": {"type": "array", "items": {"type": "string"}}
      }
    }
  }
}
----

// ref-a2a-openapi-agent-card
[id="a2a-openapi-agent-card_{context}"]
== Auto-generating Agent Cards from OpenAPI specifications

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
If you already document your API with OpenAPI, you can embed Agent Card metadata directly in your OpenAPI specification's `info` block using the `x-agent-card` vendor extension, instead of authoring and maintaining a separate `AGENT_CARD` artifact by hand. {registry} detects the extension, assembles a valid Agent Card from it, and stores it as a companion artifact.

.Enabling OpenAPI-to-Agent-Card auto-generation
[cols="2,1,3"]
|===
|Property |Default |Description

|`apicurio.a2a.openapi-integration.enabled`
|`false`
|Auto-generate a companion AGENT_CARD artifact from the `x-agent-card` OpenAPI vendor extension

|`apicurio.a2a.openapi-integration.sync-on-update.enabled`
|`true`
|Update the generated Agent Card whenever its source OpenAPI artifact is updated
|===

NOTE: `apicurio.a2a.openapi-integration.enabled` is an experimental property. You must also set `apicurio.features.experimental.enabled=true` to use it.

.Example `x-agent-card` extension
[source,yaml]
----
openapi: "3.0.0"
info:
  title: Weather API
  description: Retrieves weather forecasts by city
  version: "1.0.0"
  x-agent-card:
    capabilities: {}
    skills:
      - id: get-weather
        name: Get Weather
        description: Retrieve the current weather for a city
        tags: [weather]
    defaultInputModes: [text]
    defaultOutputModes: [text]
servers:
  - url: https://weather.example.com
----

When {registry} stores an OPENAPI artifact version with an `x-agent-card` extension under `info`, it:

. Derives any of `name`, `description`, and `version` that the extension does not explicitly set, from the OpenAPI document's own `info.title`, `info.description`, and `info.version`.
. Derives `supportedInterfaces` from the OpenAPI document's `servers[]` array when the extension does not explicitly set it, using `http+json` as the protocol binding.
. Validates the assembled Agent Card against the same A2A v1.0 schema used for `AGENT_CARD` artifacts. If the assembled card is not valid, the OpenAPI write itself is rejected (HTTP 400) with a `RuleViolationException`, and nothing is persisted.
. Creates or updates a companion `AGENT_CARD` artifact named `<artifactId>-agent-card` in the same group as the source OpenAPI artifact, so the existing group-level entitlement model applies to it unchanged.

Required Agent Card fields with no OpenAPI equivalent — `capabilities`, `skills`, `defaultInputModes`, and `defaultOutputModes` — must always be supplied explicitly in the extension.

.Provenance and sync labels
The companion artifact and its source OpenAPI artifact are marked with `apicurio.a2a.openapi-agent-card.*` labels:

[cols="2,3"]
|===
|Label |Meaning

|`apicurio.a2a.openapi-agent-card.generated` (on the companion)
|`true` if this artifact was generated by this feature

|`apicurio.a2a.openapi-agent-card.source-group-id` / `.source-artifact-id` (on the companion)
|Identifies the source OpenAPI artifact this companion was generated from

|`apicurio.a2a.openapi-agent-card.generated-hash` (on the companion)
|A canonical content hash of the Agent Card content last generated, used to detect manual edits

|`apicurio.a2a.openapi-agent-card.artifact-id` (on the source OpenAPI artifact)
|The artifact ID of its generated companion Agent Card
|===

If you edit the generated Agent Card artifact directly, {registry} detects this the next time the source OpenAPI artifact changes (the companion's latest version content no longer matches its recorded generated hash) and skips the sync rather than overwriting your edit, logging a warning instead.

If an artifact already exists with the same name as the companion (`<artifactId>-agent-card`) but was not generated by this feature, {registry} leaves it untouched and logs a warning rather than overwriting it.

[role="_additional-resources"]
.Known limitations
* Only the three REST write paths that create or update an OPENAPI artifact version trigger auto-generation (creating an artifact with a first version, adding a new version, and the internal `ifExists=UPDATE`/`FIND_OR_CREATE_VERSION` path). Other write paths, such as the Confluent-compatible API, GitOps synchronization, and Kafka journal replay in KafkaSQL deployments, do not trigger it.
* Deleting the source OpenAPI artifact does not delete its generated companion Agent Card.
* AsyncAPI does not currently support the `x-agent-card` extension.

// ref-a2a-validation-rules
[id="a2a-validation-rules_{context}"]
== Agent Card validation rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Agent Cards have three validation levels that control how much validation occurs when you create or update an Agent Card.

[cols="1,3",options="header"]
|===
|Level |Description

|`NONE`
|No validation.

|`SYNTAX_ONLY`
|Validates that the content is syntactically valid JSON and is a JSON object.

|`FULL`
a|Complete schema validation including:

* Required `name` field (non-empty string)
* `description` and `version` fields
* `supportedInterfaces` array, where each interface has `url`, `protocolBinding`, and `protocolVersion`
* `provider` object with `organization` and `url`
* `skills` array, where each skill has `id` and `name`
* `capabilities` object with boolean values
* `defaultInputModes` and `defaultOutputModes` arrays
* Authentication and security scheme validation
* Valid JSON structure
|===

// ref-a2a-compatibility-checking
[id="a2a-compatibility-checking_{context}"]
== Agent Card compatibility rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
When you version Agent Cards, {registry} enforces compatibility rules to ensure that changes do not break existing clients.

*Compatible changes (allowed):*

* Adding new skills
* Adding new capabilities
* Adding authentication schemes
* Adding input or output modes

*Incompatible changes (can break clients):*

* Removing skills
* Removing or disabling capabilities
* Removing supported interfaces (matched by URL and protocol binding)
* Changing the protocol version on an existing interface
* Removing security schemes
* Removing input or output modes

.MODEL_SCHEMA artifact type

templateId: sentiment-analysis

[id="a2a-java-sdk-usage_{context}"]
== Java SDK usage for A2A

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can use the Java SDK to discover agents and register Agent Cards programmatically.

.Agent discovery example
[source,java]
----
RegistryClient client = RegistryClientFactory.create(
    RegistryClientOptions.create("http://localhost:8080/apis/registry/v3"));

// Search for agents with specific skill
var agents = client.wellKnown().agents()
    .get(config -> {
        config.queryParameters.skill = List.of("translation");
        config.queryParameters.limit = 10;
    });

for (var agent : agents.getAgents()) {
    System.out.println("Found: " + agent.getName() + " @ " + agent.getUrl());
}
----

.Agent Card registration example
[source,java]
----
CreateArtifact artifact = new CreateArtifact();
artifact.setArtifactId("my-agent");
artifact.setArtifactType("AGENT_CARD");

CreateVersion version = new CreateVersion();
version.setVersion("1.0.0");

VersionContent content = new VersionContent();
content.setContentType("application/json");
content.setContent(agentCardJson);
version.setContent(content);

artifact.setFirstVersion(version);

client.groups().byGroupId("ai-agents").artifacts()
    .post(artifact, config -> {
        config.queryParameters.ifExists = IfArtifactExists.FIND_OR_CREATE_VERSION;
    });
----

== A2A REST API endpoints

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The following table describes the core A2A endpoints available in {registry}.

[cols="2,1,4",options="header"]
|===
|Endpoint |Method |Description

|`/.well-known/agent.json`
|GET
|Get the registry's own Agent Card

|`/.well-known/agents`
|GET
|Search registered Agent Cards

|`/.well-known/agents/\{groupId}/\{artifactId}`
|GET
|Get a specific Agent Card by artifact ID

|`/apis/registry/v3/groups/\{groupId}/artifacts`
|POST
|Create an Agent Card artifact (type: AGENT_CARD)

|`/apis/registry/v3/groups/\{groupId}/artifacts/\{artifactId}`
|GET
|Get Agent Card artifact metadata

|`/apis/registry/v3/groups/\{groupId}/artifacts/\{artifactId}/versions/\{version}/content`
|GET
|Get Agent Card content
|===

== A2A troubleshooting

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Use the following information to troubleshoot common issues with A2A features in {registry}.

A2A endpoints return 404::
Set `apicurio.a2a.enabled=true` in your configuration:
+
[source,properties]
----
apicurio.a2a.enabled=true
----

Agent Card validation fails::
Verify the following conditions:
+
* The `name` field is present and non-empty.
* Skills have both `id` and `name` fields.
* Capabilities are boolean values.
* The JSON is well-formed.

Search returns no results::
Verify the following conditions:
+
* Agent Cards are stored with type `AGENT_CARD`.
* The registry extracted labels correctly (check artifact labels).
* Search filters match stored values exactly.
