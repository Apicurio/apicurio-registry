== A2A protocol overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
With the A2A protocol, AI agents can discover and communicate with each other through standardized endpoints. {registry} serves as both an A2A agent and an agent registry.

{registry} as an A2A agent:: {registry} provides its own capabilities, including schema validation, search, and artifact management.
{registry} as an agent registry:: {registry} stores and discovers other agents' Agent Cards.

.{registry} dual-role A2A architecture
[cols="1,1",options="header"]
|===
|{registry} as an A2A agent
|{registry} as an agent card registry

a|Endpoint: `/.well-known/agent.json`

Built-in skills:

* `schema-validation`
* `schema-search`
* `artifact-management`
* `compatibility-check`
* `agent-discovery`

a|Endpoints:

* `/.well-known/agents`
* `/.well-known/agents/\{groupId}/\{artifactId}`

Capabilities:

* Store agent cards as `AGENT_CARD` artifacts
* Search by skill, capability, or input/output mode
* Version management and compatibility checking
|===

== A2A well-known endpoints

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} provides the following well-known endpoints for A2A agent discovery and retrieval.

GET /.well-known/agent.json::
Retrieves the Agent Card for the {registry} instance. This endpoint requires no authentication. The same card is available at `/.well-known/agent-card.json`.
+
Response: Agent Card JSON document
+
[source,json]
----
{
  "name": "Apicurio Registry",
  "description": "API and Schema Registry with A2A Agent support",
  "version": "3.3.3",
  "protocolVersion": "1.0",
  "supportedInterfaces": [
    {
      "url": "http://localhost:8080",
      "protocolBinding": "http+json",
      "protocolVersion": "1.0"
    }
  ],
  "provider": {
    "organization": "Apicurio",
    "url": "https://www.apicur.io"
  },
  "capabilities": {
    "streaming": false,
    "pushNotifications": false,
    "extendedAgentCard": false
  },
  "skills": [
    {
      "id": "schema-validation",
      "name": "Schema Validation",
      "description": "Validate schemas against format specifications (Avro, JSON Schema, Protobuf, OpenAPI, etc.)",
      "tags": ["schema", "validation", "avro", "json-schema", "protobuf", "openapi"]
    },
    {
      "id": "schema-search",
      "name": "Schema Search",
      "description": "Search for schemas and APIs in the registry by name, description, labels, or content",
      "tags": ["schema", "search", "discovery"]
    }
  ],
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "securitySchemes": {
    "bearer": {
      "type": "httpAuth",
      "scheme": "Bearer"
    }
  }
}
----
+
The example shows two of the five built-in skills. The `securitySchemes` object lists only the mechanisms that are enabled: `bearer` when OIDC authentication is enabled, `basic` when basic authentication is enabled, and `apiKey` when `apicurio.a2a.agent.auth.api-key.enabled` is `true`. The Agent Card includes `documentationUrl` and `iconUrl` only when you configure the corresponding properties.

GET /.well-known/agents::
Searches for registered Agent Cards with filtering support. This endpoint requires no authentication. When any authentication mechanism is enabled, the search returns only the Agent Cards that the caller has permission to view, based on the `apicurio.agent.visibility` label.
+
.Query parameters for /.well-known/agents
[cols="1,1,3",options="header"]
|===
|Parameter |Type |Description

|`name`
|string
|Filter by artifact name or artifact ID. A value without `+*+` matches anywhere in the name or ID. Use `+*+` as a prefix or suffix wildcard, for example `weather*`.

|`skill`
|string (repeatable)
|Filter by skill ID

|`capability`
|string (repeatable)
|Filter by capability (for example, `streaming:true`). Append `:false` to require that a capability is absent or disabled.

|`inputMode`
|string (repeatable)
|Filter by input mode (for example, `text`, `image`)

|`outputMode`
|string (repeatable)
|Filter by output mode

|`offset`
|integer
|Pagination offset (default: 0)

|`limit`
|integer
|Pagination limit (default: 20, maximum: 500)
|===
+
.Example request
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?skill=translation&capability=streaming:true"
----
+
.Example response: AgentSearchResults
[source,json]
----
{
  "count": 1,
  "agents": [
    {
      "groupId": "ai-agents",
      "artifactId": "translator-agent",
      "name": "Translation Agent",
      "description": "Translates text between languages",
      "owner": "alice",
      "createdOn": 1756720530000,
      "supportedInterfaces": [
        {
          "url": "http://translator:9001",
          "protocolBinding": "http+json",
          "protocolVersion": "1.0"
        }
      ],
      "skills": ["translation"],
      "capabilities": {
        "streaming": true,
        "pushNotifications": false
      }
    }
  ]
}
----
+
The `count` field is the total number of matching Agent Cards, not the number of entries in the current page. The `skills` array lists skill IDs only. To get skill names and descriptions, retrieve the full Agent Card from `/.well-known/agents/\{groupId}/\{artifactId}`.

GET /.well-known/agents/\{groupId}/\{artifactId}::
Retrieves a specific registered Agent Card.
+
*Path parameters*
+
* `groupId` - The group containing the agent card
* `artifactId` - The artifact ID of the agent card
+
*Query parameters*
+
* `version` (optional) - Specific version (defaults to latest)
+
Response: Agent Card JSON document

[id="a2a-visibility-model_{context}"]
== Agent visibility model

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Agent Cards support three visibility levels, controlled by the `apicurio.agent.visibility` artifact label. Set the label on an Agent Card to control which clients can see it.

ifndef::service-registry-downstream[]
When any authentication mechanism is enabled, `GET /.well-known/agents` and the AI Catalog and ARD endpoints described in xref:getting-started/assembly-ai-catalog-ard.adoc[AI Catalog and ARD discovery] enforce visibility.
endif::[]
ifdef::service-registry-downstream[]
When any authentication mechanism is enabled, `GET /.well-known/agents` and the AI Catalog and ARD endpoints enforce visibility.
endif::[]

.Agent visibility levels
[cols="1,3",options="header"]
|===
|Visibility |Behavior

|`public`
|Visible to everyone, including unauthenticated clients

|`entitled`
|Visible to callers who can read artifacts: a registry role (`sr-readonly`, `sr-developer` or `sr-admin`) when role-based authorization is enabled, any authenticated user when `apicurio.auth.authenticated-read-access.enabled` is set or a trusted proxy has authorized the request, and unauthenticated clients when `apicurio.auth.anonymous-read-access.enabled` is set (this is the default)

|`private`
|Visible only to the artifact owner and registry administrators
|===

.Visibility label example
[source,bash]
----
curl -X PUT "http://localhost:8080/apis/registry/v3/groups/my-agents/artifacts/my-agent" \
  -H "Content-Type: application/json" \
  -d '{"labels": {"apicurio.agent.visibility": "public"}}'
----

*How entitlements work:* {registry} maps the A2A community entitlement concept to its existing RBAC model:

* *Groups* act as organizational namespaces
* *Entitling a client* = granting read access to the group containing the Agent Card artifacts
* *Client authentication* happens in an external identity provider, such as {keycloak} or another OIDC provider
* No new authorization primitives are required

.Discovery and entitlement configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`apicurio.a2a.default-visibility`
|`entitled`
|Visibility of an Agent Card that has no `apicurio.agent.visibility` label (`public`, `entitled`, or `private`). When authentication is enabled, {registry} applies the value at each discovery request and does not write the label to the artifact. A change to this property therefore changes the visibility of every unlabeled Agent Card, including existing ones.
|===

Visibility labels control which Agent Cards appear in `/.well-known/agents` search results and in the AI Catalog and ARD responses. When you retrieve a card by ID through `/.well-known/agents/\{groupId}/\{artifactId}` or the core REST API, only read authorization applies. {registry} does not check the visibility label.

NOTE: When no authentication mechanism is configured (OIDC, basic, proxy header, Kubernetes, or form), {registry} skips visibility filtering and all agents are visible to all users.

// ref-a2a-agent-card-artifact-type
[id="a2a-agent-card-artifact-type_{context}"]
== Agent Card artifact type

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} stores Agent Cards as artifacts with type `AGENT_CARD`. You can create Agent Cards by using the REST API and you can validate them against the A2A specification JSON schema.

.Agent Card creation example
[source,bash]
----
curl -X POST "http://localhost:8080/apis/registry/v3/groups/ai-agents/artifacts" \
  -H "Content-Type: application/json" \
  -d '{
    "artifactId": "my-agent",
    "artifactType": "AGENT_CARD",
    "firstVersion": {
      "version": "1.0.0",
      "content": {
        "contentType": "application/json",
        "content": "{\"name\": \"My Agent\", \"description\": \"Executes tasks on request\", \"version\": \"1.0.0\", \"supportedInterfaces\": [{\"url\": \"https://my-agent.example.com\", \"protocolBinding\": \"http+json\", \"protocolVersion\": \"1.0\"}], \"capabilities\": {\"streaming\": false, \"pushNotifications\": false}, \"skills\": [{\"id\": \"task\", \"name\": \"Task Execution\", \"description\": \"Runs a task and returns the result\", \"tags\": [\"task\"]}], \"defaultInputModes\": [\"text\"], \"defaultOutputModes\": [\"text\"]}"
      }
    }
  }'
----

Agent Cards must conform to the A2A protocol v1.0 Agent Card schema. The following table summarizes the schema. When a `VALIDITY` rule at the `FULL` level applies to the artifact, {registry} enforces the required fields and field types that xref:a2a-validation-rules_{context}[] lists. It does not evaluate the JSON schema itself. The schema allows additional properties. A v1.0 Agent Card declares its endpoints in `supportedInterfaces` and its authentication in `securitySchemes`. The schema has no top-level `url` or `authentication` field.

.Agent Card fields (A2A v1.0)
[cols="2,1,4",options="header"]
|===
|Field |Required |Description

|`name`
|Yes
|Name of the agent. A non-empty string.

|`description`
|Yes
|Description of what the agent does. A non-empty string.

|`version`
|Yes
|Version of the agent, as a string.

|`protocolVersion`
|No
|A2A protocol version that the agent supports, for example `1.0`.

|`supportedInterfaces`
|Yes
|Array with at least one interface. Each interface has a `url`, a `protocolBinding` (for example `jsonrpc`, `grpc`, or `http+json`), a `protocolVersion`, and an optional `tenant`.

|`provider`
|No
|Organization that provides the agent. When present, the object must contain `organization` and `url`.

|`capabilities`
|Yes
|Object with the boolean capabilities `streaming`, `pushNotifications`, and `extendedAgentCard`, an optional `extensions` array, and any other boolean capability.

|`skills`
|Yes
|Array with at least one skill. Each skill has an `id`, a `name`, a `description`, and a non-empty `tags` array. The optional skill fields are `examples`, `inputModes`, `outputModes`, and `securityRequirements`.

|`defaultInputModes`
|Yes
|Non-empty array of the input modes that the agent supports, for example `text` or `application/json`.

|`defaultOutputModes`
|Yes
|Non-empty array of the output modes that the agent supports.

|`securitySchemes`
|No
|Named security scheme definitions. The scheme `type` is one of `apiKey`, `httpAuth`, `oauth2`, `openIdConnect`, or `mutualTls`.

|`securityRequirements`
|No
|Array of objects that map security scheme names to the required scopes.

|`iconUrl`
|No
|URL of an icon for the agent.

|`documentationUrl`
|No
|URL of the agent documentation.

|`signatures`
|No
|Array of JSON Web Signature (JWS) signatures for verifying the Agent Card. Each signature has `protected` and `signature`, and an optional `header`.
|===

[id="a2a-openapi-agent-card_{context}"]
== Auto-generating Agent Cards from OpenAPI specifications

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
If you already document your API with OpenAPI, you can embed Agent Card metadata in the `info` block of your OpenAPI specification by using the `x-agent-card` vendor extension, instead of maintaining a separate `AGENT_CARD` artifact by hand.

{registry} detects the extension, assembles a valid Agent Card from it, and stores it as a companion artifact.

.Enabling OpenAPI-to-Agent-Card auto-generation
[cols="2,1,3"]
|===
|Property |Default |Description

|`apicurio.a2a.openapi-integration.enabled`
|`false`
|Auto-generate a companion AGENT_CARD artifact from the `x-agent-card` OpenAPI vendor extension

|`apicurio.a2a.openapi-integration.sync-on-update.enabled`
|`true`
|Update the generated Agent Card whenever its source OpenAPI artifact is updated
|===

NOTE: Both `apicurio.a2a.openapi-integration.enabled` and `apicurio.a2a.enabled` are experimental properties. To use either, also set `apicurio.features.experimental.enabled=true`.

.Example `x-agent-card` extension
[source,yaml]
----
openapi: "3.0.0"
info:
  title: Weather API
  description: Retrieves weather forecasts by city
  version: "1.0.0"
  x-agent-card:
    capabilities: {}
    skills:
      - id: get-weather
        name: Get Weather
        description: Retrieve the current weather for a city
        tags: [weather]
    defaultInputModes: [text]
    defaultOutputModes: [text]
servers:
  - url: https://weather.example.com
----

When {registry} publishes an OPENAPI artifact version with an `x-agent-card` extension under `info`, it:

. Derives any of `name`, `description`, and `version` that the extension does not explicitly set, from the OpenAPI document's own `info.title`, `info.description`, and `info.version`.
. Derives `supportedInterfaces` from `servers[]` only when omitted, expanding server variables using their string defaults and using `http+json` as the binding. Explicit malformed values are rejected rather than replaced. Relative URLs require explicit absolute `supportedInterfaces`; the registry does not guess a base URL. Publishers must ensure the advertised endpoint actually implements A2A; OpenAPI alone does not establish this.
. Validates the assembled Agent Card against the same A2A v1.0 schema used for `AGENT_CARD` artifacts. If the assembled card is not valid, the OpenAPI write itself is rejected (HTTP 400) with a `RuleViolationException`, and nothing is persisted.
. Creates or updates `<artifactId>-agent-card` in the same group, checking companion ownership and applying its configured rules. Companion failure is logged and leaves the successful source write intact; rejected companion content is never persisted.

Ordinary DRAFT creates/edits do not generate published companions. Transitioning a draft to a published state validates and generates from its edited content. Dry-run requests do not write companions. Published updates re-read the source tip, and conditional target-version writes prevent a concurrent manual version from being superseded.

In the extension, you must explicitly supply the required Agent Card fields that have no OpenAPI equivalent: `capabilities`, `skills`, `defaultInputModes`, and `defaultOutputModes`.

{registry} marks the companion artifact and its source OpenAPI artifact with `apicurio.a2a.openapi-agent-card.*` labels:

.Provenance and sync labels
[cols="2,3"]
|===
|Label |Meaning

|`apicurio.a2a.openapi-agent-card.generated` (on the companion)
|`true` if this artifact was generated by this feature

|`apicurio.a2a.openapi-agent-card.source-group-id` / `.source-artifact-id` (on the companion)
|Identifies the source OpenAPI artifact this companion was generated from

|`apicurio.a2a.openapi-agent-card.generated-hash` (on each generated companion version)
|Canonical hash committed with that generated content. Missing or mismatched provenance stops automatic synchronization.

|`apicurio.a2a.openapi-agent-card.source-global-id` (on each generated companion version)
|The exact source version; deletion/recreation of the source does not silently adopt the old companion.

|`apicurio.a2a.openapi-agent-card.artifact-id` (on the source OpenAPI artifact)
|The artifact ID of its generated companion Agent Card
|===

If you edit the generated Agent Card artifact directly, {registry} detects this the next time the source OpenAPI artifact changes (the companion's latest version content no longer matches its recorded generated hash) and skips the sync rather than overwriting your edit, logging a warning instead.

If an artifact already exists with the same name as the companion (`<artifactId>-agent-card`) but was not generated by this feature, {registry} leaves it untouched and logs a warning rather than overwriting it.

Labels are editable provenance/navigation hints, never authorization grants. Owner-only access is checked independently on the companion. Generation provenance is stored atomically with each version; failure updating the source navigation link can be repaired on a subsequent unchanged-content synchronization. A manually edited version without generation provenance is preserved. Regeneration after manual changes requires an explicit user decision, not deletion of its hash label.

**Known limitations**

* REST publication paths trigger generation: first published version, new published version, `ifExists=UPDATE`/`FIND_OR_CREATE_VERSION`, and publication of an edited draft. KafkaSQL REST requests journal both writes; replay itself does not generate an extra companion. Confluent-compatible APIs and read-only GitOps/KubernetesOps imports do not trigger generation.
* Source and companion are separate artifacts, not one transaction. Companion errors leave the source intact; repeated optimistic conflicts are bounded and logged. A later publication retries from current source content.
* Deleting the source OpenAPI artifact does not delete its generated companion Agent Card.
* AsyncAPI does not currently support the `x-agent-card` extension.

== Agent Card validation rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Agent Cards have three validation levels that control how much validation occurs when you create or update an Agent Card.

[cols="1,3",options="header"]
|===
|Level |Description

|`NONE`
|No validation.

|`SYNTAX_ONLY`
|Validates that the content is syntactically valid JSON and is a JSON object.

|`FULL`
a|Complete schema validation including:

* Required `name` field (non-empty string)
* `description` (non-empty string) and `version` (string) fields
* `supportedInterfaces` array with at least one interface, where each interface has `url`, `protocolBinding`, and `protocolVersion`
* `provider` object with `organization` and `url`, when present
* `skills` array with at least one skill, where each skill has `id`, `name`, `description`, and a non-empty `tags` array
* `capabilities` object with boolean values
* `defaultInputModes` and `defaultOutputModes` arrays
* Authentication and security scheme validation
* Valid JSON structure
|===

[id="a2a-compatibility-checking_{context}"]
== Agent Card compatibility rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
When you version Agent Cards, {registry} enforces compatibility rules to ensure that changes do not break existing clients.

*Compatible changes (allowed):*

* Adding new skills
* Adding new capabilities
* Adding authentication schemes
* Adding input or output modes

*Incompatible changes (can break clients):*

* Removing skills
* Removing or disabling capabilities
* Removing supported interfaces (matched by URL and protocol binding)
* Changing the protocol version on an existing interface
* Removing security schemes
* Removing input or output modes

// ref-a2a-artifact-references
[id="a2a-artifact-references_{context}"]
== References between agents, MCP servers, and tools

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Artifact references record which tools, servers, models, and prompts an agent uses, and which tools an MCP server provides. The references are registry metadata: Agent Card and `server.json` content is not changed.

.Allowed reference targets
[cols="1,2,3"]
|===
|Artifact type |Can reference |Meaning

|`AGENT_CARD`
|`MCP_TOOL`, `MCP_SERVER`, `MODEL_SCHEMA`, `PROMPT_TEMPLATE`, `AGENT_CARD`
|Tools, servers, models, and prompts the agent uses, and peer agents it delegates to.

|`MCP_SERVER`
|`MCP_TOOL`
|Tools the server provides.

|`MCP_TOOL`
|None
|
|===

The allowed target types are checked by the `INTEGRITY` rule at the `REFS_EXIST` or `FULL` level, together with the check that each referenced version exists. A reference to any other artifact type is rejected, and no version is created. Without an `INTEGRITY` rule, references are not checked, so enable `INTEGRITY` for groups that contain agent artifacts. Violations of this check report the `REFS_EXIST` level, also when the rule is configured as `FULL`. Other artifact types, including custom types, do not restrict the types they reference.

Reference names are not interpreted by {registry}. Use the name of the referenced tool, server, model, or prompt.

Versions are immutable, including their references. To change the tools that an MCP server provides, create a new version of the `MCP_SERVER` artifact. Creating a version with the number of an existing version is rejected.

Disabling or deleting a referenced version does not change the versions that reference it. Their references remain, and point to a version that is disabled or no longer exists.

To find the agents and servers that use a tool, query the inbound references of the tool version:

[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/get-weather/versions/1/references?refType=INBOUND"
----

== LLM lifecycle management

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
A2A integration includes full LLM lifecycle management with additional artifact types, including MODEL_SCHEMA and PROMPT_TEMPLATE.

The MODEL_SCHEMA artifact type defines input and output schemas for LLM agents:

.MODEL_SCHEMA artifact type
[source,json]
----
{
  "$schema": "https://apicurio.io/schemas/model-schema/v1",
  "modelId": "sentiment-analysis-output",
  "provider": "a2a-demo",
  "version": "1.0.0",
  "output": {
    "type": "object",
    "required": ["sentiment", "confidence"],
    "properties": {
      "sentiment": {"type": "string", "enum": ["positive", "negative", "neutral"]},
      "confidence": {"type": "number", "minimum": 0, "maximum": 1}
    }
  }
}
----

The PROMPT_TEMPLATE artifact type stores versioned prompt templates with variable support:

.PROMPT_TEMPLATE artifact type
[source,yaml]
----
templateId: sentiment-analysis
name: Sentiment Analysis Prompt
version: "1.0.0"

template: |
  Analyze the sentiment of the following message:

  MESSAGE: {{customerMessage}}

  Respond with JSON containing sentiment and confidence.

variables:
  customerMessage:
    type: string
    required: true
    description: The message to analyze

metadata:
  outputSchema: urn:apicurio:llm-agents.schemas/sentiment-output
----

Agent Cards can reference their schemas and prompts by using URN references:

.Artifact links
[source,json]
----
{
  "name": "Sentiment Agent",
  "skills": [
    {
      "id": "sentiment-analysis",
      "name": "Sentiment Analysis",
      "outputSchema": "urn:apicurio:llm-agents.schemas/sentiment-agent-output",
      "promptTemplate": "urn:apicurio:llm-agents.prompts/sentiment-agent-prompt"
    }
  ]
}
----

== Java SDK usage for A2A

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can use the Java SDK to discover agents and register Agent Cards programmatically.

.Agent discovery example
[source,java]
----
RegistryClient client = RegistryClientFactory.create(
    RegistryClientOptions.create("http://localhost:8080/apis/registry/v3"));

// Search for agents with specific skill
var agents = client.wellKnown().agents()
    .get(config -> {
        config.queryParameters.skill = List.of("translation");
        config.queryParameters.limit = 10;
    });

for (var agent : agents.getAgents()) {
    var interfaces = agent.getSupportedInterfaces();
    String url = (interfaces == null || interfaces.isEmpty()) ? "no interface" : interfaces.get(0).getUrl();
    System.out.println("Found: " + agent.getName() + " @ " + url);
}
----

.Agent Card registration example
[source,java]
----
CreateArtifact artifact = new CreateArtifact();
artifact.setArtifactId("my-agent");
artifact.setArtifactType("AGENT_CARD");

CreateVersion version = new CreateVersion();
version.setVersion("1.0.0");

VersionContent content = new VersionContent();
content.setContentType("application/json");
content.setContent(agentCardJson);
version.setContent(content);

artifact.setFirstVersion(version);

client.groups().byGroupId("ai-agents").artifacts()
    .post(artifact, config -> {
        config.queryParameters.ifExists = IfArtifactExists.FIND_OR_CREATE_VERSION;
    });
----

// ref-a2a-peer-registries
[id="a2a-peer-registries_{context}"]
== Peer registries for federation

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
A peer registry is another {registry} instance that this registry federates with. When federation is enabled, administrators register, update, and delete peers through the admin REST API. In this release, {registry} stores the peer definitions and does not query the peer registries.

IMPORTANT: Federation is experimental. Set `apicurio.features.experimental.enabled=true` together with `apicurio.federation.enabled=true`. With the federation flag alone, {registry} does not start.

.Federation configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`apicurio.federation.enabled`
|`false`
|Enable federation with peer registries, including the peer management API (experimental)

|`apicurio.federation.peer.insecure-http.enabled`
|`false`
|Allow peer URLs that use plain `http` instead of `https`. The property applies to every peer, including peers that you declare in GitOps or KubernetesOps storage.

|`apicurio.federation.peer.loopback.enabled`
|`false`
|Allow peer URLs that point at a loopback address or a localhost name, for development and tests. The property applies to every peer.

|`apicurio.features.experimental.enabled`
|`false`
|Set to `true` to use experimental features such as federation
|===

.Peer fields
[cols="1,1,4",options="header"]
|===
|Field |Required |Description

|`peerId`
|Yes
|Unique ID of the peer. Lowercase letters, digits, `.`, `_`, and `-` only, at most 256 characters. The ID `local` is reserved.

|`url`
|Yes
|Base URL of the peer registry, for example `https://registry.eu.example.com`. The URL must satisfy the peer URL policy.

|`name`
|No
|Display name of the peer, at most 512 characters.

|`description`
|No
|Description of the peer, at most 1024 characters.

|`enabled`
|On update
|Whether {registry} uses the peer for federation. The field defaults to `true` when you create a peer without it. The update operation requires the field.

|`credentialSecretRef`
|No
|Name of a key in the peer credentials directory of {registry} that holds the credential for this peer, for example a key of a mounted Secret. Letters, digits, `.`, `_`, and `-` only, at most 253 characters, case-sensitive, and not starting with `..`. The field is a reference only. {registry} never stores or returns a credential value.
|===

Peer URL policy::
{registry} validates the `url` when you create or update a peer, and rejects the request with HTTP 400 in the following cases:
+
* The URL is not an absolute `https` URL with a host. {registry} accepts plain `http` only when `apicurio.federation.peer.insecure-http.enabled` is `true`.
* The URL contains user information, a query, or a fragment, has a port outside the range 1 to 65535, or is longer than 1024 characters.
* The host is a link-local, unspecified, multicast, reserved, or cloud metadata address. {registry} accepts a loopback address or a localhost name only when `apicurio.federation.peer.loopback.enabled` is `true`.

.Peer management operations
[cols="3,1,4",options="header"]
|===
|Endpoint |Method |Description

|`/apis/registry/v3/admin/peers`
|GET
|List the peer registries, including disabled peers, ordered by `peerId`. The `limit` and `offset` query parameters page the result. The response contains the `peers` of the page and the total `count`.

|`/apis/registry/v3/admin/peers`
|POST
|Register a peer registry. The request body is the peer definition. Returns HTTP 409 when a peer with the same `peerId` exists.

|`/apis/registry/v3/admin/peers/\{peerId}`
|GET
|Get the definition of a peer registry.

|`/apis/registry/v3/admin/peers/\{peerId}`
|PUT
|Replace the definition of a peer registry. The body must contain `url` and `enabled`. {registry} clears the optional fields that you omit.

|`/apis/registry/v3/admin/peers/\{peerId}`
|DELETE
|Delete a peer registry.
|===

All peer operations require administrator access. When `apicurio.federation.enabled` is `false`, every peer operation returns HTTP 409. Create, update, and delete also return HTTP 409 when the storage is read-only.

.Example: registering a peer registry
[source,bash]
----
curl -X POST "http://localhost:8080/apis/registry/v3/admin/peers" \
  -H "Content-Type: application/json" \
  -d '{
    "peerId": "eu-registry",
    "url": "https://registry.eu.example.com",
    "name": "EU registry",
    "description": "Registry serving the EU region.",
    "enabled": true,
    "credentialSecretRef": "eu-registry"
  }'
----

ifndef::service-registry-downstream[]
The read-only GitOps and KubernetesOps storage types load the peer list from the `peers` field of the `registry-v0` metadata instead of the admin API. The peer URL policy applies to these peers too. For the field format, see xref:getting-started/assembly-configuring-gitops-storage.adoc#gitops-repository-data-format_{context}[GitOps repository data format] and xref:getting-started/assembly-configuring-kubernetesops-storage.adoc#kubernetesops-field-reference_{context}[KubernetesOps field reference].

// ref-a2a-troubleshooting
[id="a2a-troubleshooting_{context}"]
== A2A troubleshooting

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Use the following information to troubleshoot common issues with A2A features in {registry}.

A2A endpoints return 404::
A2A protocol support is experimental, and {registry} does not start with `apicurio.a2a.enabled=true` alone. Set both of the following properties:
+
[source,properties]
----
apicurio.features.experimental.enabled=true
apicurio.a2a.enabled=true
----

Agent Card validation fails::
Verify the following conditions:
+
* The `name` and `description` fields are present and non-empty, and the `version` field is a string.
* The `supportedInterfaces`, `capabilities`, `defaultInputModes`, and `defaultOutputModes` fields are present, and `supportedInterfaces` contains at least one interface.
* Each skill has `id`, `name`, `description`, and a non-empty `tags` array.
* Capabilities are boolean values.
* The JSON is well-formed.

Search returns no results::
Verify the following conditions:
+
* Agent Cards are stored with type `AGENT_CARD`.
* The registry extracted labels correctly (check artifact labels).
* Search filters match stored values exactly.
