== A2A protocol overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
With the A2A protocol, AI agents can discover and communicate with each other through standardized endpoints. {registry} serves as both an A2A agent and an agent registry.

{registry} as an A2A agent:: {registry} provides its own capabilities, including schema validation, search, and artifact management.
{registry} as an agent registry:: {registry} stores and discovers other agents' Agent Cards.

.{registry} dual-role A2A architecture
[cols="1,1",options="header"]
|===
|{registry} as an A2A agent
|{registry} as an agent card registry

a|Endpoint: `/.well-known/agent.json`

Built-in skills:

* `schema-validation`
* `schema-search`
* `artifact-management`
* `compatibility-check`
* `agent-discovery`

a|Endpoints:

* `/.well-known/agents`
* `/.well-known/agents/\{groupId}/\{artifactId}`

Capabilities:

* Store agent cards as `AGENT_CARD` artifacts
* Search by skill, capability, or input/output mode
* Version management and compatibility checking
|===

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} provides the following well-known endpoints for A2A agent discovery and retrieval.

GET /.well-known/agent.json::
Retrieves the Agent Card for the {registry} instance. This endpoint requires no authentication. The same card is available at `/.well-known/agent-card.json`.
+

+

----
{
  "name": "Apicurio Registry",
  "description": "API and Schema Registry with A2A Agent support",
  "version": "3.3.3",
  "protocolVersion": "1.0",
  "supportedInterfaces": [
    {
      "url": "http://localhost:8080",
      "protocolBinding": "http+json",
      "protocolVersion": "1.0"
    }
  ],
  "provider": {
    "organization": "Apicurio",
    "url": "https://www.apicur.io"
  },
  "capabilities": {
    "streaming": false,
    "pushNotifications": false,
    "extendedAgentCard": false
  },
  "skills": [
    {
      "id": "schema-validation",
      "name": "Schema Validation",
      "description": "Validate schemas against format specifications (Avro, JSON Schema, Protobuf, OpenAPI, etc.)",
      "tags": ["schema", "validation", "avro", "json-schema", "protobuf", "openapi"]
    },
    {
      "id": "schema-search",
      "name": "Schema Search",
      "description": "Search for schemas and APIs in the registry by name, description, labels, or content",
      "tags": ["schema", "search", "discovery"]
    }
  ],
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "securitySchemes": {
    "bearer": {
      "type": "httpAuth",
      "scheme": "Bearer"
    }
  }
}
----
+
The example shows two of the five built-in skills. The `securitySchemes` object lists only the mechanisms that are enabled: `bearer` when OIDC authentication is enabled, `basic` when basic authentication is enabled, and `apiKey` when `apicurio.a2a.agent.auth.api-key.enabled` is `true`. The Agent Card includes `documentationUrl` and `iconUrl` only when you configure the corresponding properties.

GET /.well-known/agents::
Searches for registered Agent Cards with filtering support. This endpoint requires no authentication. When any authentication mechanism is enabled, the search returns only the Agent Cards that the caller has permission to view, based on the `apicurio.agent.visibility` label.
+
.Query parameters for /.well-known/agents
[cols="1,1,3",options="header"]
|===
|Parameter |Type |Description

|`name`
|string
|Filter by artifact name or artifact ID. A value without `+*+` matches anywhere in the name or ID. Use `+*+` as a prefix or suffix wildcard, for example `weather*`.

|`skill`
|string (repeatable)
|Filter by skill ID

|`capability`
|string (repeatable)
|Filter by capability (for example, `streaming:true`). Append `:false` to require that a capability is absent or disabled.

|`inputMode`
|string (repeatable)
|Filter by input mode (for example, `text`, `image`)

|`outputMode`
|string (repeatable)
|Filter by output mode

|`offset`
|integer
|Pagination offset (default: 0)

|`limit`
|integer
|Pagination limit (default: 20, maximum: 500)

|`publicOnly`
|boolean
|When `true`, return only Agent Cards with `public` visibility, whoever the caller is, even when authentication is disabled (default: `false`)

|`signedBy`
|string
|Experimental. Return only Agent Cards with a signature by the key with this `kid` that verifies against the keys {registry} trusts. See xref:a2a-signed-agent-cards_{context}[].
|===
+
.Example request
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?skill=translation&capability=streaming:true"
----
+
.Example response: AgentSearchResults
[source,json]
----
{
  "count": 1,
  "agents": [
    {
      "groupId": "ai-agents",
      "artifactId": "translator-agent",
      "name": "Translation Agent",
      "description": "Translates text between languages",
      "owner": "alice",
      "createdOn": 1756720530000,
      "supportedInterfaces": [
        {
          "url": "http://translator:9001",
          "protocolBinding": "http+json",
          "protocolVersion": "1.0"
        }
      ],
      "skills": ["translation"],
      "capabilities": {
        "streaming": true,
        "pushNotifications": false
      }
    }
  ]
}
----
+
The `count` field is the total number of matching Agent Cards, not the number of entries in the current page. The `skills` array lists skill IDs only. To get skill names and descriptions, retrieve the full Agent Card from `/.well-known/agents/\{groupId}/\{artifactId}`.
+
When {registry} applies `publicOnly=true`, the response contains the `publicOnly` field with the value `true`. A registry version that does not support the parameter ignores it and omits the field, so check for the field if you depend on the filter.

GET /.well-known/agents/\{groupId}/\{artifactId}::
Retrieves a specific registered Agent Card.
+
*Path parameters*
+
* `groupId` - The group containing the agent card
* `artifactId` - The artifact ID of the agent card
+
*Query parameters*
+
* `version` (optional) - Specific version (defaults to latest)
+
Response: Agent Card JSON document

[id="a2a-visibility-model_{context}"]
== Agent visibility model

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Agent Cards support three visibility levels, controlled by the `apicurio.agent.visibility` artifact label. Set the label on an Agent Card to control which clients can see it.

ifndef::service-registry-downstream[]
When any authentication mechanism is enabled, `GET /.well-known/agents` and the AI Catalog and ARD endpoints described in xref:getting-started/assembly-ai-catalog-ard.adoc[AI Catalog and ARD discovery] enforce visibility.
endif::[]
ifdef::service-registry-downstream[]
When any authentication mechanism is enabled, `GET /.well-known/agents` and the AI Catalog and ARD endpoints enforce visibility.
endif::[]

.Agent visibility levels
[cols="1,3",options="header"]
|===
|Visibility |Behavior

|`public`
|Visible to everyone, including unauthenticated clients

|`entitled`
|Visible to callers who can read artifacts: a registry role (`sr-readonly`, `sr-developer` or `sr-admin`) when role-based authorization is enabled, any authenticated user when `apicurio.auth.authenticated-read-access.enabled` is set or a trusted proxy has authorized the request, and unauthenticated clients when `apicurio.auth.anonymous-read-access.enabled` is set (this is the default)

|`private`
|Visible only to the artifact owner and registry administrators
|===

When per-resource authorization is enabled (`apicurio.auth.resource-based-authorization.enabled`), discovery shows only agents in artifacts that the caller's access rules allow them to read, before the visibility label is applied. An `entitled` agent is then visible only to callers who can read its group or artifact, and a `public` agent in a group the caller cannot read is hidden as well, including from unauthenticated clients. The visibility label narrows what callers with read access discover. It never grants access.

.Visibility label example
[source,bash]
----
curl -X PUT "http://localhost:8080/apis/registry/v3/groups/my-agents/artifacts/my-agent" \
  -H "Content-Type: application/json" \
  -d '{"labels": {"apicurio.agent.visibility": "public"}}'
----

*How entitlements work:* {registry} maps the A2A community entitlement concept to its existing RBAC model:

* *Groups* act as organizational namespaces
* *Entitling a client* = granting read access to the group containing the Agent Card artifacts. Registry roles grant read access to all groups. To entitle a client to specific groups only, enable per-resource authorization and grant `READ` on those groups in the access rules
* *Client authentication* happens in an external identity provider, such as {keycloak} or another OIDC provider
* No new authorization primitives are required

.Discovery and entitlement configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`apicurio.a2a.default-visibility`
|`entitled`
|Visibility of an Agent Card that has no `apicurio.agent.visibility` label (`public`, `entitled`, or `private`). {registry} applies the value when it filters discovery results and does not add the label to the artifact. A change to this property therefore changes the visibility of every unlabeled Agent Card, including existing ones.
|===

Visibility labels control which Agent Cards appear in `/.well-known/agents` search results and in the AI Catalog and ARD responses. When you retrieve a card by ID through `/.well-known/agents/\{groupId}/\{artifactId}` or the core REST API, only read authorization applies. {registry} does not check the visibility label.

NOTE: When no authentication mechanism is configured (OIDC, basic, proxy header, Kubernetes, or form), {registry} skips visibility filtering and all agents are visible to all users, unless a `GET /.well-known/agents` request sets `publicOnly=true`.

NOTE: This visibility model applies only to Agent Cards. MCP tool definitions are not subject to `apicurio.agent.visibility` or `apicurio.a2a.default-visibility`; see
ifndef::service-registry-downstream[]
xref:getting-started/assembly-mcp-tool-features.adoc#mcp-tool-visibility_{context}[MCP tool visibility]
endif::[]
ifdef::service-registry-downstream[]
xref:mcp-tool-visibility_{context}[MCP tool visibility]
endif::[]
for details.

[id="a2a-federated-agent-search_{context}"]
== Federated agent search

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
With federated agent search, one request searches the Agent Cards of this registry and of its enabled peer registries. The response names the source of each agent and reports an outcome for every source, so a slow or unavailable peer does not fail the search.

A peer registry is another registry that an administrator registers with this registry, for example through the `/apis/registry/v3/admin/peers` REST API. {registry} searches only the peers that are enabled.

To use federated agent search, enable A2A protocol support and set `apicurio.federation.enabled=true`. The `apicurio.agents.enabled` property does not enable federation.

NOTE: `apicurio.federation.enabled` is an experimental property. You must also set `apicurio.features.experimental.enabled=true` to use it.

The `GET /apis/registry/v3/search/federated` endpoint requires read-level authorization. It accepts the `name`, `skill`, `capability`, `inputMode`, and `outputMode` parameters of `GET /.well-known/agents` and applies them to every source. It does not accept `offset` or `limit`. The `perSourceLimit` parameter sets the maximum number of agents that each source returns, and defaults to 20. {registry} lowers a value above `apicurio.federation.search.per-source-limit.max` to that maximum.

.Example request
[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/search/federated?skill=translation&perSourceLimit=10"
----

.Example response: FederatedAgentSearchResults
[source,json]
----
{
  "agents": [
    {
      "source": "local",
      "groupId": "ai-agents",
      "artifactId": "translator-agent",
      "name": "Translation Agent",
      "skills": ["translation"],
      "owner": "alice"
    },
    {
      "source": "eu-registry",
      "groupId": "ai-agents",
      "artifactId": "translator-agent",
      "name": "Translation Agent",
      "skills": ["translation"]
    }
  ],
  "sources": [
    {
      "source": "local",
      "outcome": "ok",
      "count": 1,
      "truncated": false
    },
    {
      "source": "eu-registry",
      "outcome": "ok",
      "count": 1,
      "truncated": false
    },
    {
      "source": "us-registry",
      "outcome": "failed",
      "reason": "timeout",
      "count": 0,
      "truncated": false
    }
  ]
}
----

Each entry in `agents` has a `source` field and the agent fields that `GET /.well-known/agents` returns, which are `groupId`, `artifactId`, `name`, `description`, `supportedInterfaces`, `skills`, `capabilities`, `createdOn`, and `owner`. The example shows only some of them. The agents of this registry come first, with the source `local`, followed by the agents of each peer in peer ID order. An agent from a peer has no `owner` field. If two sources return an agent with the same group ID and artifact ID, the response contains both.

The search of this registry applies the visibility rules of the caller. {registry} calls each peer at `/.well-known/agents` with `publicOnly=true` and without credentials, so a peer returns only Agent Cards with `public` visibility. An Agent Card without the `apicurio.agent.visibility` label is public only if the peer sets `apicurio.a2a.default-visibility` to `public`. A peer that keeps the default value, `entitled`, returns only the Agent Cards whose label has the value `public`, even when authentication is disabled on the peer. {registry} never sends the credentials of the caller to a peer.

The `sources` array has one entry for this registry and one for each enabled peer.

.Fields of a `sources` entry
[cols="1,3",options="header"]
|===
|Field |Description

|`source`
|`local` for this registry, or the ID of the peer

|`outcome`
|`ok`, `deadline_exceeded`, `unsupported`, or `failed`

|`reason`
|Why {registry} could not search the peer. Present only when the outcome is `failed`.

|`count`
|Number of agents from this source in the response

|`truncated`
|`true` when the source reported more matching agents than it returned
|===

Only an administrator sees which peer is which and why a peer failed. The example response is what an administrator receives. For federated search, an administrator is a caller that has the administrator role while role-based authorization is enabled, or a caller that the admin override (`apicurio.auth.admin-override.*`) identifies as an administrator. For any other caller, the `source` of a peer is `peer-1`, `peer-2`, and so on, numbered in peer ID order within the response, and the `reason` field is absent. When authentication is disabled, every caller sees the peer IDs and the reasons.

.Source outcomes
[cols="1,3",options="header"]
|===
|Outcome |Description

|`ok`
|The source answered, and its agents are in the response.

|`deadline_exceeded`
|The search reached `apicurio.federation.search.deadline-ms` before the peer answered.

|`unsupported`
|The peer has no agent search endpoint, or its response did not confirm the `publicOnly` filter. {registry} discards the response.

|`failed`
|{registry} could not search the peer. The `reason` field says why.
|===

.Failure reasons
[cols="1,3",options="header"]
|===
|Reason |Description

|`unauthorized`
|The peer answered with HTTP 401 or 403.

|`unreachable`
|{registry} could not connect to the peer, or the address of the peer is not allowed.

|`timeout`
|The peer did not answer within `apicurio.federation.search.peer-timeout-ms`.

|`peer_error`
|The peer answered with a server error or with a redirect. {registry} does not follow redirects.

|`invalid_response`
|The response of the peer was malformed, too large, inconsistent, or not JSON. {registry} also reports this reason when the peer answers with an HTTP status that no other reason or outcome covers, for example 400 or 429.

|`circuit_open`
|The circuit breaker of the peer is open, and {registry} did not call the peer.

|`capacity_exceeded`
|{registry} did not call the peer because a limit on peer calls was reached. The configuration properties table describes the limits that you can set.
|===

{registry} calls the peers in parallel while it searches its own Agent Cards. The endpoint returns HTTP 200 whenever the search of this registry succeeds, even if some or all peers fail, so check `sources` to see which peers answered.

Each peer has its own circuit breaker, which counts connection failures, timeouts, and server error or redirect responses as failures. While the circuit breaker of a peer is open, {registry} does not call that peer.

.Error responses
[cols="1,3",options="header"]
|===
|Status |Cause

|400
|`perSourceLimit` is below 1, or the request carries the `X-Federation-Hop` header that {registry} adds to its calls to peers

|404
|A2A protocol support is not enabled

|409
|Federation is not enabled

|503
|The search of this registry did not finish within `apicurio.federation.search.deadline-ms`
|===

.Federated search configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`apicurio.federation.search.deadline-ms`
|`5000`
|Time in milliseconds that a federated search can take in total

|`apicurio.federation.search.peer-timeout-ms`
|`3000`
|Time in milliseconds that one peer has to answer. The value must be lower than `apicurio.federation.search.deadline-ms`.

|`apicurio.federation.search.per-source-limit.max`
|`100`
|Highest value that `perSourceLimit` can have

|`apicurio.federation.search.max-peers`
|`16`
|Maximum number of peers that one search queries. The peer management API refuses to enable more peers. If more peers are enabled anyway, for example after you lower this value, a search queries the first ones in peer ID order and reports the others as `failed` with the reason `capacity_exceeded`.

|`apicurio.federation.search.max-searches-per-caller`
|`2`
|Maximum number of federated searches that one caller can have in progress at once. A search beyond the limit still searches this registry, but calls no peer and reports every peer as `failed` with the reason `capacity_exceeded`. {registry} identifies an authenticated caller by principal name and an anonymous caller by network address.

|`apicurio.federation.search.max-concurrent-calls`
|`64`
|Maximum number of calls to peers in progress at once, across all federated searches. {registry} reports a peer whose call exceeds the limit as `failed` with the reason `capacity_exceeded`.

|`apicurio.federation.search.max-response-bytes`
|`1048576`
|Maximum size in bytes of the response that {registry} accepts from one peer

|`apicurio.federation.search.breaker.request-volume-threshold`
|`4`
|Number of recent calls to a peer that {registry} must have made before the circuit breaker of the peer can open

|`apicurio.federation.search.breaker.failure-ratio`
|`0.5`
|Share of the recent calls to a peer that must have failed for the circuit breaker of the peer to open

|`apicurio.federation.search.breaker.delay-ms`
|`30000`
|Time in milliseconds that an open circuit breaker waits before it lets a call through to the peer again
|===

When federation is enabled, {registry} checks these values at startup and does not start if a value is out of range.

// ref-a2a-peer-registries
[id="a2a-peer-registries_{context}"]
== Peer registries for federated agent search

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
As an administrator, you manage the peer registries through the `/apis/registry/v3/admin/peers` REST API. A registry that uses GitOps or KubernetesOps storage loads its peers from the `peers` list of the registry configuration instead.

The peer management API requires `apicurio.federation.enabled=true`, and every operation returns HTTP 409 without it. xref:a2a-federated-agent-search_{context}[Federated agent search] describes how to enable federation and how {registry} searches the peers.

.Peer fields
[cols="1,1,4",options="header"]
|===
|Field |Required |Description

|`peerId`
|Yes
|Unique ID of the peer. Lowercase letters, digits, `.`, `_`, and `-` only, at most 256 characters. The ID cannot be `.` or `..`, and the ID `local` is reserved.

|`url`
|Yes
|Base URL of the peer registry, for example `\https://registry.eu.example.com`. To search the peer, {registry} adds `/.well-known/agents` to this URL.

|`name`
|No
|Display name of the peer, at most 512 characters.

|`description`
|No
|Description of the peer, at most 1024 characters.

|`enabled`
|On update
|Whether federated agent search queries the peer. When you create a peer without this field, the peer is enabled.

|`credentialSecretRef`
|No
|Name that refers to a credential for the peer. Uppercase and lowercase letters, digits, `.`, `_`, and `-` only, at most 253 characters. The name cannot be a single period or begin with two periods. {registry} stores this name and returns it in API responses, but does not use it when it calls the peer. Do not enter a credential value.
|===

{registry} checks the `url` when you create or update a peer, and when it loads a peer from GitOps or KubernetesOps data. When a URL fails the check, the peer management API returns HTTP 400, and a load from GitOps or KubernetesOps data fails. The URL must meet the following conditions:

* The URL is an absolute `https` URL with a host. {registry} accepts plain `http` only when `apicurio.federation.peer.insecure-http.enabled` is `true`.
* The URL has no user information, query, or fragment. A port, if present, is in the range 1 to 65535. The URL is at most 1024 characters long.
* The host is not a link-local, unspecified, multicast, reserved, or cloud metadata address. {registry} accepts a loopback address or a `localhost` name only when `apicurio.federation.peer.loopback.enabled` is `true`.

Before each call to a peer, {registry} checks the scheme and the host again. When the host is a name, the address conditions apply to every address that the name resolves to.

.Peer URL configuration properties
[cols="2,1,3",options="header"]
|===
|Property |Default |Description

|`apicurio.federation.peer.insecure-http.enabled`
|Value of `apicurio.outbound.insecure-http.enabled`, `false` by default
|Allow peer URLs that use plain `http` instead of `https`

|`apicurio.federation.peer.loopback.enabled`
|Value of `apicurio.outbound.loopback.enabled`, `false` by default
|Allow peer URLs that point at a loopback address or a `localhost` name, for development and tests
|===

Both properties apply to every peer, including the peers that {registry} loads from GitOps or KubernetesOps data. The `apicurio.outbound.*` properties are also the defaults for imports from MCP servers.

.Peer management operations
[cols="3,1,4",options="header"]
|===
|Endpoint |Method |Description

|`/apis/registry/v3/admin/peers`
|GET
|List the peers, including disabled peers, ordered by `peerId`. The `limit` and `offset` query parameters page the result, and default to 20 and 0. The response contains the `peers` of the page and the total `count`.

|`/apis/registry/v3/admin/peers`
|POST

== Agent Card artifact type

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} stores Agent Cards as artifacts with type `AGENT_CARD`. You can create Agent Cards by using the REST API and you can validate them against the A2A specification JSON schema.

.Agent Card creation example
[source,bash]
----
curl -X POST "http://localhost:8080/apis/registry/v3/groups/ai-agents/artifacts" \
  -H "Content-Type: application/json" \
  -d '{
    "artifactId": "my-agent",
    "artifactType": "AGENT_CARD",
    "firstVersion": {
      "version": "1.0.0",
      "content": {
        "contentType": "application/json",
        "content": "{\"name\": \"My Agent\", \"description\": \"Executes tasks on request\", \"version\": \"1.0.0\", \"supportedInterfaces\": [{\"url\": \"https://my-agent.example.com\", \"protocolBinding\": \"http+json\", \"protocolVersion\": \"1.0\"}], \"capabilities\": {\"streaming\": false, \"pushNotifications\": false}, \"skills\": [{\"id\": \"task\", \"name\": \"Task Execution\", \"description\": \"Runs a task and returns the result\", \"tags\": [\"task\"]}], \"defaultInputModes\": [\"text/plain\"], \"defaultOutputModes\": [\"text/plain\"]}"
      }
    }
  }'
----

{registry} expects Agent Cards in the A2A protocol v1.0 format. A v1.0 Agent Card declares its endpoints in `supportedInterfaces` and its authentication in `securitySchemes`, not in a top-level `url` or `authentication` field. At the `FULL` level, the `VALIDITY` rule checks the required fields and the field types, as described in xref:a2a-validation-rules_{context}[Agent Card validation rules].

.Agent Card fields
[cols="2,1,4",options="header"]
|===
|Field |Required |Description

|`name`
|Yes
|Name of the agent. A non-empty string.

|`description`
|Yes
|Description of what the agent does. A non-empty string.

|`version`
|Yes
|Version of the agent, as a string.

|`protocolVersion`
|No
|A2A protocol version that the agent supports, for example `1.0`.

|`supportedInterfaces`
|Yes
|Array with at least one interface. Each interface has an `http` or `https` `url`, a `protocolBinding` such as `http+json`, and a `protocolVersion`. An interface can also have a `tenant`.

|`provider`
|No
|Organization that provides the agent. When present, the object must contain `organization` and an `http` or `https` `url`.

|`capabilities`
|Yes
|Object with the optional boolean fields `streaming`, `pushNotifications`, and `extendedAgentCard`, and an optional `extensions` array.

|`skills`
|Yes
|Array with at least one skill. Each skill has an `id`, a `name`, a `description`, and a `tags` array with at least one tag. The optional skill fields are `examples`, `inputModes`, `outputModes`, and `securityRequirements`.

|`defaultInputModes`
|Yes
|Array of the input modes that the agent supports, for example `text/plain` or `application/json`.

|`defaultOutputModes`
|Yes
|Array of the output modes that the agent supports.

|`securitySchemes`
|No
|Object that maps each scheme name to a security scheme definition.

|`securityRequirements`
|No
|Array of objects that map security scheme names to the required scopes.

|`iconUrl`
|No
|URL of an icon for the agent.

|`documentationUrl`
|No
|URL of the agent documentation.

|`signatures`
|No
|Array of JSON Web Signature (JWS) signatures of the Agent Card. Each signature has a `protected` string and a `signature` string, and can have a `header` object.
|===

// ref-a2a-openapi-agent-card
[id="a2a-openapi-agent-card_{context}"]
== Auto-generating Agent Cards from OpenAPI specifications

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
If you already document your API with OpenAPI, you can embed Agent Card metadata in the `info` block of your OpenAPI specification by using the `x-agent-card` vendor extension, instead of maintaining a separate `AGENT_CARD` artifact by hand.

{registry} detects the extension, assembles a valid Agent Card from it, and stores it as a companion artifact.

.Enabling OpenAPI-to-Agent-Card auto-generation
[cols="2,1,3"]
|===
|Property |Default |Description

|`apicurio.a2a.openapi-integration.enabled`
|`false`
|Auto-generate a companion AGENT_CARD artifact from the `x-agent-card` OpenAPI vendor extension

|`apicurio.a2a.openapi-integration.sync-on-update.enabled`
|`true`
|Update the generated Agent Card whenever its source OpenAPI artifact is updated
|===

NOTE: `apicurio.a2a.openapi-integration.enabled` is an experimental property. You must also set `apicurio.features.experimental.enabled=true` to use it.

.Example `x-agent-card` extension
[source,yaml]
----
openapi: "3.0.0"
info:
  title: Weather API
  description: Retrieves weather forecasts by city
  version: "1.0.0"
  x-agent-card:
    capabilities: {}
    skills:
      - id: get-weather
        name: Get Weather
        description: Retrieve the current weather for a city
        tags: [weather]
    defaultInputModes: [text]
    defaultOutputModes: [text]
servers:
  - url: https://weather.example.com
----

When {registry} publishes an OPENAPI artifact version with an `x-agent-card` extension under `info`, it:

. Derives any of `name`, `description`, and `version` that the extension does not explicitly set, from the OpenAPI document's own `info.title`, `info.description`, and `info.version`.
. Derives `supportedInterfaces` from `servers[]` only when omitted, expanding server variables using their string defaults and using `http+json` as the binding. Explicit malformed values are rejected rather than replaced. Relative URLs require explicit absolute `supportedInterfaces`; the registry does not guess a base URL. Publishers must ensure the advertised endpoint actually implements A2A; OpenAPI alone does not establish this.
. Validates the assembled Agent Card against the same A2A v1.0 schema used for `AGENT_CARD` artifacts. If the assembled card is not valid, the OpenAPI write itself is rejected (HTTP 400) with a `RuleViolationException`, and nothing is persisted.
. Creates or updates `<artifactId>-agent-card` in the same group, checking companion ownership and applying its configured rules. Companion failure is logged and leaves the successful source write intact; rejected companion content is never persisted.

Ordinary DRAFT creates/edits do not generate published companions. Transitioning a draft to a published state validates and generates from its edited content. Dry-run requests do not write companions. Published updates re-read the source tip, and conditional target-version writes prevent a concurrent manual version from being superseded.

In the extension, you must explicitly supply the required Agent Card fields that have no OpenAPI equivalent: `capabilities`, `skills`, `defaultInputModes`, and `defaultOutputModes`.

{registry} marks the companion artifact and its source OpenAPI artifact with `apicurio.a2a.openapi-agent-card.*` labels:

.Provenance and sync labels
[cols="2,3"]
|===
|Label |Meaning

|`apicurio.a2a.openapi-agent-card.generated` (on the companion)
|`true` if this artifact was generated by this feature

|`apicurio.a2a.openapi-agent-card.source-group-id` / `.source-artifact-id` (on the companion)
|Identifies the source OpenAPI artifact this companion was generated from

|`apicurio.a2a.openapi-agent-card.generated-hash` (on each generated companion version)
|Canonical hash committed with that generated content. Missing or mismatched provenance stops automatic synchronization.

|`apicurio.a2a.openapi-agent-card.source-global-id` (on each generated companion version)
|The exact source version; deletion/recreation of the source does not silently adopt the old companion.

|`apicurio.a2a.openapi-agent-card.artifact-id` (on the source OpenAPI artifact)
|The artifact ID of its generated companion Agent Card
|===

If you edit the generated Agent Card artifact directly, {registry} detects this the next time the source OpenAPI artifact changes (the companion's latest version content no longer matches its recorded generated hash) and skips the sync rather than overwriting your edit, logging a warning instead.

If an artifact already exists with the same name as the companion (`<artifactId>-agent-card`) but was not generated by this feature, {registry} leaves it untouched and logs a warning rather than overwriting it.

Labels are editable provenance/navigation hints, never authorization grants. Owner-only access is checked independently on the companion. Generation provenance is stored atomically with each version; failure updating the source navigation link can be repaired on a subsequent unchanged-content synchronization. A manually edited version without generation provenance is preserved. Regeneration after manual changes requires an explicit user decision, not deletion of its hash label.

**Known limitations**

* REST publication paths trigger generation: first published version, new published version, `ifExists=UPDATE`/`FIND_OR_CREATE_VERSION`, and publication of an edited draft. KafkaSQL REST requests journal both writes; replay itself does not generate an extra companion. Confluent-compatible APIs and read-only GitOps/KubernetesOps imports do not trigger generation.
* Source and companion are separate artifacts, not one transaction. Companion errors leave the source intact; repeated optimistic conflicts are bounded and logged. A later publication retries from current source content.
* Deleting the source OpenAPI artifact does not delete its generated companion Agent Card.
* AsyncAPI does not currently support the `x-agent-card` extension.

// ref-a2a-signed-agent-cards
[id="a2a-signed-agent-cards_{context}"]
== Signed Agent Cards

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
An Agent Card can carry JSON Web Signatures in its `signatures` array, as section 8.4 of the A2A v1.0 specification describes. {registry} can verify these signatures against the public keys of the publishers you trust, reject Agent Cards whose signatures do not verify, and tell discovery clients which trusted key signed each Agent Card. This feature is experimental.

IMPORTANT: A verified signature proves that the Agent Card was signed with a key you trust and has not been changed since. It does not prove that the agent is safe or well-behaved, or that the agent serving requests at the card's URLs is the one that signed it.

*How a signature is verified*

Each entry of `signatures` is a JWS (RFC 7515) with a detached payload: the RFC 8785 (JCS) canonical form of the Agent Card without its `signatures` member. A signature verifies when:

* Its protected header has `alg`, `typ` set to `JOSE`, and `kid`, and no `crit`. The unprotected `header` is ignored.
* `alg` is in `apicurio.a2a.signature-verification.allowed-algs`. `none` and HMAC algorithms are never accepted.
* A trusted key with that `kid` verifies the signature.

The A2A specification also asks signers to remove fields with default values before canonicalizing, which cannot be reproduced exactly without the Agent Card's Protocol Buffer schema. {registry} therefore accepts a signature computed over the Agent Card exactly as stored, or over the Agent Card with empty strings, arrays, objects and `null` values removed, which is what the reference A2A Python SDK signs. As with that SDK, empty values can be added to or removed from a signed Agent Card without breaking its signatures. An Agent Card with duplicate property names never verifies.

*Trusted keys*

`apicurio.a2a.signature-verification.jwks-urls`:: URLs of JSON Web Key Sets (JWKS) holding the public keys of the publishers you trust.
`apicurio.a2a.signature-verification.jku-allowed-hosts`:: Hosts, such as `keys.example.com` or `*.example.com`, whose key sets may be fetched from the `jku` header of a signature. A `jku` on any other host is never fetched. By default the list is empty and `jku` is never followed.

Key sets are fetched under the server-wide outbound rules: HTTPS is required unless `apicurio.outbound.insecure-http.enabled` is set, redirects are not followed, and loopback (unless `apicurio.outbound.loopback.enabled` is set), link-local and cloud metadata addresses are refused. Each fetch, from connecting to the last byte of the response, must finish within `apicurio.a2a.signature-verification.fetch.timeout.seconds` (default 5) and must not exceed `apicurio.a2a.signature-verification.fetch.max-size.bytes`. A key set is cached for `apicurio.a2a.signature-verification.cache-ttl.seconds` (default 300). A signature that names an unknown `kid` refreshes the key sets early, at most once per key set in that period, so a newly published key is picked up. A key removed from a key set stops counting once the key set is fetched again. A key set that cannot be fetched contributes no keys until it can be fetched again.

When neither property is set, which is the default, nothing is verified and no key set is ever fetched.

*Signature policy for writes*

`apicurio.a2a.signature-verification.mode` applies to every `AGENT_CARD` version published through the v3 or v2 REST API or the Confluent-compatible API, whether or not a rule is enabled. Because it is not a rule, disabling rules does not bypass it. Setting it to anything other than `off` requires `apicurio.features.experimental.enabled`.

[cols="1,3",options="header"]
|===
|Mode |Behavior

|`off` (default)
|Signatures are not checked when Agent Cards are written.

|`verify-if-present`
|An unsigned Agent Card is accepted. A signed Agent Card needs at least one signature that verifies. Other signatures, for example by keys you do not trust, do not cause a rejection.

|`require`
|Every Agent Card needs at least one signature that verifies.
|===

The policy applies when an artifact is created with its first version, when a version is added, and when a draft version is published. Draft versions are not checked until they are published. Dry runs are rejected exactly like real writes. A rejected write is reported like a rule violation, with one cause per signature that names its `kid` and the reason, for example `Signature by kid 'publisher-2026' rejected: unknown key`. Key material and signature values are never included.

The policy also applies to the Agent Cards that agent inventory synchronization creates, which go through the same v3 create path: an Agent Card that fails the policy is reported as `REJECTED`. In the v2 REST API, which has no dry runs and no drafts, the policy applies when an artifact is created, when a version is added or the artifact is updated, and to the test-update endpoint.

The following writes are not checked by the policy:

* Data import, through the admin import endpoints or the import at startup: it restores exported data, is restricted to administrators or the operator, and must reproduce the exported registry as it was.
* GitOps and KubernetesOps storage: the operator controls the repository or the Kubernetes resources that the registry loads.
* Agent Cards that {registry} generates from the `x-agent-card` extension of an OpenAPI document: the registry writes them itself, after the OpenAPI document was accepted, and they are never signed.
* Changes to the content of a draft version: the content is checked when the draft is published.

Whatever the path a card took, its signatures are always verified when it is read, so `verifiedSigners` and `signedBy` only report signatures that verify against the keys trusted at that moment.

*Signers in discovery*

Whether a signature verifies is computed when the Agent Card is read, from its content and the keys trusted at that moment; nothing is stored. Labels and metadata therefore cannot add or remove a verified signer.

* In `/.well-known/agents` results, `verifiedSigners` lists the `kid` of each signature that verifies. It is absent when no trusted keys are configured.
* `/.well-known/agents?signedBy=<kid>` returns only the Agent Cards with a signature by that `kid` that verifies now. The candidates are found through the `kid` each signature claims, and every candidate is then verified.

NOTE: The claimed `kid` of each signature is indexed when an Agent Card version is written. On SQL storage, Agent Cards whose latest version was stored before upgrading to this version of {registry} are found by `signedBy` only after a new version is added. KafkaSQL, GitOps and KubernetesOps storage rebuild the index when they start.

.Example: trust one publisher and require signed Agent Cards
[source,properties]
----
apicurio.features.experimental.enabled=true
apicurio.a2a.signature-verification.mode=require
apicurio.a2a.signature-verification.jwks-urls=https://keys.example.com/.well-known/jwks.json
----

.Example: find the Agent Cards signed by a trusted key
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?signedBy=publisher-2026"
----

[id="a2a-artifact-references_{context}"]
== References between agents, MCP servers, and tools

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Artifact references record which tools, servers, models, and prompts an agent uses, and which tools an MCP server provides. The references are registry metadata: Agent Card and `server.json` content is not changed.

.Allowed reference targets
[cols="1,2,3"]
|===
|Artifact type |Can reference |Meaning

|`AGENT_CARD`
|`MCP_TOOL`, `MCP_SERVER`, `MODEL_SCHEMA`, `PROMPT_TEMPLATE`, `AGENT_CARD`
|Tools, servers, models, and prompts the agent uses, and peer agents it delegates to.

|`MCP_SERVER`
|`MCP_TOOL`
|Tools the server provides.

|`MCP_TOOL`
|None
|
|===

The allowed target types are checked by the `INTEGRITY` rule at the `REFS_EXIST` or `FULL` level, together with the check that each referenced version exists. A reference to any other artifact type is rejected, and no version is created. Without an `INTEGRITY` rule, references are not checked, so enable `INTEGRITY` for groups that contain agent artifacts. Violations of this check report the `REFS_EXIST` level, also when the rule is configured as `FULL`. Other artifact types, including custom types, do not restrict the types they reference.

Reference names are not interpreted by {registry}. Use the name of the referenced tool, server, model, or prompt.

Versions are immutable, including their references. To change the tools that an MCP server provides, create a new version of the `MCP_SERVER` artifact. Creating a version with the number of an existing version is rejected.

Disabling or deleting a referenced version does not change the versions that reference it. Their references remain, and point to a version that is disabled or no longer exists.

To find the agents and servers that use a tool, query the inbound references of the tool version:

[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/get-weather/versions/1/references?refType=INBOUND"
----

== Java SDK usage for A2A

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can use the Java SDK to discover agents and register Agent Cards programmatically.

.Agent discovery example
[source,java]
----
RegistryClient client = RegistryClientFactory.create(
    RegistryClientOptions.create("http://localhost:8080/apis/registry/v3"));

// Search for agents with specific skill
var agents = client.wellKnown().agents()
    .get(config -> {
        config.queryParameters.skill = new String[] { "translation" };
        config.queryParameters.limit = 10;
    });

for (var agent : agents.getAgents()) {
    var interfaces = agent.getSupportedInterfaces();
    String url = (interfaces == null || interfaces.isEmpty()) ? "no interface" : interfaces.get(0).getUrl();
    System.out.println("Found: " + agent.getName() + " @ " + url);
}
----

.Agent Card registration example
[source,java]
----
CreateArtifact artifact = new CreateArtifact();
artifact.setArtifactId("my-agent");
artifact.setArtifactType("AGENT_CARD");

CreateVersion version = new CreateVersion();
version.setVersion("1.0.0");

VersionContent content = new VersionContent();
content.setContentType("application/json");
content.setContent(agentCardJson);
version.setContent(content);

artifact.setFirstVersion(version);

client.groups().byGroupId("ai-agents").artifacts()
    .post(artifact, config -> {
        config.queryParameters.ifExists = IfArtifactExists.FIND_OR_CREATE_VERSION;
    });
----

[id="a2a-troubleshooting_{context}"]
== A2A troubleshooting

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Use the following information to troubleshoot common issues with A2A features in {registry}.

A2A endpoints return 404::
Set `apicurio.agents.enabled=true`, which enables all agent discovery features, or `apicurio.a2a.enabled=true` alone. Check that `apicurio.a2a.enabled` is not set to `false`, which takes precedence:
+
[source,properties]
----
apicurio.features.experimental.enabled=true
apicurio.agents.enabled=true
----

Agent Card validation fails::
Verify the following conditions:
+
* The `name` and `description` fields are present and non-empty, and the `version` field is a string.
* The `supportedInterfaces`, `capabilities`, `defaultInputModes`, and `defaultOutputModes` fields are present, and `supportedInterfaces` contains at least one interface.
* The `skills` array contains at least one skill, and each skill has `id`, `name`, `description`, and a non-empty `tags` array.
* Capabilities are boolean values.
* The JSON is well-formed.

Search returns no results::
Verify the following conditions:
+
* Agent Cards are stored with type `AGENT_CARD`.
* The registry extracted labels correctly (check artifact labels).
* Search filters match stored values exactly.
