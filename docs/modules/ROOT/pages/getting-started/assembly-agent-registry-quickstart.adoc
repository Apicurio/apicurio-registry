[id="agent-registry-overview_{context}"]
== Agent registry overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
{registry} functions as both an A2A (Agent-to-Agent) agent that exposes its own capabilities and an agent registry that stores and serves the agent cards that other AI agents publish for discovery.

As an A2A agent, {registry} exposes capabilities such as schema validation, artifact management, and agent discovery.

The A2A protocol is a standard that AI agents use to discover and communicate with each other through well-known endpoints. MCP (Model Context Protocol) is a standard that LLM-powered tools such as Claude Desktop use to interact with external services and data sources.

{registry} supports the following AI and ML artifact types:

* `AGENT_CARD`: A2A agent card that describes an agent, its skills, and its capabilities
* `PROMPT_TEMPLATE`: versioned prompt template with variable substitution for LLM interactions
* `MODEL_SCHEMA`: input and output schema definition for an AI or ML model
* `MCP_TOOL`: MCP tool definition that describes a tool, its input parameters, and its output schema
* `MCP_SERVER`: MCP server definition that references the `MCP_TOOL` artifacts of the tools it provides

// con-agent-data-and-feature-flags
[id="agent-data-and-feature-flags_{context}"]
== Agent data and feature flags

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
The agent features are experimental and each one has its own configuration property, such as `apicurio.a2a.enabled` or `apicurio.mcp-tools.enabled`. The flags control the feature endpoints only. They do not control how {registry} stores agent artifacts.

* The AI and ML artifact types are always available. You can create, version, reference and search these artifacts through the core REST API, whether or not any agent feature is enabled.
* When you disable a feature, its endpoints stop responding: the `/.well-known` discovery endpoints and the MCP Registry API return `404`, and importing tools from an MCP server returns `409`. {registry} does not delete, hide or change any stored artifact, version, reference or label.
* Labels that a feature maintains, such as `apicurio.mcp-registry.*` and `apicurio.a2a.openapi-agent-card.*`, are kept when you update artifact metadata, even while the feature is disabled. The `apicurio.agent.visibility` label is a user label and is not changed.
* Artifacts that {registry} creates for you remain ordinary artifacts. For example, the input and output schemas embedded in a `MODEL_SCHEMA` or `PROMPT_TEMPLATE` artifact are registered as separate artifacts, such as `<artifactId>-input-schema`.
* If you enable a feature flag without setting `apicurio.features.experimental.enabled=true`, {registry} fails to start, rather than silently disabling the feature.

When an experimental feature becomes supported, changes incompatibly or is removed, the release notes describe the change. Stored agent artifacts stay readable through the core REST API.

[id="starting-agent-registry-quickstart_{context}"]
== Starting the agent registry quick start

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can start {registry} with the agent features enabled, the web console, and a demo catalog by using one Docker Compose command. The stack stores its data in PostgreSQL, so the catalog survives a restart.

IMPORTANT: The quick start stack is for local evaluation only. It has no authentication, and its database password is a fixed demo value. The agent features are experimental, and the stack uses the `latest-snapshot` images, which contain the most recent development build.

.Prerequisites
* Docker with Docker Compose v2 is installed
* `git` and `curl` are installed

.Procedure
. Clone the {registry} repository and change to its directory:
+
[source,bash]
----
git clone https://github.com/Apicurio/apicurio-registry.git
cd apicurio-registry
----
+
. Start the stack:
+
[source,bash]
----
docker compose -f distro/docker-compose/ai-agent-registry/docker-compose.yml up -d
----
+
The stack starts PostgreSQL, {registry} with the agent features enabled, and the web console. A `seed` container then loads the demo catalog into the `demo` group and exits.

.Verification
. Check that the demo catalog is loaded:
+
[source,bash]
----
docker compose -f distro/docker-compose/ai-agent-registry/docker-compose.yml logs seed
----
+
The output ends with `Demo catalog ready in group 'demo'.` The catalog contains the following artifacts:
+
* `weather`: an `MCP_SERVER` that references its `get_forecast` tool
* `weather.get_forecast`: an `MCP_TOOL` with a `BACKWARD` compatibility rule
* `translator-agent` and `sentiment-agent`: `AGENT_CARD` artifacts
* `support-reply`: a `PROMPT_TEMPLATE`
+
The seed container loads only the artifacts that do not exist yet, so restarting the stack does not change the catalog.
+
. Open the web console at `http://localhost:8888` and browse the `demo` group. The *Agents* tab lists the two agent cards.

// proc-exploring-the-demo-catalog
[id="exploring-demo-catalog_{context}"]
== Discovering agents and tools in the demo catalog

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
AI agents and orchestrators find agents and tools in {registry} through well-known discovery endpoints, without knowing the group or artifact ID in advance.

.Prerequisites
* The quick start stack is running

.Procedure
. Find the agents that have a translation skill:
+
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?skill=translation"
----
+
The response lists the `translator-agent` agent card.
+
. Retrieve the Agentic Resource Discovery (ARD) catalog, which lists every agent and tool that {registry} publishes:
+
[source,bash]
----
curl http://localhost:8080/.well-known/ard.json
----
+
. Search the catalog by name:
+
[source,bash]
----
curl -X POST http://localhost:8080/.well-known/ard/search \
  -H "Content-Type: application/json" \
  -d '{"query": {"text": "transla"}}'
----
+
The `results` list contains the *Translation Agent*.
+
. List the tools that the `weather` MCP server provides:
+
[source,bash]
----
curl http://localhost:8080/apis/registry/v3/groups/demo/artifacts/weather/versions/1/references
----
+
The server version references `weather.get_forecast` version `1`.

// proc-connecting-an-ai-assistant-by-using-mcp
[id="connecting-ai-assistant-via-mcp_{context}"]
== Connecting an AI assistant by using MCP

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can connect an MCP client, such as Claude Desktop or an IDE assistant, to the {registry} MCP server. The MCP server runs as a container that the client starts and talks to over standard input and output, and it reaches {registry} through the Docker network of the quick start stack.

.Prerequisites
* The quick start stack is running
* An MCP client that can start a local command, such as Claude Desktop

.Procedure
. Add the {registry} MCP server to the MCP configuration of your client. In Claude Desktop, open *Settings* > *Developer* > *Edit Config*:
+
[source,json]
----
{
  "mcpServers": {
    "apicurio-registry": {
      "command": "docker",
      "args": [
        "run", "-i", "--rm",
        "--network", "ai-agent-registry_default",
        "-e", "REGISTRY_URL=http://apicurio-registry:8080",
        "-e", "QUARKUS_OIDC_TENANT_ENABLED=false",
        "quay.io/apicurio/apicurio-registry-mcp-server:latest-snapshot"
      ]
    }
  }
}
----
+
. Restart the client.

.Verification
* Ask the assistant a question about the catalog, for example: "Which agents in Apicurio Registry can translate?"
+
The assistant uses the MCP server tools, such as `search_artifacts`, and answers with the Translation Agent.

// proc-rejecting-an-incompatible-tool-change
[id="rejecting-incompatible-tool-change_{context}"]
== Seeing a compatibility rule reject an incompatible tool change

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
A registry is more than a catalog: rules decide which changes are accepted. The demo `weather.get_forecast` tool has a `BACKWARD` compatibility rule, so a new version must accept every call that the previous version accepted. In this procedure, you try to make a new parameter required, which would break existing callers.

.Prerequisites
* The quick start stack is running
* You are in the root directory of the {registry} repository

.Procedure
* Try to create version `2` of the tool, which adds a required `units` parameter:
+
[source,bash]
----
curl -X POST http://localhost:8080/apis/registry/v3/groups/demo/artifacts/weather.get_forecast/versions \
  -H "Content-Type: application/json" \
  -d @distro/docker-compose/ai-agent-registry/test/get-forecast-v2-incompatible.json
----

.Verification
. {registry} rejects the version with HTTP status `400`. The response names each incompatible change, including `A property was made 'required'.` at `/inputSchema/required/1`.
. Check that the accepted version is unchanged:
+
[source,bash]
----
curl http://localhost:8080/apis/registry/v3/groups/demo/artifacts/weather.get_forecast/versions
----
+
The tool has only version `1`. Agents that use this tool keep getting the definition that they were built against.

// con-importing-tools-from-a-running-mcp-server
[id="importing-tools-from-running-mcp-server_{context}"]
== Importing tools from a running MCP server

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
Instead of writing `MCP_TOOL` artifacts by hand, you can import the tools of a running MCP server, and import them again when the server changes. The same compatibility rules apply, so an incompatible tool change is rejected on import.

NOTE: Importing tools from a running MCP server is planned for {registry} 3.4 and is not available in released versions. For the planned behavior, see xref:getting-started/assembly-mcp-tool-features.adoc[MCP tool definition features].

[id="registering-an-agent-card_{context}"]
== Registering an agent card

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can register an agent card as an `AGENT_CARD` artifact in {registry}. After registration, other AI agents and orchestrators can discover the agent by using the well-known endpoints.

.Prerequisites
* {registry} is running with agent features enabled

.Procedure
. Create a group to organize your agent cards:
+
[source,bash]
----
curl -X POST "http://localhost:8080/apis/registry/v3/groups" \
  -H "Content-Type: application/json" \
  -d '{
    "groupId": "ai-agents",
    "description": "AI agent cards"
  }'
----
+
. Register an agent card artifact in the group:
+
[source,bash]
----
curl -X POST "http://localhost:8080/apis/registry/v3/groups/ai-agents/artifacts" \
  -H "Content-Type: application/json" \
  -d '{
    "artifactId": "customer-support-agent",
    "artifactType": "AGENT_CARD",
    "firstVersion": {
      "version": "1.0.0",
      "content": {
        "contentType": "application/json",
        "content": "{\"name\": \"Customer Support Agent\", \"description\": \"Handles customer inquiries, analyzes sentiment, and generates responses\", \"version\": \"1.0.0\", \"supportedInterfaces\": [{\"url\": \"http://support-agent:9001\", \"protocolBinding\": \"http+json\", \"protocolVersion\": \"1.0\"}], \"provider\": {\"organization\": \"Acme Corp\", \"url\": \"https://acme.example.com\"}, \"skills\": [{\"id\": \"sentiment-analysis\", \"name\": \"Sentiment Analysis\", \"description\": \"Analyzes customer message sentiment\"}, {\"id\": \"response-generation\", \"name\": \"Response Generation\", \"description\": \"Generates context-aware customer responses\"}], \"capabilities\": {\"streaming\": false, \"pushNotifications\": false}, \"defaultInputModes\": [\"text\"], \"defaultOutputModes\": [\"text\"]}"
      }
    }
  }'
----

.Verification
. Verify that the agent card is available through the well-known agents endpoint:
+
[source,bash]
----
curl http://localhost:8080/.well-known/agents
----
+
The response includes the registered agent card with its skills and capabilities.

// proc-discovering-agents
[id="discovering-agents_{context}"]
== Discovering agents

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can discover registered agents by searching with query parameters such as agent name, skill ID, or capability. {registry} also exposes its own agent card at a dedicated well-known endpoint.

.Prerequisites
* {registry} is running with agent features enabled
* At least one agent card is registered

.Procedure
. Search for agents by name:
+
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?name=Customer"
----
+
. Search for agents by skill ID:
+
[source,bash]
----
curl "http://localhost:8080/.well-known/agents?skill=sentiment-analysis"
----
+
. Retrieve a specific agent card by group and artifact ID:
+
[source,bash]
----
curl "http://localhost:8080/.well-known/agents/ai-agents/customer-support-agent"
----
+
. View the {registry} built-in agent card:
+
[source,bash]
----
curl http://localhost:8080/.well-known/agent.json
----
+
You can also browse registered agent cards by using the {registry} web console at `http://localhost:8888`.

// proc-connecting-claude-desktop-by-using-mcp
[id="connecting-claude-desktop-via-mcp_{context}"]
== Connecting Claude Desktop by using MCP

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can connect Claude Desktop to {registry} by using the MCP server. After you configure Claude Desktop, you can interact with {registry} artifacts, search for schemas, and manage agent cards by using natural language.

.Prerequisites
* {registry} is running (on `localhost:8080`)
* Claude Desktop is installed (macOS or Windows)
+
NOTE: Claude Desktop is officially supported on macOS and Windows. Linux support is available through community builds. For installation details, see the link:https://claude.ai/download[Claude Desktop download page].

.Procedure
. In Claude Desktop, open the MCP configuration file by navigating to *File* > *Settings* > *Developer* > *Edit Config*.
+
. Add the {registry} MCP server to the configuration file:
+
[source,json]
----
{
  "mcpServers": {
    "Apicurio Registry (docker)": {
      "command": "docker",
      "args": [
        "run",
        "-i",
        "--rm",
        "-e", "REGISTRY_URL=<registry-url>",
        "quay.io/apicurio/apicurio-registry-mcp-server:latest"
      ]
    }
  }
}
----
+
Replace `<registry-url>` with the URL of your {registry} instance. For local development with Docker Compose, use `\http://localhost:8080`. For OpenShift deployments, use the route URL of your {registry} instance.
+
. Restart Claude Desktop by selecting *File* > *Exit* and reopening the application.

.Verification
. Verify the connection by asking Claude a question about {registry}, for example: "What groups are present in {registry}?"
+
The MCP server provides tools for working with groups, artifacts, versions, and configuration properties in {registry}.
endif::[]
