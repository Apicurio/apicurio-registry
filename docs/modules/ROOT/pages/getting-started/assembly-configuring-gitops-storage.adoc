[id="assembly-configuring-gitops-storage_{context}"]
= Configuring {registry} with GitOps storage

:_mod-docs-content-type: ASSEMBLY

[role="_abstract"]
Configure {registry} to use a Git repository as the source of registry data. With GitOps storage, you manage schemas and API designs declaratively in Git, and all changes flow through Git commits instead of REST API calls.

== Prerequisites

* You have a way to run the {registry} container image, for example Docker, Podman, or {kubernetes-with-article} cluster.
* You have a Git repository for registry data.

//INCLUDES

[id="gitops-storage-overview_{context}"]
== Overview of GitOps storage

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
GitOps storage is a read-only storage variant that loads registry data from a Git repository. You declare the desired state of the registry in files, and the registry serves that state, so all changes flow through your Git workflow with reviews, history, and rollbacks.

*Architecture*

GitOps storage uses a polling-based architecture with blue-green database switching:

. The registry reads a local Git clone on a mounted volume. The registry never fetches from remote repositories itself; a sync container or an external process updates the clone.
. The registry periodically checks the current commit of the clone. A debounce mechanism absorbs rapid sequences of pushes before a load starts.
. When the commit changes, the registry loads all data into an inactive in-memory database and validates it.
. After a successful load, the active and inactive databases switch atomically. If the load fails, the registry keeps serving the last successfully loaded data.

Data flows in one direction only: from Git to the registry. REST API calls that would modify data are rejected with an HTTP `409` response. The {registry} web console detects the read-only storage, switches to read-only mode, and shows a banner that tells users to update the source Git repository. The registry requires no external database, because data is loaded into in-memory storage from Git.

*Relationship of repositories and registry instances*

One repository can serve multiple registry instances, and one registry instance can aggregate multiple repositories. Each metadata file can declare which registry instances load it, and the registry loads only the data that references its own identifier.

*When to use GitOps storage*

GitOps storage is a good fit when:

* You want schema and API changes to go through pull requests, reviews, and CI checks
* You need a read-only registry where all changes flow through a Git workflow
* You want to avoid operating an external database
* You already manage configuration as code and want registry content to follow the same model

[id="gitops-repository-data-format_{context}"]
== GitOps repository data format

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
A GitOps repository contains metadata files that describe registry content, and plain schema files that hold the content itself. This section describes the file types, their discovery, and their fields.

No fixed directory structure is required. The registry discovers metadata files anywhere in the repository by file name suffix. By default, files ending in `.registry` or `.ar`, combined with the `.yaml`, `.yml`, or `.json` extensions, are treated as metadata files, for example `order-event.registry.yaml`. You can change the suffixes with the `apicurio.polling-storage.file-suffixes` property.

Each metadata file declares its kind and the version of the data format with a `$type` discriminator, for example `$type: artifact-v1`. The current version is `v1`. For the versions that the registry reads, see xref:gitops-data-format-versions_{context}[].

.Metadata file types
[cols="1,3", options="header"]
|===
| Type
| Purpose and main fields

| `registry-v1`
| Registry configuration. Fields: `registryId`, `globalRules` (list of `ruleType` and `config` pairs), `properties`, and `peers` (list of peer registries; see below). The `registryId` value must match the `apicurio.polling-storage.id` property of the registry instance.

| `group-v1`
| An artifact group. Fields: `registryIds` (list), `groupId`, `description`, `labels`, `owner`, `artifactsType`, `rules`, `createdOn`, and `modifiedOn`. Every group that an artifact references must be declared by a `group-v1` file; the registry does not create groups automatically.

| `artifact-v1`
| An artifact with its versions declared inline. Fields: `registryIds`, `groupId`, `artifactId`, `artifactType` (optional), `name`, `description`, `labels`, `owner`, `createdOn`, `modifiedOn`, `rules`, `validatedUpTo`, and `versions`. Each version has `version`, `state`, and `content`, where `content` is a relative path to a schema file. A version can also have `name`, `description`, `labels`, `owner`, `globalId`, `createdOn`, `modifiedOn`, and `contentMetadata`, which is a relative path to a `content-v1` file.

| `content-v1`
| Optional content metadata, for explicit content identifiers and references. Fields: `contentId`, `content` (relative path to the schema file), and `references` (list of entries with `groupId`, `artifactId`, `version`, and `name`).
|===

GitOps storage and KubernetesOps storage share one data format. The KubernetesOps field reference lists the type and description of each field except `createdOn`, `modifiedOn`, and `validatedUpTo`. The rules later in this section describe those three fields.

The following example declares a registry configuration, a group, and an artifact. All three files are required: a load that references an undeclared group fails, and the registry does not become ready.

[source,yaml]
----
$type: registry-v1
registryId: main
globalRules:
  - ruleType: VALIDITY
    config: FULL
----

[source,yaml]
----
$type: group-v1
groupId: my-schemas
----

[source,yaml]
----
$type: artifact-v1
groupId: my-schemas
artifactId: order-event
artifactType: AVRO
versions:
  - version: "1.0.0"
    state: ENABLED
    content: order-event-1.0.0.avsc
----

Content files are plain schema files that metadata files reference by a path relative to the directory of the metadata file.

When `artifactType` is omitted, the registry determines the type in the following order:

. *Unambiguous file extension* — extensions listed in the table below are mapped directly to a single artifact type. An explicit `artifactType` always takes precedence over the extension. A mapped extension is treated like a declared `artifactType`: the content is not checked against it, so an OpenAPI document saved as `api.avsc` is stored as AVRO unless a validity rule rejects it.
. *Content-based detection* — for ambiguous extensions (`.json`, `.yaml`, `.yml`, `.xml`) where multiple artifact types are possible, the registry inspects the file content to determine the type.
. *Error* — if neither the extension nor the content identifies a type, the load fails with an error listing the supported extensions.

All versions of an artifact must share the same type. When `artifactType` is omitted and versions resolve to different types from their extensions, the load fails with an error asking you to set `artifactType` explicitly.

.File extensions and artifact type detection
[cols="1,2,2", options="header"]
|===
| Extension
| Artifact type
| Stored media type

| `.avsc`
| AVRO
| JSON

| `.proto`
| PROTOBUF
| Protobuf

| `.graphql`, `.gql`
| GRAPHQL
| GraphQL

| `.wsdl`
| WSDL
| XML

| `.xsd`
| XSD
| XML

| `.thrift`
| THRIFT
| Thrift

| `.json`, `.yaml`, `.yml`, `.xml`
| _(detected from content)_
| _(matches extension)_

| All other extensions
| _(detected from content)_
| JSON
|===

The following additional rules apply:

* If `registryIds` is omitted or empty on a group or artifact, any registry instance loads it.
* The `createdOn` and `modifiedOn` timestamps on groups, artifacts, and versions are optional. When omitted, the registry uses the Git commit time. Supported formats are ISO 8601, with or without a time zone or as a date only, and Unix milliseconds.
* The optional `validatedUpTo` field on an artifact controls rule validation during a load. When unset, only the latest version is validated, against all preceding versions. When set to a version identifier, versions up to and including that version are not re-validated. When the value matches no version, all versions are validated.
* The optional `peers` list on the registry configuration declares peer registries. Each entry has `peerId` (lowercase letters, digits, `.`, `_`, and `-` only; must be unique and cannot be `local`, which is reserved), `url`, optional `name` and `description`, `enabled` (defaults to `true` when omitted), and an optional `credentialSecretRef`, which is a reference to a credential and never a secret value itself. The full `peers` list is replaced on every load: omitting the key, or setting it to an empty list, removes all previously loaded peers.

[id="gitops-data-format-versions_{context}"]
== GitOps data format versions

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The data format of GitOps and KubernetesOps metadata files is versioned. The version is the suffix of the `$type` value, for example `v1` in `artifact-v1`, and it applies to the whole file.

.Data format versions
[cols="1,1,3", options="header"]
|===
| Version
| Status in {registry} 3.4
| Behavior

| `v1`
| Current
| Read. The export to GitOps format writes this version.

| `v0`
| Deprecated
| Read. A load that contains `v0` files logs one warning with the number of files and an example path. `v1` has the same fields as `v0`, so only the `$type` values differ.
|===

The registry reads at most two versions: the current one and at most one deprecated one. A deprecated version stays readable for at least two minor releases after the release that deprecated it, or until the next major release. A newer version of the data format is introduced only together with the removal of the oldest one.

A file with a version that the registry doesn't read fails the load, and the registry keeps serving the last successfully loaded data:

* A removed version: the error names the version and the version to convert to.
* A newer version, written for a later {registry} release: the error says that the file requires a newer registry.

Within a version, the format changes only by adding optional fields. The registry rejects fields that it doesn't know, so use a new field only when every registry that reads the repository supports it.

*Converting a repository to the current version*

A repository can contain files of both readable versions, so you can convert it in one commit or file by file. To convert from `v0` to `v1`, change the `$type` values, for example:

[source,bash]
----
grep -rlE '^\$type: (registry|group|artifact|content)-v0' --include='*.registry.yaml' . \
  | xargs sed -i -E 's/^\$type: (registry|group|artifact|content)-v0$/$type: \1-v1/'
----

Adjust the file pattern if you changed `apicurio.polling-storage.file-suffixes`, or if your metadata files use the `.yml` or `.json` extension.

Before you convert, check which registry instances read the repository:

* Convert only after every registry instance that reads the repository runs {registry} 3.4 or later. {registry} 3.3 and earlier skip `v1` files, so the converted artifacts disappear from those instances.
* If you convert file by file, convert the registry configuration file first. A registry that can't read it rejects the whole load and keeps serving its last data, instead of serving data without the converted files.
* To roll back to a {registry} release that doesn't read `v1`, revert the conversion commit.


[id="configuring-gitops-storage-single-repository_{context}"]
== Configuring GitOps storage with a single repository

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can configure {registry} to load its data from a single Git repository that is available as a local clone on a mounted volume.

.Prerequisites
* You have a Git repository that contains a registry configuration file (`registry-v1`) and registry content.
* You have a local clone of the repository, or a sync container that maintains one.

.Procedure
. In your repository, verify that a registry configuration file exists and that its `registryId` value matches the registry instance identifier that you configure in the next step. The default identifier is `main`.
. Configure the registry with the following environment variables:
+
[source,bash]
----
APICURIO_STORAGE_KIND=gitops
APICURIO_POLLING_STORAGE_ID=main
----
. Mount the local clone of the repository into the registry container at `/repos/default`. A read-only mount is sufficient for serving content, because the registry does not write to the repository. If you use dry-run validation, mount the workspace writable instead, because the registry writes validation request files under the workspace directory. The mount path is the workspace directory (`apicurio.gitops.workspace`, default `/repos`) combined with the repository directory name (`apicurio.gitops.repo.dir`, default `default`).
+
For example, with Docker Compose:
+
[source,yaml]
----
volumes:
  - ./example-repo:/repos/default:ro
----
. Optional: To read from a branch other than `main`, set the `APICURIO_GITOPS_REPO_BRANCH` environment variable. If the configured branch does not exist in the clone, the registry falls back to `HEAD`.
. Start the registry.
. Verify the synchronization status:
+
[source,bash]
----
$ curl http://localhost:8080/apis/registry/v3/admin/gitops/status
----
+
The registry reports not ready on its readiness probe until the first load succeeds. After the first successful load, it stays ready even if a later load fails, and it keeps serving the last successfully loaded data. With the default poll and debounce settings, expect a new commit to become visible after roughly 20 to 30 seconds.

[id="configuring-gitops-sync-container_{context}"]
== Configuring the GitOps sync container

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
The registry reads only local Git clones and never contacts remote repositories. You can run the GitOps sync container next to the registry to keep a local clone up to date with a remote repository, or to accept pushes directly.

.Prerequisites
* You have configured the registry for GitOps storage.
* For pull mode, you have the URL of a remote Git repository.

.Procedure
. Run the `quay.io/apicurio/apicurio-registry-gitops-sync` container so that it shares a volume with the registry. Mount the shared volume at `/repos` in both containers, read-only in the registry container.
. For pull mode, which is the default, set the remote repository URL:
+
[source,bash]
----
APICURIO_GITOPS_REPO_URL=https://github.com/my-org/my-registry-data.git
----
+
The sync container clones the repository and then updates it every 30 seconds. You can change the interval with the `APICURIO_GITOPS_PULL_INTERVAL` environment variable.
. Optional: For SSH remotes, provide the private key and the known hosts file:
+
[source,bash]
----
APICURIO_GITOPS_PULL_SSH_KEYS=/etc/gitops/ssh/id_ed25519
APICURIO_GITOPS_PULL_SSH_KNOWN_HOSTS=/etc/gitops/ssh/known_hosts
----
. Optional: Adjust the security level with the `APICURIO_GITOPS_SECURITY` environment variable. The default level, `strict`, rejects loose key file permissions, and fails at startup when an SSH remote is configured without any SSH keys. When you provide keys without a known hosts file, the container accepts a host key on first connection. The `dev` level relaxes host key checking for development. Plaintext `http://` remote URLs are rejected at both levels.
. Optional: To accept Git pushes instead of pulling from a remote, set `APICURIO_GITOPS_MODE=push`. The sync container runs a restricted SSH server for the `git` user on port `2222`. Configure the authorized client keys and the host key:
+
[source,bash]
----
APICURIO_GITOPS_PUSH_SSH_AUTHORIZED_KEYS=/etc/gitops/ssh/authorized_keys
APICURIO_GITOPS_PUSH_SSH_HOST_KEY=/etc/gitops/ssh/host_key
----
+
Clients then push to the container directly:
+
[source,bash]
----
$ git push ssh://git@registry-host:2222/repos/default
----
+
[NOTE]
====
In push mode, any authorized push user can access all Git repositories on the shared volume.
====
. Optional: When you configure multiple repositories, set the mode per repository with `APICURIO_GITOPS_REPOS_N_MODE`, which overrides the global `APICURIO_GITOPS_MODE` setting.


[id="configuring-gitops-multiple-repositories_{context}"]
== Configuring multiple GitOps repositories

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can configure one registry instance to aggregate data from multiple Git repositories, for example one repository per team. The registry detects conflicting artifact definitions across repositories and rejects them.

.Prerequisites
* You have configured the registry for GitOps storage.

.Procedure
. Configure the repositories on the registry with indexed environment variables. Indexes must start at 0 and be consecutive:
+
[source,bash]
----
APICURIO_GITOPS_REPOS_0_DIR=platform
APICURIO_GITOPS_REPOS_1_DIR=fulfillment
APICURIO_GITOPS_REPOS_1_BRANCH=fulfillment
----
+
Optional: Assign an identifier for status reporting with `APICURIO_GITOPS_REPOS_N_ID`. The default identifier is the directory name.
+
[NOTE]
====
Do not combine the single-repository variables (`APICURIO_GITOPS_REPO_DIR`, `APICURIO_GITOPS_REPO_BRANCH`) with indexed variables. The registry rejects mixed configuration, index gaps, duplicate repository identifiers, and duplicate directory and branch combinations at startup.
====
. If you use the sync container, configure the remote URL for each repository with `APICURIO_GITOPS_REPOS_N_URL`, and optionally per-repository SSH keys with `APICURIO_GITOPS_REPOS_N_SSH_KEYS`.
. Ensure that each artifact is defined in exactly one repository. If the same `groupId` and `artifactId` combination is defined in more than one repository, the registry reports all conflicts and rejects the entire load.
. Verify the aggregated state:
+
[source,bash]
----
$ curl http://localhost:8080/apis/registry/v3/admin/gitops/status
----
+
The `sources` field maps each repository identifier to the currently loaded commit.
+
By default, the registry labels each loaded group and artifact with the identifier of its source repository, using the `system:source` label key. You can change or disable this with the `apicurio.polling-storage.source-label-key` property.


[id="validating-gitops-changes_{context}"]
== Validating repository changes before merging

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can validate a Git reference, such as a pull request branch, against the full registry validation pipeline without affecting the data that the registry serves. This enables CI checks that reject invalid schema changes before they merge.

.Prerequisites
* Validation is enabled on the registry (`apicurio.gitops.validate.enabled`, default `true`). When validation is disabled, the validation endpoints return an HTTP `503` response.
* The sync container is running, because it fetches the reference to validate.
* The workspace volume is writable by the registry, because the registry writes validation request files under the workspace directory.

.Procedure
. Create a validation task for the reference:
+
[source,bash]
----
$ curl -X POST -H "Content-Type: application/json" \
  -d '{"type": "pull", "repoId": "platform", "ref": "refs/pull/42/head"}' \
  http://localhost:8080/apis/registry/v3/admin/gitops/validate
----
+
The `repoId` value must be the identifier of a configured repository. The registry rejects a missing or unconfigured value with an HTTP `400` response that lists the configured identifiers. The value must also match the repository directory name, because the sync container resolves `repoId` by directory name. The registry accepts an identifier that you assign with `APICURIO_GITOPS_REPOS_N_ID`, but the created task then fails with an `Unknown repoId` error. The response contains a `taskId`.
. Poll the task until it completes:
+
[source,bash,subs="+quotes"]
----
$ curl http://localhost:8080/apis/registry/v3/admin/gitops/validate/_TASK_ID_
----
+
The task moves through the states `pending`, `submitted`, `fetching`, and `validating` to `completed` or `failed`.
. Check the outcome of a completed task in the `result` field, which is `success` or `failure`. A successful task reports group, artifact, and version counts. A failed validation reports structured errors with a `detail` message and, where available, the `source` repository and the `context` file path.
. Optional: Delete a task that you no longer need:
+
[source,bash,subs="+quotes"]
----
$ curl -X DELETE http://localhost:8080/apis/registry/v3/admin/gitops/validate/_TASK_ID_
----
+
Tasks are removed automatically after a time to live, which is one hour by default. To limit disk usage, at most five tasks hold disk resources at the same time by default; further requests are queued.

[id="gitops-storage-configuration-properties_{context}"]
== GitOps storage configuration properties

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You configure GitOps storage with {registry} configuration properties for the registry and with environment variables for the GitOps sync container.

.Registry configuration properties
[cols="3,2,3", options="header"]
|===
| Property (environment variable)
| Default
| Description

| `apicurio.storage.kind` (`APICURIO_STORAGE_KIND`)
| `sql`
| Set to `gitops` to enable GitOps storage.

| `apicurio.gitops.workspace` (`APICURIO_GITOPS_WORKSPACE`)
| `/repos`
| Base directory where Git repositories are mounted. Repository directories are resolved relative to this path.

| `apicurio.gitops.repo.dir` (`APICURIO_GITOPS_REPO_DIR`)
| `default`
| Directory name of the Git repository, relative to the workspace. Single-repository configuration.

| `apicurio.gitops.repo.branch` (`APICURIO_GITOPS_REPO_BRANCH`)
| `main`
| Branch to read from. Single-repository configuration.

| `apicurio.gitops.repos.N.dir` (`APICURIO_GITOPS_REPOS_N_DIR`)
| No default
| Directory name for repository `N`. Multi-repository configuration; indexes must start at 0 and be consecutive.

| `apicurio.gitops.repos.N.branch` (`APICURIO_GITOPS_REPOS_N_BRANCH`)
| `main`
| Branch for repository `N`.

| `apicurio.gitops.repos.N.id` (`APICURIO_GITOPS_REPOS_N_ID`)
| Directory name
| Identifier for repository `N`, used in status reporting and source labels.

| `apicurio.gitops.validate.enabled` (`APICURIO_GITOPS_VALIDATE_ENABLED`)
| `true`
| Enable the dry-run validation endpoints. When disabled, the validation endpoints return an HTTP `503` response.

| `apicurio.gitops.validate.task.ttl.seconds` (`APICURIO_GITOPS_VALIDATE_TASK_TTL_SECONDS`)
| `3600`
| Time to live for validation tasks. Tasks are removed automatically after this period.

| `apicurio.gitops.validate.max-tasks` (`APICURIO_GITOPS_VALIDATE_MAX_TASKS`)
| `5`
| Maximum number of validation tasks that hold disk resources at the same time. Further requests are queued.

| `apicurio.polling-storage.id` (`APICURIO_POLLING_STORAGE_ID`)
| `main`
| Identifier of this registry instance. Only data referencing this identifier is loaded. Must match the `registryId` value in the registry configuration file.

| `apicurio.polling-storage.deterministic-ids-enabled` (`APICURIO_POLLING_STORAGE_DETERMINISTIC_IDS_ENABLED`)
| `true`
| Generate content and global identifiers deterministically from content hashes and coordinates when they are not specified in the data.

| `apicurio.polling-storage.poll-period` (`APICURIO_POLLING_STORAGE_POLL_PERIOD`)
| `PT10S`
| Minimum period between checks of the data source.

| `apicurio.polling-storage.debounce.quiet-period` (`APICURIO_POLLING_STORAGE_DEBOUNCE_QUIET_PERIOD`)
| `PT3S`
| Wait until no new changes arrive for this duration before loading. `PT0S` disables debouncing.

| `apicurio.polling-storage.debounce.max-wait-period` (`APICURIO_POLLING_STORAGE_DEBOUNCE_MAX_WAIT_PERIOD`)
| `PT90S`
| Maximum time to wait for changes to settle before a load is forced. `PT0S` means no maximum.

| `apicurio.polling-storage.file-suffixes` (`APICURIO_POLLING_STORAGE_FILE_SUFFIXES`)
| `registry,ar`
| Suffixes that identify metadata files, combined with the `.yaml`, `.yml`, and `.json` extensions.

| `apicurio.polling-storage.require-registry-config` (`APICURIO_POLLING_STORAGE_REQUIRE_REGISTRY_CONFIG`)
| `true`
| Reject a load when no registry configuration file matches the configured registry identifier. This guards against accidental data loss from force pushes or empty branches.

| `apicurio.polling-storage.source-label-key` (`APICURIO_POLLING_STORAGE_SOURCE_LABEL_KEY`)
| `system:source`
| Label key used to tag loaded groups and artifacts with the identifier of their source repository. An empty value disables source labels.

| `APICURIO_GITOPS_VALIDATE_FETCH_TIMEOUT_SECONDS`
| `120`
| Timeout for fetching a Git reference during validation.
|===


[id="gitops-management-api_{context}"]
== GitOps management API

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The registry provides administrative REST endpoints for GitOps storage under the `/apis/registry/v3/admin/gitops` path. The endpoints return an HTTP `409` response when a different storage variant is active.

.GitOps management endpoints
[cols="3,1,3", options="header"]
|===
| Path
| Method
| Description

| `/admin/gitops/status`
| `GET`
| Return the synchronization status.

| `/admin/gitops/sync`
| `POST`
| Trigger an immediate synchronization. Returns an HTTP `204` response.

| `/admin/gitops/validate`
| `POST`
| Create a dry-run validation task for a Git reference.

| `/admin/gitops/validate`
| `GET`
| List validation tasks.

| `/admin/gitops/validate/\{taskId}`
| `GET`
| Return the status and results of a validation task.

| `/admin/gitops/validate/\{taskId}`
| `DELETE`
| Delete a validation task and clean up its files.
|===

The status response contains the following fields:

.GitOps status fields
[cols="1,3", options="header"]
|===
| Field
| Description

| `syncState`
| Current state: `INITIALIZING`, `IDLE`, `LOADING`, `SWITCHING`, or `ERROR`. The state is `ERROR` after a failed load or a failed poll of the data source, for example when the registry cannot read the local Git clone. After a later successful poll, the state returns to `IDLE` only if no load errors remain. Otherwise the state stays `ERROR` and keeps reporting the load errors.

| `lastSuccessfulSync`
| Timestamp of the last successful load.

| `lastSyncAttempt`
| Timestamp of the last poll attempt, successful or not.

| `groupCount`, `artifactCount`, `versionCount`
| Counts of the currently loaded data.

| `errors`
| Structured errors from the last failed load and the last failed poll. Each load error has a `detail` message and, where available, a `source` repository identifier and a `context` file path. A poll error has only a `detail` message that starts with `Poll failed:`. Load errors stay listed through later successful polls until a load succeeds.

| `sources`
| Map of repository identifiers to the abbreviated commit currently loaded from each repository.
|===

If a load fails because of a data error, for example malformed metadata, a missing content file, or a rule violation, the registry does not retry the same commit. Push a new commit that fixes the problem to trigger a fresh load. The registry reports a transient error, such as a failed poll of the data source, as `ERROR` in the status with an `errors` entry, and retries on the next poll.
