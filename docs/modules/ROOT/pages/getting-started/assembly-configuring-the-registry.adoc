[id="configuring-file-based-secrets_{context}"]
== Loading configuration values from files

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can load a {registry} configuration value from a file, such as a mounted secret, to keep the value out of the deployment's environment variables.

.Prerequisites
* You can update and restart the {registry} deployment.
* The file contains the required configuration value and is readable by the {registry} process.

.Procedure
. Mount the file in the {registry} container, for example, at `/run/secrets/db_password`.
Use file permissions that restrict access to the processes that need the value.
. Set the environment variable for the configuration property with an additional `_FILE` suffix:
+
[source,properties]
----
APICURIO_DATASOURCE_PASSWORD_FILE=/run/secrets/db_password
----
+
Alternatively, configure the property with a `.file` suffix in the server configuration:
+
[source,properties]
----
apicurio.datasource.password.file=/run/secrets/db_password
----
+
The file value takes precedence over a directly configured value for `apicurio.datasource.password`.
{registry} removes leading and trailing whitespace from the file contents.
This mechanism applies to configuration properties resolved by the server, including properties other than passwords.
. Restart the deployment to load the value.
+
{registry} caches the value after reading the file.
Restart the deployment after changing the file or its configured path.

.Verification
* Check the server log for a message that confirms the file was loaded for `apicurio.datasource.password`.
The message identifies the property without displaying the secret value.

.Troubleshooting
* If the server reports that the file is missing or unreadable, check the mounted path and file permissions.
A configured file that cannot be read causes configuration resolution to fail; the server does not fall back to the directly configured value.

[id="configuring-registry-http-caching_{context}"]
== Enabling HTTP caching for artifact content

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can enable HTTP cache headers for supported v3 content endpoints so that a reverse proxy can serve repeated requests from its cache.

.Prerequisites
* You can update and restart the {registry} deployment.
* A reverse proxy cache is available in front of {registry}.
* An artifact version is available for testing content requests.

.Procedure
. Enable HTTP caching in the server configuration:
+
[source,properties]
----
apicurio.http-caching.enabled=true
----
+
The equivalent environment variable is `APICURIO_HTTP_CACHING_ENABLED=true`.
. Set expiration times that match how long your clients can tolerate stale content.
For example, the following configuration caches highly cacheable content for one hour and uses shorter periods for content that can change:
+
[source,properties]
----
apicurio.http-caching.high-cacheability.max-age-seconds=3600
apicurio.http-caching.moderate-cacheability.max-age-seconds=30
apicurio.http-caching.low-cacheability.max-age-seconds=10
----
. Configure the reverse proxy to use `Surrogate-Control`, `ETag`, and `Vary` response headers.
+
The default `Vary` headers are `Accept`, `Accept-Encoding`, and `Authorization`.
Configure the proxy to keep responses for different credentials separate and to enforce your access policy when serving cached responses.
{registry} does not invalidate proxy entries when content access or version state changes.
. Restart the {registry} deployment to apply the configuration.

.Verification
* Request an existing artifact version through the proxy and inspect its response headers:
+
[source,bash]
----
curl --include \
  "https://registry.example.com/apis/registry/v3/groups/my-group/artifacts/my-schema/versions/1.0.0/content"
----
+
Replace the URL and artifact coordinates with values from your deployment, and supply authentication if required.
For a successful cacheable response, check for `ETag`, `Surrogate-Control`, and `Vary` headers.
With the default diagnostic headers enabled, `X-Cache-Cacheability` identifies the selected cacheability level.
Use the proxy's cache-hit statistics or logs to verify that repeated requests use its cache.

[id="registry-http-cache-behavior_{context}"]
== HTTP cache behavior

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} assigns a cacheability level to supported v3 content responses based on the request, version state, and reference handling.

.HTTP cacheability levels
[cols="1,1,3",options="header"]
|===
|Level
|Default expiration
|Typical behavior

|`HIGH`
|864,000 seconds (10 days)
|Content identified by an immutable identifier or a specific immutable version can use the longest expiration.

|`MODERATE`
|30 seconds
|Requests that use version expressions, such as a branch, or retrieve mutable draft content need a shorter expiration.

|`LOW`
|10 seconds
|Responses whose dependencies can change or whose content identity cannot be determined use the shortest expiration.

|`NONE`
|Not applicable
|The response does not receive a `Surrogate-Control` caching policy.
|===

Activation::
HTTP caching is disabled by default.
Set `apicurio.http-caching.enabled=true` and keep at least one cacheability expiration greater than zero to activate it.
Setting an individual expiration to zero or a negative value suppresses the caching policy for that level.

Scope::
Cache headers apply to supported v3 content operations, including content retrieved by global ID and by group, artifact, and version.
The server evaluates the request and can reduce its cacheability because of reference handling or version mutability.

Response headers::
`Surrogate-Control` specifies the proxy expiration policy.
`ETag` identifies the response representation, and `Vary` identifies request headers that distinguish cached representations.
These headers do not enable browser caching; the API's `Cache-Control` policy remains `no-cache, no-store`.

Expiration and invalidation::
Cached responses can remain available until the proxy refreshes or expires them.
Automatic invalidation of reverse proxy entries is not available.
Choose shorter expiration times when content changes or access changes must reach clients sooner.

== Configuring the {registry} web console

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can set optional environment variables to configure the {registry} web console specifically for your deployment environment or to customize its behavior.

.Prerequisites
* You have already installed {registry}.

.Procedure
. Set the `REGISTRY_API_URL` environment variable to override the default REST API URL. For example, `\https://registry-api.my-domain.com/apis/registry/v3`.
+
Typically the {operator} automatically configures the UI component with the REST API v3 URL. Override this value only if your deployment requires a custom URL.
. Set the `REGISTRY_FEATURE_READ_ONLY` environment variable to `true` to enable read-only mode. The default value is `false`.
+
In read-only mode, you cannot make changes to registered artifacts. For example, the following actions are unavailable:
+
* Creating a group
* Creating an artifact
* Uploading a new artifact version
* Updating artifact metadata
* Deleting an artifact

[id="configuring-registry-observability_{context}"]
== {registry} observability with OpenTelemetry

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can configure {registry} to export telemetry data using OpenTelemetry (OTel) for comprehensive observability. This includes distributed tracing, metrics export by using the OTLP protocol, and log correlation with trace context.

{registry} is built with OpenTelemetry support and all telemetry signals (traces, metrics, logs) are enabled at build time. However, the OpenTelemetry SDK is disabled by default at runtime. When enabled, {registry} exports telemetry data to an OpenTelemetry-compatible collector such as Jaeger, Grafana Tempo, or the OpenTelemetry Collector.

IMPORTANT: The individual signal properties (`QUARKUS_OTEL_TRACES_ENABLED`, `QUARKUS_OTEL_METRICS_ENABLED`, `QUARKUS_OTEL_LOGS_ENABLED`) are build-time properties and cannot be changed at runtime. All signals are already enabled in the {registry} build. Use `QUARKUS_OTEL_SDK_DISABLED=false` to enable telemetry at runtime.

NOTE: Before you configure OpenTelemetry, ensure that you have installed {registry} and have an OpenTelemetry-compatible backend available, for example, Jaeger, Grafana Tempo, or OpenTelemetry Collector.

To enable OpenTelemetry observability, configure the following environment variables:

.Environment variables for enabling OpenTelemetry
[.table-expandable,width="100%",cols="4,6",options="header"]
|===
|Environment variable
|Description
|`QUARKUS_OTEL_SDK_DISABLED`
|Set to `false` to enable the OpenTelemetry SDK and all telemetry signals. Default is `true` (disabled).
|`QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT`
|The endpoint URL of your OpenTelemetry collector. For example, `http://jaeger:4317` for gRPC or `http://jaeger:4318` for HTTP.
|===

.Example: Enabling OpenTelemetry with Jaeger
[source,yaml]
----
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT: "http://jaeger:4317"
----

In production environments, configure trace sampling to reduce processing overhead and control the volume of trace data:

.Environment variables for trace sampling
[.table-expandable,width="100%",cols="4,6",options="header"]
|===
|Environment variable
|Description
|`QUARKUS_OTEL_TRACES_SAMPLER`
|The sampling strategy. Use `parentbased_traceidratio` for production.
|`QUARKUS_OTEL_TRACES_SAMPLER_ARG`
|The sampling ratio (0.0 to 1.0). A value of `0.1` samples 10% of traces.
|===

.Example: Production sampling configuration (10% of traces)
[source,yaml]
----
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT: "http://otel-collector:4317"
  QUARKUS_OTEL_TRACES_SAMPLER: "parentbased_traceidratio"
  QUARKUS_OTEL_TRACES_SAMPLER_ARG: "0.1"
----

When you use JSON logging format, {registry} automatically includes trace context (trace ID and span ID) in log entries. You can then correlate logs and traces.

.Example: Enabling structured logging with trace context
[source,yaml]
----
environment:
  QUARKUS_OTEL_TRACES_ENABLED: "true"
  QUARKUS_LOG_CONSOLE_JSON: "true"
----


// con-otel-features
[id="otel-features_{context}"]
== OpenTelemetry features in {registry}

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
When OpenTelemetry is enabled, {registry} provides several observability features that are fully compatible with your existing monitoring setup.

* *Distributed tracing*: All REST API requests are automatically traced with spans containing request details, path parameters, and Apicurio-specific attributes such as `groupId`, `artifactId`, and `version`.

* *Storage layer tracing*: All storage operations create child spans. You can trace the complete request flow from REST API to database.

* *Kafka tracing*: When using KafkaSQL storage, Kafka operations are automatically traced with context propagation.

* *Custom metrics*: OpenTelemetry metrics for artifact operations, schema validations, and search requests are exported alongside existing Prometheus metrics.

* *Log correlation*: When JSON logging is enabled, trace context is automatically injected into log entries for correlation.

Existing monitoring endpoints continue to function:

* The Prometheus metrics endpoint is available at `/metrics` on the management port (default 9000).
* Health check endpoints (`/health/ready`, `/health/live`) are served on the management port (default 9000).
* All existing Micrometer-based metrics continue to function.

|+6% (+0.16ms)

*Key findings:*

* Average overhead is approximately 4-6% in throughput with 100% trace sampling.

[id="configuring-dynamic-log-level_{context}"]
== Changing the {registry} log level at runtime

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can change the log level of a running {registry} instance without restarting it by setting the dynamic `apicurio.log.level` configuration property. The setting applies to the {registry} loggers in the `io.apicurio` category.

.Prerequisites
* You have administrator access to the {registry} instance.

.Procedure
. Set the log level with the admin configuration REST endpoint. Valid values are `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `OFF`, and `ALL`. The default value is `INFO`:
+
[source,bash]
----
$ curl -X PUT -H "Content-Type: application/json" \
  -d '{"value": "DEBUG"}' \
  http://localhost:8080/apis/registry/v3/admin/config/properties/apicurio.log.level
----
+
Alternatively, use the CLI:
+
[source,bash]
----
$ acr server-config set apicurio.log.level DEBUG
----
+
The registry applies the change within a few seconds. The value is stored in the registry storage, so it persists across restarts.
. To revert to the original log level, remove the dynamic property. The registry restores the log level that was active at startup:
+
[source,bash]
----
$ acr server-config reset apicurio.log.level
----

== REST request metrics distribution configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The following properties control how {registry} publishes distribution statistics for its REST request timer metrics. Change the distribution type when your monitoring system computes percentiles poorly from histogram buckets, for example, Datadog.

.REST metrics distribution properties
[.table-expandable,width="100%",cols="4,3,4",options="header"]
|===
|Property
|Default
|Description

|`apicurio.metrics.rest.distribution.type`
|`histogram`
|Distribution type for REST request timers. The `histogram` type publishes bucket histograms with service level objective boundaries, and the `summary` type publishes pre-computed percentiles only. An invalid value prevents the application from starting.

|`apicurio.metrics.rest.distribution.percentiles`
|`0.5,0.95,0.99,0.9995`
|Percentiles to pre-compute. Each value must be between 0.0 and 1.0.

|`apicurio.metrics.rest.distribution.slo`
|`0.1,0.25,0.5,1.0,2.0,5.0,10.0`
|Service level objective boundaries in seconds for the histogram buckets. Only used when the distribution type is `histogram`.
|===

[id="configuring-liveness-readiness-probes_{context}"]
== Configuring {registry} health checks on OpenShift

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Health check endpoints are served on the management interface (port 9000 by default), separate from the main application port (8080). Configure liveness and readiness probes to target port 9000.

You can configure optional environment variables for liveness and readiness probes to monitor the health of the {registry} server on OpenShift:

* _Liveness probes_ test if the application can make progress. If the application cannot make progress, OpenShift automatically restarts the failing Pod.

* _Readiness probes_ test if the application is ready to process requests. If the application is not ready, it can become overwhelmed by requests, and OpenShift stops sending requests for the time that the probe fails. If other Pods are OK, they continue to receive requests.

IMPORTANT: The default values of the liveness and readiness environment variables are designed for most cases. Change these values only if required by your environment. Any changes to the defaults depend on your hardware, network, and amount of data stored. Keep these values as low as possible to avoid unnecessary processing overhead.

.Prerequisites
* You must have an OpenShift cluster with cluster administrator access.
* You must have already installed {registry} on OpenShift.
* You must have already installed and configured your chosen {registry} storage in either {kafka-streams} or PostgreSQL.

.Procedure

. In the OpenShift Container Platform web console, log in using an account with cluster administrator privileges.

. Click *Installed Operators* > *{registry}*.

. On the *ApicurioRegistry* tab, click the Operator custom resource for your deployment, for example, *example-apicurioregistry*.

. In the main overview page, find the *Deployment Name* section and the corresponding `DeploymentConfig` name for your {registry} deployment, for example, *example-apicurioregistry*.

. In the left navigation menu, click *Workloads* > *Deployment Configs*, and select your `DeploymentConfig` name.

. Click the *Environment* tab, and enter your environment variables in the *Single values env* section, for example:
** *NAME*: `LIVENESS_STATUS_RESET`
** *VALUE*: `350`

. Click *Save* at the bottom.
+
Alternatively, you can complete these steps by using the OpenShift `oc` command. For more details, see the link:https://docs.openshift.com/container-platform/{registry-ocp-version}/cli_reference/openshift_cli/getting-started-cli.html[OpenShift CLI documentation].

[id="registry-liveness-env-vars_{context}"]
== Environment variables for {registry} health checks

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can use the following environment variables to configure {registry} health checks on OpenShift. These variables control liveness and readiness probes that monitor the health of the {registry} server.

IMPORTANT: The following environment variables are provided for reference only. The default values are designed for most cases. Change these values only if required by your environment. Any changes to the defaults depend on your hardware, network, and amount of data stored. Keep these values as low as possible to avoid unnecessary processing overhead.

.Environment variables for {registry} liveness probes
[.table-expandable,width="100%",cols="5,5,2,5",options="header"]
|===
|Name
|Description
|Type
|Default
|`LIVENESS_ERROR_THRESHOLD`
|Number of liveness issues or errors that can occur before the liveness probe fails.
|Integer
|`1`
|`LIVENESS_COUNTER_RESET`
|Period in which the threshold number of errors must occur. For example, if this value is 60 and the threshold is 1, the check fails after two errors occur in 1 minute.
|Seconds
|`60`
|`LIVENESS_STATUS_RESET`
|Number of seconds that must elapse without any more errors for the liveness probe to reset to OK status.
|Seconds
|`300`
|`LIVENESS_ERRORS_IGNORED`
|Comma-separated list of ignored liveness exceptions.
|String
|`io.grpc.StatusRuntimeException,org.apache.kafka.streams.errors.InvalidStateStoreException`
|===

NOTE: Because OpenShift automatically restarts a Pod that fails a liveness check, the liveness settings, unlike readiness settings, do not directly affect behavior of {registry} on OpenShift.

.Environment variables for {registry} readiness probes
[.table-expandable,width="100%",cols="4,5,2,2",options="header"]
|===
|Name
|Description
|Type
|Default
|`READINESS_ERROR_THRESHOLD`
|Number of readiness issues or errors that can occur before the readiness probe fails.
|Integer
|`1`
|`READINESS_COUNTER_RESET`
|Period in which the threshold number of errors must occur. For example, if this value is 60 and the threshold is 1, the check fails after two errors occur in 1 minute.
|Seconds
|`60`
|`READINESS_STATUS_RESET`
|Number of seconds that must elapse without any more errors for the readiness probe to reset to OK status. This value determines how long the Pod remains not ready before it returns to normal operation.
|Seconds
|`300`
|`READINESS_TIMEOUT`
a|Readiness tracks the timeout of two operations:

* How long it takes for storage requests to complete
* How long it takes for HTTP REST API requests to return a response

If either operation exceeds the configured timeout, {registry} reports a readiness issue or error. This value controls the timeouts for both operations.
|Seconds
|`5`
|===
