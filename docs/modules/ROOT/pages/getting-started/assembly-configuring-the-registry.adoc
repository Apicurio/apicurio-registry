:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can set optional environment variables to configure the {registry} web console specifically for your deployment environment or to customize its behavior.

.Prerequisites
* You have already installed {registry}.

.Procedure
. Set the `REGISTRY_API_URL` environment variable to override the default REST API URL. For example, `\https://registry-api.my-domain.com/apis/registry/v3`.
+
Typically the {operator} automatically configures the UI component with the REST API v3 URL. Override this value only if your deployment requires a custom URL.

+

* Creating an artifact
* Uploading a new artifact version
* Updating artifact metadata
* Deleting an artifact

== {registry} observability with OpenTelemetry

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can configure {registry} to export telemetry data using OpenTelemetry (OTel) for comprehensive observability. This includes distributed tracing, metrics export by using the OTLP protocol, and log correlation with trace context.

{registry} is built with OpenTelemetry support and all telemetry signals (traces, metrics, logs) are enabled at build time. However, the OpenTelemetry SDK is disabled by default at runtime. When enabled, {registry} exports telemetry data to an OpenTelemetry-compatible collector such as Jaeger, Grafana Tempo, or the OpenTelemetry Collector.

IMPORTANT: The individual signal properties (`QUARKUS_OTEL_TRACES_ENABLED`, `QUARKUS_OTEL_METRICS_ENABLED`, `QUARKUS_OTEL_LOGS_ENABLED`) are build-time properties and cannot be changed at runtime. All signals are already enabled in the {registry} build. Use `QUARKUS_OTEL_SDK_DISABLED=false` to enable telemetry at runtime.

NOTE: Before you configure OpenTelemetry, ensure that you have installed {registry} and have an OpenTelemetry-compatible backend available, for example, Jaeger, Grafana Tempo, or OpenTelemetry Collector.

To enable OpenTelemetry observability, configure the following environment variables:

.Environment variables for enabling OpenTelemetry
[.table-expandable,width="100%",cols="4,6",options="header"]
|===
|Environment variable
|Description
|`QUARKUS_OTEL_SDK_DISABLED`
|Set to `false` to enable the OpenTelemetry SDK and all telemetry signals. Default is `true` (disabled).
|`QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT`
|The endpoint URL of your OpenTelemetry collector. For example, `http://jaeger:4317` for gRPC or `http://jaeger:4318` for HTTP.
|===

.Example: Enabling OpenTelemetry with Jaeger
[source,yaml]
----
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT: "http://jaeger:4317"
----

In production environments, configure trace sampling to reduce processing overhead and control the volume of trace data:

.Environment variables for trace sampling
[.table-expandable,width="100%",cols="4,6",options="header"]
|===
|Environment variable
|Description
|`QUARKUS_OTEL_TRACES_SAMPLER`
|The sampling strategy. Use `parentbased_traceidratio` for production.
|`QUARKUS_OTEL_TRACES_SAMPLER_ARG`
|The sampling ratio (0.0 to 1.0). A value of `0.1` samples 10% of traces.
|===

.Example: Production sampling configuration (10% of traces)
[source,yaml]
----
environment:
  QUARKUS_OTEL_SDK_DISABLED: "false"
  QUARKUS_OTEL_EXPORTER_OTLP_ENDPOINT: "http://otel-collector:4317"
  QUARKUS_OTEL_TRACES_SAMPLER: "parentbased_traceidratio"
  QUARKUS_OTEL_TRACES_SAMPLER_ARG: "0.1"
----

When you use JSON logging format, {registry} automatically includes trace context (trace ID and span ID) in log entries. You can then correlate logs and traces.

.Example: Enabling structured logging with trace context
[source,yaml]
----
environment:
  QUARKUS_OTEL_TRACES_ENABLED: "true"
  QUARKUS_LOG_CONSOLE_JSON: "true"
----

== OpenTelemetry features in {registry}

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
When OpenTelemetry is enabled, {registry} provides several observability features that are fully compatible with your existing monitoring setup.

* *Distributed tracing*: All REST API requests are automatically traced with spans containing request details, path parameters, and Apicurio-specific attributes such as `groupId`, `artifactId`, and `version`.

* *Storage layer tracing*: All storage operations create child spans. You can trace the complete request flow from REST API to database.

* *Kafka tracing*: When using KafkaSQL storage, Kafka operations are automatically traced with context propagation.

* *Custom metrics*: OpenTelemetry metrics for artifact operations, schema validations, and search requests are exported alongside existing Prometheus metrics.

* *Log correlation*: When JSON logging is enabled, trace context is automatically injected into log entries for correlation.

Existing monitoring endpoints continue to function:

* The Prometheus metrics endpoint is available at `/metrics` on the management port (default 9000).
* Health check endpoints (`/health/ready`, `/health/live`) are served on the management port (default 9000).
* All existing Micrometer-based metrics continue to function.

== Changing the {registry} log level at runtime

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can change the log level of a running {registry} instance without restarting it by setting the dynamic `apicurio.log.level` configuration property. The setting applies to the {registry} loggers in the `io.apicurio` category.

.Prerequisites
* You have administrator access to the {registry} instance.

.Procedure
. Set the log level with the admin configuration REST endpoint. Valid values are `TRACE`, `DEBUG`, `INFO`, `WARN`, `ERROR`, `OFF`, and `ALL`. The default value is `INFO`:
+
[source,bash]
----
$ curl -X PUT -H "Content-Type: application/json" \
  -d '{"value": "DEBUG"}' \
  http://localhost:8080/apis/registry/v3/admin/config/properties/apicurio.log.level
----
+
Alternatively, use the CLI:
+
[source,bash]
----
$ acr server-config set apicurio.log.level DEBUG
----
+
The registry applies the change within a few seconds. The value is stored in the registry storage, so it persists across restarts.
. To revert to the original log level, remove the dynamic property. The registry restores the log level that was active at startup:
+
[source,bash]
----
$ acr server-config reset apicurio.log.level
----

[id="registry-storage-content-cache_{context}"]
== Storage content cache

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
{registry} keeps an in-memory, byte-weighted cache of immutable artifact content in front of the storage layer. The cache reduces storage round trips for reads that look up content by content ID or content hash, such as the Confluent-compatible schema lookup by ID that Kafka clients use.

The cache is enabled by default and applies to every storage variant because {registry} adds it as a storage decorator. The storage content cache is separate from HTTP caching, which sets response headers so that a reverse proxy or CDN can cache REST responses outside {registry}. The content cache works inside the {registry} process and also serves requests that HTTP caching does not cover, such as Confluent-compatible requests, which {registry} returns without cache headers.

*Cached reads*

A cache entry holds the content bytes, the artifact type, and the parsed references for one piece of content. {registry} caches only reads whose result depends solely on an immutable content identifier:

* Content by content ID, for example, `GET /apis/registry/v3/ids/contentIds/\{contentId}` and its `/references` variant.
* Content by SHA-256 content hash, for example, `GET /apis/registry/v3/ids/contentHashes/\{contentHash}` and its `/references` variant.
* Content and artifact type by content ID, which serves the Confluent-compatible `GET /apis/ccompat/v7/schemas/ids/\{id}` and `GET /apis/ccompat/v7/schemas/ids/\{id}/schema` requests when legacy ID mode is disabled, which is the default.

{registry} does not cache reads that resolve content through a group, artifact, and version coordinate, or through a global ID, because that mapping can change over time.

Content bytes never change for a given content ID or content hash, so the content-by-ID and content-by-hash entries have no expiry. {registry} evicts them only when a cache exceeds its size limit. The content-and-type entry also depends on whether an artifact version still references the content, so it has a bounded staleness window.

{registry} coalesces concurrent misses for the same key into a single storage call. It never caches failed lookups, so a request for content that does not exist always reaches storage.

*Bounded staleness window*

{registry} returns `404 Not Found` for a content-and-type lookup when the content is orphaned, that is, when no artifact version references it. Orphan status can change after {registry} caches the entry, most commonly when you delete the last version that references the content. To keep the hot path fast, {registry} accepts a short window during which a cached content-and-type entry can be stale:

* Each content-and-type entry expires `apicurio.storage.content-cache.hot-path.ttl-seconds` after {registry} writes it. The default is 30 seconds.
* When you delete a single artifact version, {registry} resolves the content ID of that version before the delete and invalidates the matching content-and-type entry after the delete. If the lookup fails, the delete still completes and the entry expires through the TTL instead.
* Other operations that can orphan content, such as deleting a whole artifact or group, importing data, or restoring a snapshot, do not invalidate entries. The TTL bounds the staleness for these cases.

As a result, a Confluent-compatible schema lookup by ID can still succeed for up to the TTL after a bulk operation removes the last referencing version. Set the TTL to `0` to disable the content-and-type cache and remove the window at the cost of a storage query on every lookup.

The scheduled orphaned content cleanup job, configured by `apicurio.storage.orphan-cleanup.every`, later removes orphaned content rows from storage. Content-by-ID and content-by-hash entries never expire, so a cached copy of removed content remains readable by content ID or content hash until {registry} evicts it or restarts.

*Memory sizing*

`apicurio.storage.content-cache.max-size` sets the maximum weight, in bytes, of each of the three caches separately, not of all caches together. The default is 64 MiB (`67108864` bytes) for each cache, so the caches can hold up to about 192 MiB of content in total. The same content can be present in more than one cache, for example, when clients request it by content ID and by content hash.

NOTE: The configuration reference describes this property as a maximum total weight. The limit applies to each cache separately, so the total memory bound is the configured value multiplied by the number of caches.

{registry} weighs each entry as the size of the content bytes plus 64 bytes of overhead and 128 bytes for each reference. The weight estimates the payload, not the JVM objects that hold it. When you plan the JVM heap and the container memory limit, count up to three times the configured `max-size` toward the memory that {registry} uses under sustained load, in addition to the baseline memory that your capacity planning requires.

To size the cache for your workload, compare the total size of the schemas that clients read most often with the per-cache limit. Use the cache metrics to confirm the result after a change.

== Configuring the storage content cache

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can disable the storage content cache, change its size limit, or tune the staleness window for the content-and-type entry. {registry} reads these settings at startup, so you apply them by restarting {registry} with updated configuration properties or environment variables.

.Prerequisites
* {registry} is installed and you can change its configuration properties or environment variables.
* You can reach the {registry} management port, `9000` by default, to read metrics.

.Procedure
. Decide whether to keep the cache enabled. To disable it entirely, set `apicurio.storage.content-cache.enabled` to `false`. The default value is `true`.
. Set the per-cache size limit in bytes with `apicurio.storage.content-cache.max-size`. The default value is `67108864` (64 MiB). For example, set `134217728` to allow 128 MiB in each of the three caches.
. Set the staleness window for the content-and-type entry with `apicurio.storage.content-cache.hot-path.ttl-seconds`. The default value is `30`. Set `0` to disable that cache and query storage on every Confluent-compatible schema lookup by ID.
. Apply the settings and restart {registry}. Use configuration properties or the equivalent environment variables:
+
.Example: Configuration properties
[source,properties]
----
apicurio.storage.content-cache.enabled=true
apicurio.storage.content-cache.max-size=134217728
apicurio.storage.content-cache.hot-path.ttl-seconds=10
----
+
.Example: Environment variables in a container deployment
[source,yaml]
----
environment:
  APICURIO_STORAGE_CONTENT_CACHE_ENABLED: "true"
  APICURIO_STORAGE_CONTENT_CACHE_MAX_SIZE: "134217728"
  APICURIO_STORAGE_CONTENT_CACHE_HOT_PATH_TTL_SECONDS: "10"
----

.Verification
These steps assume the default setting `apicurio.ccompat.legacy-id-mode.enabled=false`.

. Request the same content twice by content ID. Replace `1` with a content ID that exists in your registry:
+
[source,bash]
----
$ curl -s http://localhost:8080/apis/registry/v3/ids/contentIds/1 > /dev/null
$ curl -s http://localhost:8080/apis/registry/v3/ids/contentIds/1 > /dev/null
----
. Read the cache metrics from the management port and filter for the content caches:
+
[source,bash]
----
$ curl -s http://localhost:9000/metrics | grep 'cache="content'
----
. Confirm the behavior that matches your configuration:
+
* When the cache is enabled, `cache_gets_total{cache="contentById",result="hit"}` increases on the second request and `cache_size{cache="contentById"}` is at least `1`.
* When the cache is disabled, the output contains no series with a `cache="contentById"`, `cache="contentByHash"`, or `cache="contentAndTypeById"` tag.
* When the TTL is `0`, the `cache="contentAndTypeById"` series are absent while the other two caches still report metrics.

== Storage content cache properties and metrics

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The storage content cache has three configuration properties, three named caches, and five Micrometer meters for each cache, exposed at `/metrics` on the management port. When `apicurio.storage.content-cache.hot-path.ttl-seconds` is `0`, {registry} does not create the `contentAndTypeById` cache and does not register its meters. The properties are available since {registry} 3.3.3.

.Storage content cache configuration properties
[.table-expandable,width="100%",cols="4,4,2,5",options="header"]
|===
|Property
|Environment variable
|Default
|Description

|`apicurio.storage.content-cache.enabled`
|`APICURIO_STORAGE_CONTENT_CACHE_ENABLED`
|`true`
|Enables the storage content cache. When `false`, {registry} does not create the caches and every content read goes to storage.

|`apicurio.storage.content-cache.max-size`
|`APICURIO_STORAGE_CONTENT_CACHE_MAX_SIZE`
|`67108864`
|Maximum weight, in bytes, of each of the three caches. The limit applies to each cache separately, so the caches can hold up to three times this value in total.

[.table-expandable,width="100%",cols="3,3,4,5",options="header"]
|===
|Cache name (`cache` tag)
|Key
|Expiry

|`contentById`
|Content ID
|None. {registry} evicts entries only when the cache exceeds its size limit.

|`contentByHash`
|SHA-256 content hash

[.table-expandable,width="100%",cols="3,3,3,5",options="header"]
|===
|Micrometer meter
|Prometheus name
|Tags
|Description

|`cache.size`
|`cache_size`
|`cache`
|Approximate number of entries currently in the cache.

|`cache.gets`
|`cache_gets_total`
|`cache`, `result`
|Number of lookups that returned a cached value (`result="hit"`) or loaded a new value from storage (`result="miss"`).

|`cache.puts`
|`cache_puts_total`
|`cache`
|Number of loads from storage, including lookups that failed because the content does not exist. A failed load does not add an entry.

|`cache.evictions`
|`cache_evictions_total`
|`cache`
|Number of entries removed by size-based eviction or expiry. The count excludes invalidations after a version delete.

|`cache_eviction_weight_total`
|`cache`
|Total weight, in bytes, of the evicted entries. The count excludes invalidations after a version delete.
|===

*Reading the metrics*

* The hit ratio for a cache is `hit / (hit + miss)` from `cache_gets_total`. A high ratio means that most reads avoid a storage round trip.
* When `cache_evictions_total` and `cache_gets_total{result="miss"}` both grow steadily, the working set exceeds the per-cache limit. Raise `apicurio.storage.content-cache.max-size` if memory allows.
* When the hit ratio stays high with few evictions, a smaller limit reclaims memory without affecting throughput.
* When the cache is disabled, or when the TTL is `0` for the `contentAndTypeById` cache, {registry} does not register the corresponding series.

== Configuring {registry} health checks on OpenShift

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Health check endpoints are served on the management interface (port 9000 by default), separate from the main application port (8080). Configure liveness and readiness probes to target port 9000.

You can configure optional environment variables for liveness and readiness probes to monitor the health of the {registry} server on OpenShift:

* _Liveness probes_ test if the application can make progress. If the application cannot make progress, OpenShift automatically restarts the failing Pod.

* _Readiness probes_ test if the application is ready to process requests. If the application is not ready, it can become overwhelmed by requests, and OpenShift stops sending requests for the time that the probe fails. If other Pods are OK, they continue to receive requests.

IMPORTANT: The default values of the liveness and readiness environment variables are designed for most cases. Change these values only if required by your environment. Any changes to the defaults depend on your hardware, network, and amount of data stored. Keep these values as low as possible to avoid unnecessary processing overhead.

.Prerequisites
* You must have an OpenShift cluster with cluster administrator access.
* You must have already installed {registry} on OpenShift.
* You must have already installed and configured your chosen {registry} storage in either {kafka-streams} or PostgreSQL.

.Procedure

. In the OpenShift Container Platform web console, log in using an account with cluster administrator privileges.

. Click *Installed Operators* > *{registry}*.

. On the *ApicurioRegistry* tab, click the Operator custom resource for your deployment, for example, *example-apicurioregistry*.

. In the main overview page, find the *Deployment Name* section and the corresponding `DeploymentConfig` name for your {registry} deployment, for example, *example-apicurioregistry*.

. In the left navigation menu, click *Workloads* > *Deployment Configs*, and select your `DeploymentConfig` name.

. Click the *Environment* tab, and enter your environment variables in the *Single values env* section, for example:
** *NAME*: `LIVENESS_STATUS_RESET`
** *VALUE*: `350`

. Click *Save* at the bottom.
+
Alternatively, you can complete these steps by using the OpenShift `oc` command. For more details, see the link:https://docs.openshift.com/container-platform/{registry-ocp-version}/cli_reference/openshift_cli/getting-started-cli.html[OpenShift CLI documentation].
