= {registry} data contracts

:_mod-docs-content-type: ASSEMBLY

[role="_abstract"]
{registry} provides a Data Contracts framework that uses the Open Data Contract Standard (ODCS) v3.1 as the native contract format for managing schema contracts between data producers and consumers.

[id="data-contracts-overview_{context}"]
== Overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
The Data Contracts framework enables teams to define, enforce, and track formal agreements about schema structure, ownership, and quality using the industry-standard ODCS format.

A data contract in {registry} combines the following elements:

ODCS format:: Contracts are submitted as ODCS v3.1 YAML documents and projected onto schema artifacts.
Metadata:: Ownership, classification, SLA, and support information are projected as labels.
Lifecycle:: Status tracking (DRAFT, STABLE, DEPRECATED) and promotion stages (DEV, STAGE, PROD).
Quality rules:: Accuracy and completeness rules from ODCS are projected as CEL contract rules.
Field tags:: PII and classification annotations are stored as version labels, with automatic extraction from Avro, JSON Schema, and Protobuf schemas.
Multi-contract support:: Multiple contracts can reference the same schema artifact without overwriting each other.

NOTE: Data contracts are always available. No special configuration is required: submitting a contract is an explicit opt-in action.

[id="data-contracts-odcs_{context}"]
== ODCS native format

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
{registry} uses the Open Data Contract Standard (ODCS) v3.1 as its native contract format. ODCS is a Linux Foundation standard maintained by the Bitol project. When an ODCS contract is submitted, its contents are *projected* onto the referenced schema artifacts.

{registry} adopts ODCS for the following reasons:

Industry standard:: ODCS is the Linux Foundation standard for data contracts, with ecosystem tooling such as `datacontract-cli`.
Vendor neutral:: {registry} is the first schema registry to natively support ODCS.
Interoperable:: ODCS contracts can be imported, exported, and used with external tools without translation.

Multiple ODCS contracts can reference the same schema artifact. Each contract's projections are namespaced by contract ID, so they do not interfere:

----
Contract "orders-contract" → contract.orders-contract.owner.team = orders-team
Contract "billing-contract" → contract.billing-contract.owner.team = billing-team
----

Updating or deleting a contract only affects its own namespaced labels, rules, and tags.

[id="data-contracts-odcs-projection_{context}"]
== ODCS projection mapping

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
When you submit an ODCS contract, {registry} parses the YAML, stores it as an `ODCS_CONTRACT` artifact, and projects its contents onto the referenced schema artifacts. Each projection is namespaced by the contract ID.

.ODCS projection mapping
[cols="2,3", options="header"]
|===
|ODCS section |Projected to

|`info.status`
|`contract.{contractId}.status` label (draft->DRAFT, active->STABLE, deprecated or retired->DEPRECATED, any other value->DRAFT)

|`info.dataClassification`
|`contract.{contractId}.classification` label

|`team.name` / `team.domain` / `team.contact`
|`contract.{contractId}.owner.team`, `.owner.domain`, `.support.contact` labels

|`quality.accuracy` rules
|CEL contract rules prefixed `odcs:{contractId}:` in the contract_rules table

|`quality.completeness` rules
|`contract.{contractId}.quality.completeness.{field}` labels

|`quality.freshness`
|`contract.{contractId}.quality.freshness.maxStaleness` label

|`schemas[].fields[].pii` / `.tags`
|`field-tag.{contractId}:{fieldPath}\|{tagName}` version labels

|`serviceLevel.*`
|`contract.{contractId}.sla.*` labels (stored, not enforced by registry)
|===

ODCS accuracy rule thresholds determine what happens when a rule fails:

.Accuracy rule threshold mapping
[cols="1,1,3", options="header"]
|===
|Threshold |Failure action |Behavior

|1.0 (100%)
|`ERROR`
|Zero tolerance. Non-compliant data is rejected.

|0.95-0.99
|`DLQ`
|Near-100% tolerance. Violations are routed to a dead letter queue.

|Below 0.95
|`NONE`
|Soft constraint. Violations are logged only.
|===

== ODCS contract example

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Submitting a complete ODCS v3.1 contract to {registry} produces a set of projections on the schema artifacts that the contract references. The example contract and its resulting projections show how each contract section maps to labels and rules on those artifacts.

.ODCS v3.1 contract
[source,yaml]
----
apiVersion: v3.1.0
kind: DataContract
id: orders-contract
info:
  title: Orders Contract
  version: 1.0.0
  description: Data contract for order events
  status: active
  dataClassification: confidential
team:
  name: orders-team
  domain: commerce
  contact: orders@company.com
schemas:
  - name: OrderEvent
    type: avro
    location: orders/OrderEvent:3
    fields:
      customerEmail:
        description: Customer email address
        pii: true
        tags:
          - PII
          - EMAIL
      totalAmount:
        description: Total order amount in cents
quality:
  accuracy:
    - name: positive-amount
      expression: totalAmount > 0
      threshold: 1.0
    - name: valid-email
      expression: "customerEmail.matches('.*@.*\\\\..*')"
      threshold: 0.99
  completeness:
    - field: orderId
      threshold: 1.0
    - field: customerEmail
      threshold: 0.99
  freshness:
    maxStaleness: PT5M
serviceLevel:
  availability: 0.999
  latency:
    p99: PT1S
----

When submitted, this contract results in the following projections:

. An `ODCS_CONTRACT` artifact is created to store the YAML.
. Namespaced labels are set on the `orders/OrderEvent` artifact: `contract.orders-contract.status=STABLE`, `contract.orders-contract.owner.team=orders-team`, and `contract.orders-contract.classification=CONFIDENTIAL`.
. Two CEL contract rules are created: `odcs:orders-contract:positive-amount` with `onFailure=ERROR`, and `odcs:orders-contract:valid-email` with `onFailure=DLQ`.
. Completeness thresholds are stored as labels, such as `contract.orders-contract.quality.completeness.orderId=1.0`.
. Field tags are set: `field-tag.orders-contract:customerEmail|PII=EXTERNAL` and `field-tag.orders-contract:customerEmail|EMAIL=EXTERNAL`.
. SLA labels are stored for external monitoring tools.

When you update an ODCS contract, only rules prefixed with `odcs:{contractId}:` are replaced. Rules added manually through the contract ruleset API are preserved.

[id="data-contracts-odcs-location_{context}"]
== Schema location format

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The `schemas[].location` field in an ODCS contract references an artifact in the registry.

----
groupId/artifactId:version
----

The following examples show the supported location forms:

`orders/OrderEvent:3`:: Group `orders`, artifact `OrderEvent`, version 3.
`OrderEvent:latest`:: Default group, artifact `OrderEvent`, latest version.
`OrderEvent`:: Default group, artifact `OrderEvent`, latest version.

IMPORTANT: Each entry under `schemas[]` is independent. Projection and field metadata (PII, tags, classifications) apply only to the artifact named in that entry's `location`. Cross-artifact schema references inside the Avro/JSON Schema/Protobuf content are not followed during projection. If a nested type lives in another artifact, either add a separate `schemas[]` entry for that artifact or give it its own contract. For more information, see the artifact references concept in the additional resources.

== Artifact references and data contracts

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
Schema artifacts can reference other artifacts (for example an Avro `OrderEvent` that references a shared `Address` record). Data contracts stay scoped to each artifact. {registry} does not walk those cross-artifact references when projecting ODCS field metadata.

*What works at evaluation time*

When a Kafka record is serialized, nested objects are fully materialized. An Avro `GenericRecord` contains the nested `Address` values inline, not a pointer to another registry artifact. After conversion to a map, CEL rules can reach nested paths:

[source,json]
----
{
  "orderId": "ORD-123",
  "address": { "street": "123 Main St", "zipCode": "90210" }
}
----

A CEL expression such as `address.zipCode != ""` works at rule evaluation time because the nested fields are present on the record.

*What projection does not do*

ODCS `schemas[].fields` metadata (PII flags, tags, classifications) is projected only for fields that belong to the artifact listed in that `schemas[]` entry. The projection engine does not resolve artifact references to discover fields that live on another schema.

So you cannot tag `address.street` as PII from an `OrderEvent` contract if `street` is defined on a separate `Address` artifact. Declare PII on the `Address` contract (or add `Address` as its own `schemas[]` entry) instead.

*Why contracts stay per-artifact*

* Ownership stays clear: the team that owns `Address` declares which of its fields are PII.
* Changing `Address` does not force every dependent contract to be re-projected.
* Conflicting metadata is avoided when two contracts would otherwise both claim the same nested field.

*Practical guidance*

* Put field-level PII and tags on the contract (or `schemas[]` entry) for the artifact that actually defines those fields.
* Use CEL quality rules on the parent artifact when you need to validate nested values on the wire; those rules see the materialized record.
* List every governed schema under `schemas[]` when one ODCS document should cover several related artifacts.

NOTE: **Upgrade note:** Earlier releases projected field tags from every `schemas[]` entry onto each target artifact. Field-tag projection now uses only the entry whose `location` resolves to the target artifact. Artifacts with no matching entry receive no projected field tags. Contracts that previously relied on cross-entry tag bleed-through should add a dedicated `schemas[]` entry per governed artifact.

== Field-level tags

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Field tags provide semantic annotation of schema fields, enabling you to identify sensitive data and apply tag-based governance.

Tags come from two sources:

Inline tags:: Extracted automatically from schema content during registration by tag extractors.
External tags:: Projected from ODCS contracts or set manually by using the version labels API.

{registry} recognizes the following common tags:

.Common field tags
[cols="1,3", options="header"]
|===
|Tag |Meaning

|`PII`
|Personally Identifiable Information

|`SENSITIVE`
|Sensitive data requiring special handling

|`EMAIL`
|Email address fields

|`PHONE`
|Phone number fields

|`FINANCIAL`
|Financial data

|`HEALTH`
|Health-related data (PHI)
|===

[id="data-contracts-field-tags-formats_{context}"]
== Supported schema formats

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Tag extractors read field-level tags from schema content for Avro, JSON Schema, and Protobuf.

Avro:: Tags are extracted from `tags` and `confluent:tags` field properties.
+
[source,json]
----
{
  "type": "record",
  "name": "User",
  "fields": [{
    "name": "email",
    "type": "string",
    "tags": ["PII", "EMAIL"]
  }]
}
----

JSON Schema:: Tags are extracted from `x-tags` and `x-confluent-tags` extension properties. Supports nested objects, arrays, `additionalProperties`, and `allOf`/`oneOf`/`anyOf` compositions.
+
[source,json]
----
{
  "type": "object",
  "properties": {
    "email": {
      "type": "string",
      "x-tags": ["PII", "EMAIL"]
    }
  }
}
----

Protobuf:: Tags are extracted from documentation comments using the `@tag:` annotation. Also supports Confluent `confluent.field_meta` field options.
+
[source,protobuf]
----
message User {
  // @tag:PII,EMAIL
  string email = 1;
}
----

== Contract rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Contract rules define validation and transformation logic associated with artifacts or specific versions. Rules are organized into *domain rules* (business logic) and *migration rules* (schema evolution).

When you submit an ODCS contract, its `quality.accuracy` rules are automatically projected as CEL domain rules on the referenced schema artifact.

The rule execution and migration REST endpoints enforce contract rules on the server. The Java Kafka SerDes enforce them on the client, where they evaluate a cached copy of the artifact-level ruleset.

Rules are classified by kind:

`CONDITION`:: Validates a condition and either passes or fails.
`TRANSFORM`:: Modifies data.

Rules run in one of the following modes:

`WRITE`:: Executes on serialize (producer side).
`READ`:: Executes on deserialize (consumer side).
`WRITEREAD`:: Executes on both.
`UPGRADE` / `DOWNGRADE`:: Executes during schema migration.

{registry} supports the following rule types:

`CEL`:: Common Expression Language for validation conditions and simple transforms, implemented with the `cel-standalone` library. Supports the full CEL specification, including `has()`, `size()`, `contains()`, `startsWith()`, parenthesized grouping, and ternary expressions.
`JSONATA`:: JSONata expressions for data transformation. Supports both `CONDITION` (truthy check) and `TRANSFORM` (returns transformed data) kinds. Useful for schema migration transforms.

A CEL expression can use each top-level field of the record as a variable with the same name, for example `totalAmount > 0`. Reference nested fields by dot path, for example `address.zipCode != ""`. An expression that references a field that the record does not contain fails to compile. {registry} treats an evaluation error as a rule failure and applies the rule's `onFailure` action.

When a rule fails, one of the following actions occurs:

`NONE`:: Processing continues and the violation is logged only.
`ERROR`:: An exception is thrown and the operation is rejected.
`DLQ`:: The message is routed to a dead letter queue.

Each rule in a `domainRules` or `migrationRules` list has the following fields:

.Contract rule fields
[cols="1,1,4", options="header"]
|===
|Field |Required |Description

|`name`
|Yes
|Rule name. The scope merge matches rules by name. ODCS projection names its rules `odcs:\{contractId}:\{ruleName}`.

|`kind`
|Yes
|`CONDITION` or `TRANSFORM`.

|`type`
|Yes
|Rule executor type: `CEL` or `JSONATA`.

|`mode`
|Yes
|`WRITE`, `READ`, `WRITEREAD`, `UPGRADE`, or `DOWNGRADE`.

|`expr`
|No
|The CEL or JSONata expression.

|`params`
|No
|Map of string parameters attached to the rule. ODCS projection sets `source` to `odcs:\{contractId}:\{contractVersion}` and `threshold` to the threshold of the ODCS accuracy rule (`1.0` when the ODCS rule has no threshold).

|`tags`
|No
|List of string tags. You can search rules by tag across the registry.

|`onSuccess`
|No
|Action for a passing rule: `NONE`, `ERROR`, or `DLQ`. {registry} stores and returns the value but does not act on it. ODCS projection sets `NONE`.

|`onFailure`
|No
|Action when the rule fails: `NONE`, `ERROR`, or `DLQ`. A failing rule with `onFailure=ERROR` stops evaluation of the remaining rules.

|`disabled`
|No
|When `true`, the rule does not run.
|===

== Contract lifecycle

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The contract lifecycle tracks the maturity of a schema through defined status transitions.

A contract has one of the following statuses:

`DRAFT`:: The schema is being developed and is not ready for production.
`STABLE`:: The schema is production-ready.
`DEPRECATED`:: The schema is being phased out.

Statuses transition in one direction only:

----
DRAFT ──────► STABLE ──────► DEPRECATED
   │                              ▲
   └──────────────────────────────┘
         (skip stable)
----

NOTE: Reverse transitions are not allowed.

Independently of status, a contract also tracks a promotion stage:

----
DEV ──────► STAGE ──────► PROD
----

The `POST /groups/\{groupId}/artifacts/\{artifactId}/contract/promote` endpoint applies the following rules and rejects a request that breaks one with HTTP 400.

* Promotion moves forward only. The endpoint rejects the current stage and earlier stages.
* Stages cannot be skipped. A contract in `DEV` must reach `STAGE` before `PROD`.
* Promotion to `PROD` requires the `STABLE` status.
* The first promotion of a contract with no stage can target any stage. `PROD` still requires `STABLE`.

The contract metadata API can also set the stage directly. It checks only that the value is `DEV`, `STAGE`, or `PROD` and does not apply the promotion rules.

[id="data-contracts-migration_{context}"]
== Schema migration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Schema migration allows you to transform data records between different schema versions using migration rules.

Migration rules use the UPGRADE or DOWNGRADE mode and are typically JSONata TRANSFORM rules that reshape data from one version to another:

.Migration rule example
[source,json]
----
{
  "domainRules": [],
  "migrationRules": [
    {
      "name": "v1-to-v2-upgrade",
      "kind": "TRANSFORM",
      "type": "JSONATA",
      "mode": "UPGRADE",
      "expr": "$ ~> |$|{'fullName': firstName & ' ' & lastName}|",
      "onFailure": "ERROR",
      "disabled": false
    }
  ]
}
----

The migration endpoint chains transforms across multiple versions:

[source,bash]
----
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/migrate \
  -H 'Content-Type: application/json' \
  -d '{
    "fromVersion": "1",
    "toVersion": "3",
    "record": {"firstName": "John", "lastName": "Doe", "amount": 100}
  }'
----

The service determines the direction (upgrade or downgrade), loads migration rules for each intermediate version, and chains the transforms sequentially. The response has the same fields as the rule execution response: `passed`, `violations`, `executedRules`, and `failedRules`. When at least one transform changed the record, the response also contains the migrated record in `transformedRecord`.

Compatibility groups partition the version history for compatibility checking. Versions in different groups are not compared against each other during compatibility validation.

[source,bash]
----
# Set compatibility group
curl -X PUT \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/compatibility-group \
  -H 'Content-Type: application/json' \
  -d '{"contractId": "orders-contract", "compatibilityGroup": "v2-family"}'

# Get compatibility group
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/compatibility-group?contractId=orders-contract"
----

Both requests require the contract ID. The `GET` request returns `{"compatibilityGroup": "v2-family"}`. You can also set the compatibility group with the `compatibilityGroup` field of the contract metadata API.

== Kafka SerDes integration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Contract rules can be enforced during normal Kafka serialization and deserialization using the Apicurio Registry SerDes libraries. Rules are executed transparently; no code changes are required beyond configuration.

Enable contract rule enforcement by setting these properties on your Kafka producer or consumer:

.SerDes contract rule properties
[cols="3,1,3", options="header"]
|===
|Property |Default |Description

|`apicurio.registry.serde.contract-rules.enabled`
|`false`
|Enable contract rule execution during serialize/deserialize

|`apicurio.registry.serde.contract-rules.fail-on-error`
|`true`
|When `true`, rule violations throw a `RuntimeException`. When `false`, the SerDes log the violations as warnings and continue

|`apicurio.registry.serde.contract-rules.cache.ttl.seconds`
|`60`
|Number of seconds that the SerDes cache a fetched ruleset. After the entry expires, the SerDes fetch the ruleset again on the next message

|`apicurio.registry.serde.contract-rules.migration.enabled`
|`false`
|Used by deserializers only. Enables inline schema migration when the schema version of a record differs from the target version

|`apicurio.registry.serde.contract-rules.migration.target-version`
|None
|Used by deserializers only. The schema version to migrate records to. Migration runs only when both migration properties are set
|===

The SerDes libraries depend on the contract rules engine, so you need no extra dependency.

Contract rule enforcement works as follows:

Ruleset cache:: On the first message for an artifact, the SerDes fetch the artifact-level contract ruleset from the registry and cache it for `apicurio.registry.serde.contract-rules.cache.ttl.seconds`. Later messages do not call the registry. A ruleset change on the server reaches a client after the cached entry expires.
Rule scope:: The SerDes evaluate the artifact-level ruleset. Global contract rules and version-level domain rules run only on the server-side rule execution endpoint, not in the SerDes.
Producer (serializer):: After schema resolution and before serialization, the serializer evaluates the cached ruleset locally with mode `WRITE`. If a rule fails and `fail-on-error` is `true`, the serializer throws an exception.
Consumer (deserializer):: After deserialization, the deserializer evaluates the cached ruleset locally with mode `READ`.
Inline migration (deserializer):: When `migration.enabled` is `true` and `migration.target-version` is set, the deserializer compares the schema version of the record with the target version. When they differ, it loads the version-level ruleset of each version after the record's version, up to and including the target version. It caches each ruleset for the same TTL and runs its migration rules in `UPGRADE` or `DOWNGRADE` mode. The deserializer handles a failing migration rule like a failing domain rule.
DLQ pattern:: Set `fail-on-error=false` to allow serialization to proceed even when rules fail. The SerDes log the violations as warnings. Your application routes the message to a dead letter queue.

.Producer with contract rules example
[source,java]
----
Properties props = new Properties();
props.put(SerdeConfig.REGISTRY_URL, "http://localhost:8080/apis/registry/v3");
props.put(SerdeConfig.EXPLICIT_ARTIFACT_GROUP_ID, "my-group");
props.put(SerdeConfig.ARTIFACT_RESOLVER_STRATEGY, TopicRecordIdStrategy.class.getName());
props.put(SerdeConfig.CONTRACT_RULES_ENABLED, "true");
props.put(SerdeConfig.CONTRACT_RULES_FAIL_ON_ERROR, "true");
props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, AvroKafkaSerializer.class.getName());
// ... other Kafka producer properties

KafkaProducer<String, GenericRecord> producer = new KafkaProducer<>(props);
----

== Audit log

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The contract audit log records contract metadata updates and status transitions for compliance and debugging.

The audit log records the following operations:

* Metadata updates through the contract metadata API, recorded with the action `METADATA_UPDATED`
* Status transitions through the contract status API, for example from `DRAFT` to `STABLE`, recorded with the action `STATUS_CHANGED` and the transition in `details`

The audit log does not record ruleset changes or ODCS contract submissions. Ruleset changes emit `CONTRACT_RULESET_CONFIGURED` events instead.

Query the audit log for an artifact. The endpoint returns entries newest first by `createdOn`. Page through them with the `offset` (default `0`) and `limit` (default `20`, maximum `500`) query parameters:

[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/audit?offset=0&limit=20"
----

.Response
[source,json]
----
[
  {
    "auditId": 12,
    "groupId": "my-group",
    "artifactId": "my-artifact",
    "version": null,
    "action": "STATUS_CHANGED",
    "principal": "admin",
    "details": "DRAFT -> STABLE",
    "createdOn": "2026-05-19T10:30:00Z"
  },
  {
    "auditId": 11,
    "groupId": "my-group",

NOTE: Entries with the same `createdOn` timestamp have no fixed order and can change position between requests.

== Contract search

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Search for contracts across the registry using metadata filters, and find contract rules by tag.

The `GET /search/contracts` endpoint returns the artifacts that carry contract metadata labels. The response is a standard artifact search result with a `count` and a list of `artifacts`. The endpoint accepts the following query parameters and ignores any other parameter.

.Contract search query parameters
[cols="2,3", options="header"]
|===
|Parameter |Description

|`status`
|Filter by lifecycle status (`DRAFT`, `STABLE`, `DEPRECATED`)

|`ownerTeam`
|Filter by owner team name

|`compatibilityGroup`
|Filter by compatibility group

|`offset`
|Number of results to skip (default `0`)

|`limit`
|Maximum number of results (default `20`, maximum `1000`)

|`order`
|Sort direction: `asc` or `desc` (default `desc`)

|`orderby`
|Sort field: `name`, `createdOn`, or `modifiedOn` (default `createdOn`)
|===

[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/search/contracts?status=STABLE&ownerTeam=orders-team&limit=10"
----

The `GET /search/contract/rules` endpoint returns every artifact-level or version-level contract rule with a given tag. The `tag` query parameter is required. Results include only rules on artifacts that you can read.

[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/search/contract/rules?tag=pii"
----

.Response
[source,json]
----
[
  {
    "groupId": "my-group",
    "artifactId": "my-artifact",
    "globalId": null,
    "ruleCategory": "DOMAIN",
    "rule": {
      "name": "require-email",
      "kind": "CONDITION",
      "type": "CEL",
      "mode": "WRITE",
      "expr": "customerEmail != \"\"",
      "tags": ["pii"],
      "onFailure": "ERROR",
      "disabled": false
    }
  }
]
----

`globalId` identifies the version for a version-level rule and is `null` for an artifact-level rule. `ruleCategory` is `DOMAIN` or `MIGRATION`.

[id="data-contracts-global-rules_{context}"]
== Global contract rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Global contract rulesets provide a baseline set of rules applied to all artifacts. Artifact-level and version-level rules override global rules by name.

You can also manage the global contract ruleset in the {registry} web console. Click the *Contract rules* tab in the console navigation to add, delete, or clear global contract rules without calling the REST API directly.

The rule execution endpoint merges domain rules from three scopes:

. Global rules apply to all artifacts and are set through `/admin/contracts/ruleset`.
. Artifact rules apply to a specific artifact and are set through `/groups/\{g}/artifacts/\{a}/contract/ruleset`.
. Version rules apply to a specific version and are set through `.../versions/{v}/contract/ruleset`.

If a rule with the same name exists at multiple levels, the most specific scope wins. {registry} does not merge migration rules across scopes. The migration endpoint and the deserializer load the migration rules of each version from that version's ruleset. The Kafka SerDes evaluate the artifact-level ruleset only and do not apply global rules.

[source,bash]
----
# Set global ruleset
curl -X PUT \
  http://localhost:8080/apis/registry/v3/admin/contracts/ruleset \
  -H 'Content-Type: application/json' \
  -d '{
    "domainRules": [{
      "name": "require-non-empty",
      "kind": "CONDITION",
      "type": "CEL",
      "mode": "WRITE",
      "expr": "size(orderId) > 0",
      "onFailure": "ERROR",
      "disabled": false
    }],
    "migrationRules": []
  }'

# Get global ruleset
curl http://localhost:8080/apis/registry/v3/admin/contracts/ruleset

# Delete global ruleset
curl -X DELETE http://localhost:8080/apis/registry/v3/admin/contracts/ruleset
----

== REST API

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The Data Contracts REST API provides endpoints for managing ODCS contracts, contract metadata, and contract rulesets.

.ODCS contract REST API endpoints
[cols="1,4,3", options="header"]
|===
|Method |Endpoint |Description

|POST
|`/groups/{groupId}/contracts`
|Submit an ODCS contract YAML. Creates the contract artifact and projects onto referenced schema artifacts.

|GET
|`/groups/{groupId}/contracts?limit=&offset=`
|List ODCS contracts in a group (paginated, default 20, max 500)

|GET
|`/groups/{groupId}/contracts/{contractId}`
|Retrieve the ODCS contract YAML

|PUT
|`/groups/{groupId}/contracts/{contractId}`
|Update an ODCS contract (creates a new version and re-projects)

|DELETE
|`/groups/{groupId}/contracts/{contractId}`
|Delete an ODCS contract artifact

|GET
|`/groups/{groupId}/artifacts/{artifactId}/contract/export`
|Export an artifact's contract data as ODCS YAML
|===

NOTE: The `POST /groups/\{groupId}/contracts` and `PUT /groups/\{groupId}/contracts/\{contractId}` endpoints store the ODCS contract without artifact references. For such a contract, the `references=DEREFERENCE` and `references=REWRITE` options of the version content endpoint return the YAML unchanged. Reference resolution works only for `ODCS_CONTRACT` artifacts registered through the generic artifact endpoints with their references.

== REST API examples

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Common `curl` examples for the Data Contracts REST API, including submitting, listing, exporting, and promoting contracts.

.Submitting an ODCS contract
[source,bash]
----
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/contracts \
  -H 'Content-Type: application/x-yaml' \
  --data-binary @my-contract.yaml
----

.Response
[source,json]
----
{
  "contractId": "orders-contract",
  "version": "1.0.0",
  "projection": {
    "rulesApplied": 2,
    "labelsApplied": 8,
    "tagsApplied": 3,
    "warnings": []
  }
}
----

.Listing contracts
[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/groups/my-group/contracts?limit=10&offset=0"
----

.Exporting as ODCS
[source,bash]
----
curl http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/export
----

Returns the reconstructed ODCS v3.1 YAML from the artifact's current contract labels, rules, and field tags.

.Promoting a contract
[source,bash]
----
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/promote \
  -H 'Content-Type: application/json' \
  -d '{"contractId": "orders-contract", "targetStage": "STAGE"}'
----

.Getting quality score
[source,bash]
----
curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/quality?contractId=orders-contract"
----

.Response
[source,json]
----
{"overall": 0.85, "completeness": 0.83, "compliance": 1.0, "stability": 0.67}
----

.Executing contract rules
[source,bash]
----
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/versions/1/contract/execute \
  -H 'Content-Type: application/json' \
  -d '{"mode": "WRITE", "record": {"totalAmount": 100, "customerEmail": "jane@example.com"}}'
----

.Response
[source,json]
----
{"passed": true, "violations": [], "executedRules": 2, "failedRules": 0}
----

The example assumes no global contract rules. The execute endpoint merges the global ruleset into the evaluation, so a global rule that references a field missing from the record, such as `size(orderId) > 0`, fails and the endpoint rejects the request.

.Setting contract metadata directly
[source,bash]
----
curl -X PUT \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/metadata \
  -H 'Content-Type: application/json' \
  -d '{
    "status": "DRAFT",
    "ownerTeam": "Platform Team",
    "ownerDomain": "payments",
    "supportContact": "platform@example.com",
    "classification": "CONFIDENTIAL",
    "stage": "DEV"
  }'
----

.Transitioning contract status
[source,bash]
----
curl -X POST \
  http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/contract/status \
  -H 'Content-Type: application/json' \
  -d '{ "status": "STABLE" }'
----

== Configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Data contracts are always available; no special configuration is required. Submitting a contract is an explicit opt-in action that does not affect existing registry functionality.

Contract rule enforcement in Kafka client applications is controlled by the SerDes properties described in the Kafka SerDes integration reference.

Data contracts work across all storage variants:

SQL (PostgreSQL):: Full support with immediate consistency. The `contract_audit_log` table is created automatically (database upgrade 106).
KafkaSQL:: Full support. Label writes go through the Kafka journal for multi-node consistency.
GitOps / KubernetesOps:: Read-only safe. Write operations are rejected by the read-only decorator.
