// con-operator-overview
[id="operator-overview_{context}"]
== {operator} deployment overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
The {operator} installs the `ApicurioRegistry3` custom resource definition (CRD). You use the `ApicurioRegistry3` CR to deploy and manage {registry} instances on {kubernetes}.

The custom resource enables you to declaratively configure all aspects of your {registry} deployment, including storage, authentication, networking, and component-specific settings.

NOTE: Additional `ApicurioRegistry3` custom resource examples are available in the {registry} upstream repository.

The `ApicurioRegistry3` custom resource is organized into three sections:

* `spec.app` - Configures the {registry-app}
* `spec.ui` - Configures the {registry-ui}
* `spec.consolePlugin` - Configures the OpenShift Console plugin component. See xref:configuring-console-plugin_{context}[].

You configure replicas, ingress, environment variables, and pod specifications separately for `spec.app` and `spec.ui`.

The {operator} Deployment sets `runAsNonRoot: true`, `seccompProfile.type: RuntimeDefault`, `allowPrivilegeEscalation: false`, and `readOnlyRootFilesystem: true`, and drops all Linux capabilities. These settings meet the `restricted` Pod Security Standards profile. The {operator} sets no security context on the {registry} app and UI pods, so they use the namespace defaults. To run them in a namespace that enforces the `restricted` profile, set the security context in `podTemplateSpec`:

[source,yaml]
----
spec:
  app:
    podTemplateSpec:
      spec:
        securityContext:
          runAsNonRoot: true
          seccompProfile:
            type: RuntimeDefault
        containers:
          - name: apicurio-registry-app
            securityContext:
              allowPrivilegeEscalation: false
              capabilities:
                drop:
                  - ALL
----

// ref-operator-storage-options
[id="operator-storage-options_{context}"]
== Storage options

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} supports the following storage options:

* *Embedded H2 database* (default) - When you do not specify a storage type, {registry} uses SQL storage with an embedded H2 database. Suitable for development and testing only. {registry} stores all data in memory and loses it when the pod restarts.
* *PostgreSQL* - Stores data in a PostgreSQL database. Suitable for production deployments.
* *MySQL* - Stores data in a MySQL database. Suitable for production deployments.
* *KafkaSQL* - Stores data in Apache Kafka topics, with an embedded H2 database as a local SQL store that {registry} rebuilds from the Kafka journal on each startup. Suitable for production deployments when you configure persistent Kafka storage.
* *KubernetesOps* - Read-only storage that loads registry data from Kubernetes ConfigMaps. Suitable for
Kubernetes-native and GitOps workflows. This is an experimental feature.
* *GitOps* - Read-only storage that loads registry data from Git repositories through a sync sidecar container. Suitable for Git-based workflows. This is an experimental feature.

IMPORTANT: The default embedded H2 configuration is not suitable for production environments. Configure a storage type (`postgresql`, `mysql`, `kafkasql`, `kubernetesops`, or `gitops`) for production use.

// proc-deploying-registry-inmemory
[id="deploying-registry-inmemory_{context}"]
== Deploying {registry} with default configuration (embedded H2 database)

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can deploy a basic {registry} instance by using the default storage configuration (SQL with an embedded H2 database). This configuration is suitable for development and testing environments only.

You do not need to specify a storage type in the CR. When omitted, {registry} defaults to an embedded H2 database.

.Prerequisites
* You must have cluster administrator access to {kubernetes-with-article} cluster.
* You must have already installed the {operator}. See {installing-the-registry-openshift}.

.Procedure

. In the {kubernetes} web console, log in using an account with cluster administrator privileges.

. Change to the {kubernetes-namespace} in which the {operator} is installed. For example, from the
*Project* drop-down, select `my-project`.

. Click *Installed Operators* > *{registry}* > *ApicurioRegistry3* > *Create ApicurioRegistry3*.

. Paste in the following custom resource definition:
+
[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry
spec:
  app:
    ingress:
      host: registry.example.com
  ui:
    ingress:
      host: registry-ui.example.com
----
+
NOTE: Replace the `host` values with hostnames for your environment. By default, the {operator} creates plain HTTP Ingresses. To enable TLS, set `tlsTermination` and `tlsSecretName` in the `ingress` section of each component. See xref:configuring-ingress-hostname_{context}[]. You can instead disable the operator-managed Ingress and create your own Ingress or Route resources with TLS.

. Click *Create* and wait for the {registry} deployment to be created.

. Click *Networking* > *Ingresses* (or *Routes*) to access the route for the {registry} web console.

.Verification

* Access the {registry} web console using the configured hostname and verify that the UI loads successfully.

// proc-deploying-registry-postgresql
[id="deploying-registry-postgresql_{context}"]
== Deploying {registry} with PostgreSQL storage

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Deploy {registry} with PostgreSQL database storage. This configuration is suitable
for production environments.

.Prerequisites
* You must have cluster administrator access to {kubernetes-with-article} cluster.
* You must have already installed the {operator}. See {installing-the-registry-openshift}.
* You must have a PostgreSQL database available with a database created for {registry}.
* You must have created a Kubernetes Secret containing the PostgreSQL database password.

.Procedure

. Create a Secret containing the database password:
+
[source,yaml]
----
apiVersion: v1
kind: Secret
metadata:
  name: postgresql-credentials
type: Opaque
stringData:
  password: your-database-password
----

. In the {kubernetes} web console, click *Installed Operators* > *{registry}* > *ApicurioRegistry3* >
*Create ApicurioRegistry3*.

. Paste in the following custom resource definition, adjusting the values for your environment:
+
[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-postgresql
spec:
  app:
    storage:
      type: postgresql
      sql:
        dataSource:
          url: jdbc:postgresql://postgresql.my-project.svc:5432/registry
          username: registry_user
          password:
            name: postgresql-credentials
            key: password
    ingress:
      host: registry.example.com
  ui:
    ingress:
      host: registry-ui.example.com
----
+
NOTE: Update the `url` to match your PostgreSQL service name, namespace, port, and database name. Update the
`username` to match your database user.

. Click *Create* and wait for the {registry} deployment to be created.

.Verification

* Access the {registry} web console and create a test artifact to verify that data is being persisted to
the database.
* Restart the {registry} pod and verify that the artifact still exists, confirming that data is persisted.

// proc-deploying-registry-kafkasql
[id="deploying-registry-kafkasql_{context}"]
== Deploying {registry} with KafkaSQL storage

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can deploy {registry} with KafkaSQL storage, which uses Apache Kafka as the primary data store. This configuration is suitable for production environments when you configure persistent Kafka storage.

KafkaSQL uses an embedded H2 database as a local SQL store that {registry} rebuilds from the Kafka journal on each startup.

.Prerequisites
* You must have cluster administrator access to {kubernetes-with-article} cluster.
* You must have already installed the {operator}. See {installing-the-registry-openshift}.
* You must have a Kafka cluster available. For OpenShift, see {installing-the-registry-storage-openshift}.

.Procedure

. Obtain the Kafka bootstrap servers address from your Kafka cluster. For example, with {kafka-streams}:
`my-cluster-kafka-bootstrap.my-project.svc:9092`

. In the {kubernetes} web console, click *Installed Operators* > *{registry}* > *ApicurioRegistry3* >
*Create ApicurioRegistry3*.

. Paste in the following custom resource definition, adjusting the `bootstrapServers` value:
+
[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-kafkasql
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        bootstrapServers: my-cluster-kafka-bootstrap.my-project.svc:9092
    ingress:
      host: registry.example.com
  ui:
    ingress:
      host: registry-ui.example.com
----

. Click *Create* and wait for the {registry} deployment to be created.

. If using {kafka-streams}, configure the Kafka topic that {registry} uses (named `kafkasql-journal` by default)
with delete cleanup policy and infinite retention:
+
[source,yaml]
----
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: kafkasql-journal
  labels:
    strimzi.io/cluster: my-cluster
spec:
  partitions: 3
  replicas: 3
  config:
    cleanup.policy: delete
    retention.ms: -1
    retention.bytes: -1
----
+
WARNING: You must configure the Kafka topic used by {registry} with `cleanup.policy: delete` and infinite retention
(`retention.ms: -1` and `retention.bytes: -1`), otherwise data loss might occur.
+
ifndef::service-registry-downstream[]
NOTE: Before you upgrade a KafkaSQL deployment from a version earlier than 3.1.3, correct the configuration of the topics that {registry} created automatically. See xref:getting-started/assembly-registry-high-availability.adoc#ha-kafkasql-topics_{context}[KafkaSQL topic configuration].
endif::[]
ifdef::service-registry-downstream[]
NOTE: Before you upgrade a KafkaSQL deployment from a version earlier than 3.1.3, correct the configuration of the topics that {registry} created automatically. See xref:ha-kafkasql-topics_{context}[].
endif::[]

.Verification

* Access the {registry} web console and create a test artifact to verify that data is being persisted to Kafka.
* Restart the {registry} pod and verify that the artifact still exists after the cache is rebuilt from Kafka.

// ref-configuring-kafkasql-tls
[id="configuring-kafkasql-tls_{context}"]
== KafkaSQL TLS configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
When your Kafka cluster requires TLS encryption, you can configure {registry} to connect securely.

[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-kafkasql-tls
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        bootstrapServers: my-cluster-kafka-bootstrap.my-project.svc:9093
        tls:
          truststoreSecretRef:
            name: kafka-cluster-ca-cert
            key: ca.p12
          truststorePasswordSecretRef:
            name: kafka-cluster-ca-cert
            key: ca.password
    ingress:
      host: registry.example.com
----

NOTE: The Secret containing the Kafka cluster CA certificate must be in PKCS12 format.

// ref-configuring-kafkasql-sasl
[id="configuring-kafkasql-sasl_{context}"]
== KafkaSQL SASL authentication configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
When your Kafka cluster requires SASL authentication (such as SCRAM-SHA-512), the recommended approach is to use
the Strimzi Kafka Access Operator (available starting with {registry} version 3.2.0), which automatically provides
all connection details in a single Kubernetes Secret.

[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-kafkasql-sasl
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        kafkaAccessSecretName: my-kafka-access
    ingress:
      host: registry.example.com
----

For OAuth (OAUTHBEARER) authentication, use the `auth` section instead:

[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-kafkasql-oauth
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        bootstrapServers: my-cluster-kafka-bootstrap.my-project.svc:9093
        tls:
          truststoreSecretRef:
            name: kafka-cluster-ca-cert
          truststorePasswordSecretRef:
            name: kafka-cluster-ca-cert
        auth:
          enabled: true
          mechanism: OAUTHBEARER
          clientIdRef:
            name: kafka-oauth-credentials
            key: clientId
          clientSecretRef:
            name: kafka-oauth-credentials
            key: clientSecret
          tokenEndpoint: https://identity-server.example.com/token
          loginHandlerClass: io.strimzi.kafka.oauth.client.JaasClientOauthLoginCallbackHandler
    ingress:
      host: registry.example.com
----

// proc-deploying-registry-kubernetesops
[id="deploying-registry-kubernetesops_{context}"]
== Deploying {registry} with KubernetesOps storage

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Deploy {registry} with KubernetesOps storage. KubernetesOps is a read-only storage
variant that loads registry data from Kubernetes ConfigMaps, enabling Kubernetes-native and GitOps workflows for
managing schemas and APIs.

IMPORTANT: KubernetesOps storage is an *experimental* feature. You must enable the experimental features gate to use it.

.Prerequisites
* You must have cluster administrator access to {kubernetes-with-article} cluster.
* You must have already installed the {operator}. See {installing-the-registry-openshift}.
* You must have access to create ConfigMaps in your cluster. The {operator} creates the required RBAC resources automatically.

.Procedure

. In the {kubernetes} web console, click *Installed Operators* > *{registry}* > *ApicurioRegistry3* >
*Create ApicurioRegistry3*.

. Paste in the following custom resource definition, adjusting the values for your environment:
+
[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-kubernetesops
spec:
  app:
    storage:
      type: kubernetesops
      kubernetesops:
        registryId: my-registry
        namespace: apicurio
    ingress:
      host: registry.example.com
  ui:
    ingress:
      host: registry-ui.example.com
----
+
NOTE: Replace `registryId` with a unique identifier for your registry instance, and
`namespace` with the namespace containing your ConfigMaps. The operator automatically enables
the experimental features gate required by KubernetesOps storage.

. Optional: Verify that the {operator} created the RBAC resources that grant the registry read access
to ConfigMaps. The {operator} automatically creates a ServiceAccount, a Role, and a RoleBinding, each named
`<cr-name>-kubeops`, and sets the service account on the registry deployment.
ifndef::service-registry-downstream[]
For deployments without the {operator}, see xref:getting-started/assembly-configuring-kubernetesops-storage.adoc#kubernetesops-rbac-requirements_{context}[RBAC requirements].
endif::[]
ifdef::service-registry-downstream[]
For deployments without the {operator}, see xref:kubernetesops-rbac-requirements_{context}[RBAC requirements].
endif::[]

. Create ConfigMaps containing your registry data.
ifndef::service-registry-downstream[]
See xref:getting-started/assembly-configuring-kubernetesops-storage.adoc#kubernetesops-configmap-format_{context}[ConfigMap data format] for the required format.
endif::[]
ifdef::service-registry-downstream[]
See xref:kubernetesops-configmap-format_{context}[ConfigMap data format] for the required format.
endif::[]

. Click *Create* and wait for the {registry} deployment to be created.

.Verification

// proc-deploying-registry-gitops
[id="deploying-registry-gitops_{context}"]
== Deploying {registry} with GitOps storage

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Deploy {registry} with GitOps storage, a read-only storage variant that loads registry data from one or more Git repositories. The {operator} adds a sync sidecar container, `apicurio-registry-gitops-sync`, to the {registry} pod. The sidecar keeps a clone of each repository in a shared volume mounted at `/repos` in both containers.

IMPORTANT: GitOps storage is an *experimental* feature. The {operator} enables the experimental features gate when you configure this storage type.

.Prerequisites
* You must have cluster administrator access to {kubernetes-with-article} cluster.
* You must have already installed the {operator}. See {installing-the-registry-openshift}.
* You must have a Git repository with registry data in the GitOps repository format, or plan to push that data to the sidecar.

.Procedure

. In the {kubernetes} web console, click *Installed Operators* > *{registry}* > *ApicurioRegistry3* >
*Create ApicurioRegistry3*.

. Paste in the following custom resource definition, adjusting the values for your environment:
+
[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry-gitops
spec:
  app:
    storage:
      type: gitops
      gitops:
        registryId: prod
        repos:
          - url: https://github.com/my-org/my-registry-data.git
            branch: main
    ingress:
      host: registry.example.com
  ui:
    ingress:
      host: registry-ui.example.com
----
+
NOTE: The `registryId` value must match the `registryId` in the registry configuration file of your repository. Otherwise, {registry} starts but loads no data. If you omit `registryId`, the application default `main` applies.

. Optional: To pull from a private repository over SSH, create one Secret with the SSH private key and another with a `known_hosts` file. Reference them in the `pull` section:
+
[source,yaml]
----
spec:
  app:
    storage:
      type: gitops
      gitops:
        registryId: prod
        repos:
          - url: git@github.com:my-org/my-registry-data.git
        pull:
          sshKeys:
            name: gitops-ssh-keys
            key: id_ed25519
          knownHosts:
            name: gitops-known-hosts
            key: known_hosts
----
+
The {operator} mounts both Secrets into the sidecar and sets its SSH environment variables.

. Optional: To accept `git push` instead of pulling from a remote repository, set `mode` to `push`. Reference the Secrets that hold the `authorized_keys` file and a persistent SSH host key:
+
[source,yaml]
----
spec:
  app:
    storage:
      type: gitops
      gitops:
        mode: push
        registryId: prod
        push:
          authorizedKeys:
            name: gitops-push-authorized-keys
            key: authorized_keys
          hostKey:
            name: gitops-push-host-key
            key: ssh_host_key
----
+
In push mode, the {operator} creates a Service named `<cr-name>-gitops-ssh-service` that exposes the SSH server of the sidecar on port `2222`. It also allows that port in the NetworkPolicy of the app component. Clients push to `ssh://git@<service-host>:2222/repos/default`.

. Optional: To load data from several repositories, list them in `repos` and give each one a distinct `dir`:
+
[source,yaml]
----
spec:
  app:
    storage:
      type: gitops
      gitops:
        registryId: prod
        repos:
          - url: https://github.com/my-org/platform-schemas.git
            dir: platform
          - url: https://github.com/my-org/fulfillment-schemas.git
            branch: fulfillment
            dir: fulfillment
----

. Click *Create* and wait for the {registry} deployment to be created.

.Verification

* Access the {registry} web console and verify that the artifacts from your repository are visible.

NOTE: GitOps storage is read-only. You cannot create, update, or delete artifacts through the REST API or web console.

// proc-configuring-registry-authentication
[id="configuring-registry-authentication_{context}"]
== Configuring authentication and authorization

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Configure {registry} with OIDC authentication and role-based authorization by using
an identity provider such as {keycloak}.

ifndef::service-registry-downstream[]
NOTE: To authenticate clients with Kubernetes service account tokens instead of an OpenID Connect provider, configure the experimental `spec.app.auth.kubernetesAuth` section and leave `spec.app.auth.enabled` unset. See xref:getting-started/assembly-configuring-registry-security.adoc#registry-security-kubernetes-auth_{context}[Configuring {registry} Kubernetes-native authentication] and xref:getting-started/assembly-operator-config-reference.adoc#kubernetes-auth-spec_{context}[KubernetesAuthSpec].
endif::[]
ifdef::service-registry-downstream[]
NOTE: To authenticate clients with Kubernetes service account tokens instead of an OpenID Connect provider, configure the experimental `spec.app.auth.kubernetesAuth` section and leave `spec.app.auth.enabled` unset. See xref:registry-security-kubernetes-auth_{context}[] and xref:kubernetes-auth-spec_{context}[].
endif::[]

.Prerequisites
* You must have cluster administrator access to {kubernetes-with-article} cluster.
* You must have already deployed {registry}. See xref:deploying-registry-inmemory_{context}[].
* You must have an OIDC identity provider configured with appropriate clients for {registry}.

.Procedure

. Configure two clients in your identity provider:
** Backend API client (for example, `registry-client-api`) - Used by the {registry-app}.
** UI client (for example, `registry-client-ui`) - Used by the {registry-ui}.

. Update your `ApicurioRegistry3` custom resource to enable authentication:
+
[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry
spec:
  app:
    auth:
      enabled: true
      appClientId: registry-client-api
      uiClientId: registry-client-ui
      authServerUrl: https://keycloak.example.com/realms/registry
      redirectUri: https://registry-ui.example.com
      logoutUrl: https://registry-ui.example.com
    ingress:
      host: registry.example.com
  ui:
    ingress:
      host: registry-ui.example.com
----

. To enable role-based authorization, add the `authz` configuration:
+
[source,yaml]
----
spec:
  app:
    auth:
      enabled: true
      appClientId: registry-client-api
      uiClientId: registry-client-ui
      authServerUrl: https://keycloak.example.com/realms/registry
      redirectUri: https://registry-ui.example.com
      logoutUrl: https://registry-ui.example.com
      authz:
        enabled: true
        ownerOnlyEnabled: true
        roles:
          source: token
          admin: sr-admin
          developer: sr-developer
          readOnly: sr-readonly
    ingress:
      host: registry.example.com
----

. To enable admin override functionality:
+
[source,yaml]
----
spec:
  app:
    auth:
      authz:
        enabled: true
        ownerOnlyEnabled: true
        adminOverride:
          enabled: true
          from: token
          type: role
          role: sr-admin
----

. To allow anonymous read-only access:
+
[source,yaml]
----
spec:
  app:
    auth:
      enabled: true
      anonymousReadsEnabled: true
      appClientId: registry-client-api
      # ... other auth settings
----

// ref-configuring-ingress-hostname
[id="configuring-ingress-hostname_{context}"]
== Ingress hostname, class, and TLS configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can specify the Ingress hostname and IngressClass for each component, and configure TLS on the operator-managed Ingress.

[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry
spec:
  app:
    ingress:
      host: registry-api.example.com
      ingressClassName: nginx
      annotations:
        nginx.org/proxy-connect-timeout: "30s"
  ui:
    ingress:
      host: registry-ui.example.com
      ingressClassName: nginx
      annotations:
        nginx.org/proxy-connect-timeout: "30s"
----

To configure TLS on the operator-managed Ingress of a component, set `tlsSecretName` and `tlsTermination` in its `ingress` section. Without these fields, the {operator} creates a plain HTTP Ingress. Unless you configure application TLS, it also logs a warning that the Ingress has no TLS.

`tlsSecretName`:: Name of a Secret of type `kubernetes.io/tls` in the namespace of the custom resource. The {operator} adds a `tls` section to the Ingress that references this Secret and the configured `host`.
`tlsTermination`:: TLS termination type: `edge`, `passthrough`, or `reencrypt`. The {operator} also sets the `route.openshift.io/termination` annotation on the Ingress. On OpenShift, this annotation controls the TLS termination of the Route that OpenShift generates from the Ingress.

With edge termination, TLS ends at the Ingress or Route, and traffic to the {registry} pod uses HTTP. Do not configure application TLS (`spec.app.tls`). Set the `REGISTRY_API_URL` environment variable of the UI to the HTTPS URL of the API:

[source,yaml]
----
spec:
  app:
    ingress:
      host: registry-api.example.com
      tlsTermination: edge
      tlsSecretName: registry-tls-cert
  ui:
    ingress:
      host: registry-ui.example.com
      tlsTermination: edge
      tlsSecretName: registry-tls-cert
    env:
      - name: REGISTRY_API_URL
        value: https://registry-api.example.com/apis/registry/v3
----

On OpenShift, you can omit `tlsSecretName` and set only `tlsTermination: edge` to use the default certificate of the OpenShift router. Cloud-based OpenShift clusters, such as Red Hat OpenShift Service on AWS, Azure Red Hat OpenShift, and OpenShift on Google Cloud, usually require HTTPS. On those clusters, set `tlsTermination: edge` so that the operator-managed Ingress works.

With passthrough termination, the encrypted traffic passes through the Ingress or Route to the {registry} pod, so you must also configure application TLS. When you configure the application keystore, the {operator} points the Ingress backend at the `https` port of the application Service:

[source,yaml]
----
spec:
  app:
    ingress:
      host: registry-api.example.com
      tlsTermination: passthrough
      tlsSecretName: registry-tls-cert
    tls:
      insecureRequests: disabled
      keystoreSecretRef:
        name: registry-keystore
        key: keystore.p12
      keystorePasswordSecretRef:
        name: registry-keystore
        key: keystore.password
  ui:
    ingress:
      host: registry-ui.example.com
      tlsTermination: edge
      tlsSecretName: registry-tls-cert
    env:
      - name: REGISTRY_API_URL
        value: https://registry-api.example.com/apis/registry/v3
----

NOTE: On Kubernetes with the NGINX Ingress Controller, passthrough might also need the `nginx.ingress.kubernetes.io/ssl-passthrough: "true"` annotation. Add it through the `annotations` field. For the application TLS fields, see xref:configuring-app-tls_{context}[].

// ref-configuring-autoscaling
[id="configuring-autoscaling_{context}"]
== Autoscaling configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can configure the {operator} to manage a horizontal pod autoscaler (HPA) for the app and UI components. When autoscaling is enabled, the {operator} creates an HPA that targets the component's Deployment, and the static `replicas` field is ignored.

[source,yaml]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry
spec:
  app:
    autoscaling:
      enabled: true
      minReplicas: 2
      maxReplicas: 5
      targetCPUUtilizationPercentage: 70
----

.Autoscaling fields
[cols="2,3,1,1",options="header"]
|===
|Field
|Description
|Type
|Default

|`enabled`
|Whether the {operator} manages a HorizontalPodAutoscaler for the component.
|Boolean
|`false`

|`minReplicas`
|Minimum number of replicas.
|Integer
|`1`

|`maxReplicas`
|Maximum number of replicas. Set this field when you enable autoscaling; when omitted, it falls back to the `minReplicas` value.
|Integer
|`minReplicas`

|`targetCPUUtilizationPercentage`
|Target average CPU utilization percentage across all pods.
|Integer
|`80`

|`targetMemoryUtilizationPercentage`
|Target average memory utilization percentage across all pods. When not set, memory-based scaling is not configured.
|Integer
|Not set
|===

The autoscaling configuration is available on both `spec.app.autoscaling` and `spec.ui.autoscaling`. If you set both `replicas` and `autoscaling` on a component, the {operator} reports a validation error condition and ignores the `replicas` field. The {operator} also manages a PodDisruptionBudget when autoscaling is enabled with `maxReplicas` greater than 1.

// ref-configuring-poddisruptionbudget
[id="configuring-poddisruptionbudget_{context}"]
== PodDisruptionBudget configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The {operator} manages PodDisruptionBudget resources by default. For the app component, it creates a PodDisruptionBudget with `maxUnavailable: 1` only when the component can run more than one pod. That is the case when `replicas` is greater than `1`, or when autoscaling is enabled with `maxReplicas` greater than `1`. With the default single replica, the app component gets no PodDisruptionBudget. For the UI component, the {operator} creates a PodDisruptionBudget with `minAvailable: 1` whenever the operator-managed PodDisruptionBudget is enabled. To manage these resources yourself, disable the operator-managed PodDisruptionBudget.

[source,yaml]
----
spec:
  app:
    podDisruptionBudget:
      enabled: false
  ui:
    podDisruptionBudget:
      enabled: false
----

// ref-using-podtemplatespec
[id="using-podtemplatespec_{context}"]
== PodTemplateSpec advanced customization

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
For advanced pod configuration, you can provide a custom PodTemplateSpec.

[source,yaml]
----
spec:
  app:
    podTemplateSpec:
      metadata:
        labels:
          custom-label: custom-value
        annotations:
          custom-annotation: custom-value
      spec:
        containers:
          - name: apicurio-registry-app
            resources:
              requests:
                memory: "512Mi"
                cpu: "500m"
              limits:
                memory: "1Gi"
                cpu: "1000m"
        affinity:
          podAntiAffinity:
            preferredDuringSchedulingIgnoredDuringExecution:
              - weight: 100
                podAffinityTerm:
                  labelSelector:
                    matchExpressions:
                      - key: app
                        operator: In
                        values:
                          - apicurio-registry
                  topologyKey: kubernetes.io/hostname
----

To customize the component container (for example, to set resource requests/limits), you must specify the container name as follows:

* `apicurio-registry-app` for the {registry-app}.
* `apicurio-registry-ui` for the {registry-ui}.

You can also add additional containers to the pod if needed.

IMPORTANT: *Order of evaluation:* The operator first extends the provided PodTemplateSpec with default values and then applies additional configuration based on other fields in the `ApicurioRegistry3` CR. Therefore, other configuration fields might override settings in the PodTemplateSpec.

// ref-configuring-app-tls
[id="configuring-console-plugin_{context}"]
== OpenShift Console plugin configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
On OpenShift, the {operator} can deploy a console plugin that adds an *Apicurio* section to the OpenShift Console administrator perspective, with pages for listing and inspecting `ApicurioRegistry3` instances.

To deploy the console plugin, both of the following conditions must be met:

* The top-level `spec.consolePlugin.enabled` field is set to `true` in the custom resource. The field defaults to `false`.
* The console plugin image is configured on the {operator}, by using the `REGISTRY_CONSOLE_PLUGIN_IMAGE` environment variable on the operator deployment.

[source,yaml]
----
spec:
  consolePlugin:
    enabled: true
----

The {operator} then creates a console plugin Deployment and Service secured with OpenShift service serving certificates, and registers a cluster-scoped `ConsolePlugin` resource named `<cr-namespace>-<cr-name>-console-plugin`. The namespace is included because `ConsolePlugin` is cluster-scoped, so the name must stay unique across CRs that share the same name in different namespaces. The plugin backend forwards the logged-in user's OpenShift bearer token to the registry API. On clusters that are not OpenShift, the console plugin is not deployed.

[id="configuring-app-tls_{context}"]
== Application TLS configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
To configure TLS certificates for the {registry} application, provide keystore references in the `ApicurioRegistry3` custom resource.

[source,yaml]
----
spec:
  app:
    tls:
      keystoreSecretRef:
        name: registry-tls
        key: keystore.p12
      keystorePasswordSecretRef:
        name: registry-tls
        key: keystore.password
----

When you configure application TLS, the `insecureRequests` field controls the plain HTTP port. `enabled`, the default, keeps the port open. `redirect` keeps it open but redirects every request to HTTPS. `disabled` does not open it. You can also provide a truststore with the `truststoreSecretRef` and `truststorePasswordSecretRef` fields. If you omit the `key` of a reference, the {operator} uses `user.p12` and `user.password` for the keystore and `ca.p12` and `ca.password` for the truststore. To serve HTTPS only:

[source,yaml]
----
spec:
  app:
    tls:
      insecureRequests: disabled
      keystoreSecretRef:
        name: registry-tls
        key: keystore.p12
      keystorePasswordSecretRef:
        name: registry-tls
        key: keystore.password
----
