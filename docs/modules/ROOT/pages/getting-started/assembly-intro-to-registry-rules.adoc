[id="registry-rules_{context}"]
== Govern {registry} content using rules

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
To govern the evolution of artifact content added to {registry}, you can configure optional rules. All configured global rules, group-specific rules, or artifact-specific rules must pass before a new artifact version can be added to {registry}.

Configured artifact-specific rules override any configured group-specific rules, which in turn override any configured global rules.

The goal of these rules is to prevent invalid content from being added to {registry} and to control the evolution of an artifact (by e.g. checking the compatibility of a new artifact version against previous versions). For example, content can be invalid for the following reasons:

* Invalid syntax for a given artifact type, for example, `AVRO` or `PROTOBUF`.
* Valid syntax, but semantics violate a specification.
* Incompatibility, when new content includes breaking changes relative to the current artifact version.
* Artifact reference integrity, for example, a duplicate or non-existent artifact reference mapping.

You can enable optional content rules using the {registry} web console, REST API commands, or by using one of the SDKs.

[id="registry-rules-apply_{context}"]
== When rules are applied

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
{registry} applies rules when you add content, and when a draft version leaves the `DRAFT` state. The following REST operations apply rules:

* Adding an artifact
* Adding an artifact version
* Changing the state of a `DRAFT` version, for example to finalize it

With `dryRun=true`, each operation applies the rules and reports the result without storing anything. Adding an artifact or version in the `DRAFT` state does not apply the rules unless you set `apicurio.rest.draft.production-mode.enabled` to `true`. {registry} applies the rules when you finalize the draft.

The compatibility check endpoints of the Confluent-compatible API also apply the configured rules to the submitted schema without storing it. When no `COMPATIBILITY` rule is configured, they check `BACKWARD` compatibility.

If a rule is violated, {registry} returns an HTTP error. The response body includes the violated rule and a message showing what went wrong.

[id="registry-rules-violation-response_{context}"]
== Rule violation responses from the REST API

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
When the content that you submit violates a content rule, the Core Registry API v3 rejects the request. The problem details body describes each violation.

The following operations apply content rules and can return a rule violation response:

* `POST /groups/\{groupId}/artifacts`, which creates an artifact
* `POST /groups/\{groupId}/artifacts/\{artifactId}/versions`, which creates an artifact version
* `PUT /groups/\{groupId}/artifacts/\{artifactId}/versions/\{versionExpression}/state`, when the version is in the `DRAFT` state, for example when you finalize a draft

With `dryRun=true`, each operation returns the same response without storing anything.

The response has HTTP status `400`, or `409` when `apicurio.rest.legacy-error-codes.enabled` is `true`. The body has the following fields:

`title`::
A short summary of the violation.

`detail`::
The summary, followed by each cause in the form `<description> at <context>`.

`status`::
The HTTP status code.

`name`::
The name of the error.

`ruleViolation`::
The details of the violation:
+
* `ruleType`: the type of the violated rule, one of `VALIDITY`, `COMPATIBILITY`, or `INTEGRITY`.
* `causes`: one entry per problem, with a `description` and a `context` that locates the problem in the content, for example a JSON Pointer.

`causes`::
The same list as `ruleViolation.causes`. This top-level field is deprecated and remains for earlier clients. Use `ruleViolation.causes` instead.

The following example shows the response when a new version of a JSON Schema artifact violates a `COMPATIBILITY` rule:

[source,json]
----
{
  "status": 400,
  "name": "RuleViolationException",
  "title": "Incompatible artifact: my-schema [JSON], num of incompatible diffs: {1}, list of diff types: [The 'maxLength' string-length limit was decreased. at /properties/name/maxLength]",
  "detail": "Incompatible artifact: my-schema [JSON], num of incompatible diffs: {1}, list of diff types: [The 'maxLength' string-length limit was decreased. at /properties/name/maxLength] Causes: The 'maxLength' string-length limit was decreased. at /properties/name/maxLength",
  "ruleViolation": {
    "ruleType": "COMPATIBILITY",
    "causes": [
      {
        "description": "The 'maxLength' string-length limit was decreased.",
        "context": "/properties/name/maxLength"
      }
    ]
  },
  "causes": [
    {
      "description": "The 'maxLength' string-length limit was decreased.",
      "context": "/properties/name/maxLength"
    }
  ]
}
----

The API defines four more optional fields on each cause: `code`, `direction`, `proposed`, and `existing`. No built-in rule returns them. Treat them as optional in client code.

[id="registry-rules-precedence_{context}"]
== Order of precedence of rules

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The order of precedence for artifact-specific and global rules is as follows:

* Artifact-specific rules have the highest priority
* Group-specific rules have the next highest priority
* Global rules have the lowest priority

NOTE: If a rule is configured at a higher level (e.g. at the global level), but you want that rule to be disabled at a lower level, you must configure the same rule (so that it overrides it) at the lower level and set its rules value to `NONE`.

[id="registry-rules-work_{context}"]
== How rules work

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
Each rule has a name and configuration information. {registry} maintains the list of rules for each artifact, each group, and the list of global rules. Each rule in the list consists of a name and configuration for the rule implementation.

When a rule is executed, it is provided with the content of the current version of the artifact (if one exists) and the new version of the artifact being added. The rule implementation returns either passes or fails depending on whether the artifact passes the rule. If not, {registry} reports the reason why in an HTTP error response. Some rules might not use the previous version of the content. For example, compatibility rules use previous versions, but syntax or semantic validity rules do not.

[id="registry-rules-config_{context}"]
== Content rule configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Administrators can configure {registry} global rules, group-specific rules, and artifact-specific rules. Developers can configure group-specific and artifact-specific rules only.

{registry} evaluates rule precedence separately for each rule type, such as `COMPATIBILITY` or `VALIDITY`. For each rule type, an artifact-specific rule overrides a group-specific rule of the same type, and a group-specific rule overrides a global rule of the same type. If a rule type is not configured at any level, and no default global rule is set for that type in the application properties, {registry} does not enforce that rule type. Configuring one rule type at a lower level does not disable other rule types that are configured at a higher level.

For example, consider a group with a `COMPATIBILITY` rule set to `BACKWARD`, and an artifact in that group with only a `VALIDITY` rule set to `FULL`:

* When you add a new version of the artifact, {registry} enforces both rules: the `VALIDITY` rule from the artifact and the `COMPATIBILITY` rule from the group. The group rule still applies because the artifact rule is of a different type.
* {registry} rejects a new version that is not backward compatible, and accepts a new version that passes both rules.
* To disable compatibility checks for this artifact only, configure a `COMPATIBILITY` rule set to `NONE` on the artifact. The artifact-specific rule then overrides the group rule, and {registry} accepts the previously rejected content.

You can configure group-specific and artifact-specific rules using the {registry} web console or REST API.

[id="registry-rules-config-global_{context}"]
== Default global rule configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Administrators can configure global rules in several ways.

* Use the `admin/rules` operations in the REST API
* Use the {registry} web console
* Set default global rules using {registry} application properties

Administrators can configure {registry} at the application level to enable or disable global rules. You can configure default global rules at installation time without post-install configuration using the following application property format:

----
apicurio.rules.global.<ruleName>
----

The following rule names are currently supported:

* `compatibility`
* `validity`
* `integrity`

The value of the application property must be a valid configuration option that is specific to the rule being
configured.

NOTE: You can configure these application properties as Java system properties or include them in the Quarkus
`application.properties` file. For more details, see the https://quarkus.io/guides/config#overriding-properties-at-runtime[Quarkus documentation].
