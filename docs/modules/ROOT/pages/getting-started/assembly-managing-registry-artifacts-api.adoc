[id="managing-artifacts-using-rest-api_{context}"]
== Managing schema and API artifacts using {registry} REST API commands

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Use the Core Registry API v3 to add and retrieve a schema artifact in {registry}.

.Prerequisites

* {registry} is installed and running in your environment.

.Procedure

. Add an artifact to {registry} using the `/groups/\{groupId\}/artifacts` operation. The following example `curl` command adds a schema artifact for a share price application:
+
[source,bash]
----
$ curl -X POST MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-raw '{
    "artifactId": "share-price",
    "artifactType": "AVRO",
    "firstVersion": {
        "content": {
            "content": "{\"type\":\"record\",\"name\":\" p\",\"namespace\":\"com.example\", \"fields\":[{\"name\":\"symbol\",\"type\":\"string\"},{\"name\":\"price\",\"type\":\"string\"}]}",
            "contentType": "application/json"
        }
    }
}'
----
+
* This example adds an Apache Avro schema artifact with an artifact ID of `share-price`. If you do not specify a unique artifact ID, {registry} generates one automatically as a UUID.
* `MY-REGISTRY-URL` is the
hostname on which {registry} is deployed. For example: `\http://localhost:8080`.
* This example specifies a group ID of `my-group` in the API path. If you do not specify a unique group ID, you must specify `../groups/default` in the API path.

. Verify that the response includes the expected JSON body to confirm that the artifact was added. For example:
+
[source,bash]
----
{"artifact":{"owner":"","createdOn":"2024-09-26T17:24:21Z","modifiedBy":"","modifiedOn":"2024-09-26T17:24:21Z","artifactType":"AVRO","groupId":"my-group","artifactId":"share-price"},"version":{"version":"1","owner":"","createdOn":"2024-09-26T17:24:21Z","artifactType":"AVRO","globalId":2,"state":"ENABLED","groupId":"my-group","contentId":2,"artifactId":"share-price"}}
----
+
* You did not specify a version when adding the artifact, so the default version `1` is created automatically.
* This was the second artifact added to {registry}, so the global ID and content ID have a value of `2`.
. Retrieve the artifact version content from {registry} using its artifact ID in the API path. In this example, the specified ID is `share-price`:
+
[source,bash]
----
$ curl -H "Authorization: Bearer $ACCESS_TOKEN" \
 MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts/share-price/versions/1/content
 {"type":"record","name":"price","namespace":"com.example",
  "fields":[{"name":"symbol","type":"string"},{"name":"price","type":"string"}]}
----

.Additional resources

== Managing schema and API artifact versions using {registry} REST API commands

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
If you do not specify an artifact version number when adding schema and API artifacts using the Core Registry API v3, {registry} generates a version number automatically. The default version when creating a new artifact is `1`.

{registry} also supports custom versioning where you can specify a version number when creating the artifact or artifact version. Specifying a custom version value overrides the default version normally assigned when creating an artifact or artifact version. You can then use this version value when running REST API operations that require a version number.

Use the Core Registry API v3 to add and retrieve a custom Apache Avro schema version in {registry}. You can specify custom version numbers to create artifacts, or to add artifact versions.

.Prerequisites

* {registry} is installed and running in your environment.

.Procedure

. Add an artifact version in the registry using the `/groups/\{groupId\}/artifacts` operation. The following example `curl` command adds an artifact for a share price application:
+
[source,bash]
----
$ curl -X POST MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-raw '{
    "artifactId": "my-share-price",
    "artifactType": "AVRO",
    "firstVersion": {
        "version": "1.1.1",
        "content": {
            "content": "{\"type\":\"record\",\"name\":\" p\",\"namespace\":\"com.example\", \"fields\":[{\"name\":\"symbol\",\"type\":\"string\"},{\"name\":\"price\",\"type\":\"string\"}]}",
            "contentType": "application/json"
        }
    }
}'
----
+
* This example adds an Avro schema artifact with an artifact ID of `my-share-price` and version of `1.1.1`. If you do not specify a version, {registry} automatically generates a default version of `1`.
* `MY-REGISTRY-URL` is the
hostname on which {registry} is deployed. For example: `\http://localhost:8080`.
* This example specifies a group ID of `my-group` in the API path. If you do not specify a unique group ID, you must specify `../groups/default` in the API path.

. Verify that the response includes the expected JSON body to confirm that the custom artifact version was added. For example:
+
[source,bash]
----
{"artifact":{"owner":"","createdOn":"2024-09-26T17:06:21Z","modifiedBy":"","modifiedOn":"2024-09-26T17:06:21Z","artifactType":"AVRO","groupId":"my-group","artifactId":"my-share-price"},"version":{"version":"1.1.1","owner":"","createdOn":"2024-09-26T17:06:21Z","artifactType":"AVRO","globalId":4,"state":"ENABLED","groupId":"my-group","contentId":4,"artifactId":"my-share-price"}}
----
* You specified a custom version of `1.1.1` when adding the artifact.
* This was the fourth artifact added to the registry, so the global ID and content ID have a value of `4`.

. Retrieve the artifact content from the registry using its artifact ID and version in the API path. In this example, the specified ID is `my-share-price` and the version is `1.1.1`:
+
[source,bash]
----
$ curl -H "Authorization: Bearer $ACCESS_TOKEN" \
    MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts/my-share-price/versions/1.1.1/content
{"type":"record","name":"price","namespace":"com.example",
  "fields":[{"name":"symbol","type":"string"},{"name":"price","type":"string"}]}
----

[id="registering-base64-content-using-rest-api_{context}"]
== Registering base64-encoded content using the REST API

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can send UTF-8 schema or API content as base64 in a JSON request to avoid escaping quotation marks and line breaks in the content.
Set `encoding` to `base64` in the `VersionContent` object.
{registry} decodes the content before processing it.

.Prerequisites
* {registry} is running, and you have permission to create artifacts in `my-group`.
* The `my-group` group exists.
* You have installed `curl`, `base64`, and `jq`.
* The `schema.json` file contains an Apache Avro schema.
* The `REGISTRY_URL` environment variable contains the registry URL, and `ACCESS_TOKEN` contains a valid access token if authentication is enabled.

.Procedure
. Create the request body from your schema file:
+
[source,bash]
----
$ base64 < schema.json | tr -d '\r\n' > schema.base64
$ jq -n --rawfile content schema.base64 '{
    artifactId: "encoded-schema",
    artifactType: "AVRO",
    firstVersion: {
        version: "1.0.0",
        content: {
            content: $content,
            contentType: "application/json",
            encoding: "base64"
        }
    }
}' > request.json
----
+
`contentType` describes the decoded schema, not the base64 text.
The `encoding` value is case-sensitive.
Omit `encoding` when sending unencoded content.
. Register the artifact:
+
[source,bash]
----
$ curl --fail-with-body -X POST \
  "$REGISTRY_URL/apis/registry/v3/groups/my-group/artifacts" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-binary @request.json
----
+
You can also set `encoding` in the `content` object when creating a version of an existing artifact.
Invalid base64 content returns HTTP `400`.

.Verification
* Retrieve the version content and confirm that it contains the decoded schema:
+
[source,bash]
----
$ curl --fail-with-body \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  "$REGISTRY_URL/apis/registry/v3/groups/my-group/artifacts/encoded-schema/versions/1.0.0/content"
----

[id="managing-artifact-references-using-rest-api_{context}"]
== Managing schema and API artifact references using {registry} REST API commands

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Some {registry} artifact types can include _artifact references_ from one artifact file to another. You can create efficiencies by defining reusable schema or API artifacts, and then referencing them from multiple locations in artifact references.

The following artifact types support artifact references:

* Apache Avro
* Google Protobuf
* JSON Schema
* OpenAPI
* AsyncAPI
* XML Schema (XSD)
* WSDL (1.1 and 2.0)

For XSD and WSDL artifacts, the reference name must equal the literal value of the `schemaLocation`
attribute (`xs:import`, `xs:include`, `xs:redefine`, and `xs:override`, including schemas embedded in WSDL
`types`) or the `location` attribute (`wsdl:import`, and WSDL 2.0 `import` and `include`).
An `xs:import` element that specifies only a `namespace`, without a `schemaLocation`, does not require a
reference mapping.

For the full list of artifact types that support references, and what each type supports, see
ifndef::service-registry-downstream[]
xref:getting-started/assembly-artifact-reference.adoc#registry-artifact-type-reference-support_{context}[Artifact reference support by type].
endif::[]
ifdef::service-registry-downstream[]
xref:registry-artifact-type-reference-support_{context}[].
endif::[]

Use the Core Registry API v3 to add and retrieve an artifact reference in {registry}.

This example first creates a schema artifact named `ItemId`:

**ItemId schema**

[source,json]
----
{
    "namespace":"com.example.common",
    "name":"ItemId",
    "type":"record",
    "fields":[
        {
            "name":"id",
            "type":"int"
        }
    ]
}
----

This example then creates a schema artifact named `Item`, which includes a reference to the nested `ItemId` artifact.

**Item schema with nested ItemId schema**

[source,json]
----
{
    "namespace":"com.example.common",
    "name":"Item",
    "type":"record",
    "fields":[
        {
            "name":"itemId",
            "type":"com.example.common.ItemId"
        }
    ]
}
----

**Dereference**

In some situations, having an artifact's content with the referenced content inlined might be helpful. For those situations, the Core Registry API v3 supports the _references parameter_ in certain operations.

Support for `DEREFERENCE` and `REWRITE` varies by artifact type. For the types that support each value, see
ifndef::service-registry-downstream[]
xref:getting-started/assembly-artifact-reference.adoc#registry-artifact-type-reference-support_{context}[Artifact reference support by type].
endif::[]
ifdef::service-registry-downstream[]
xref:registry-artifact-type-reference-support_{context}[].
endif::[]
`DEREFERENCE` resolves references transitively. If the reference graph is deeper than `apicurio.storage.references.max-depth` (default `100`), the request returns HTTP `409`.

NOTE: For Avro and Protobuf artifacts, requesting `references=REWRITE` returns HTTP `400`
(`DereferencingNotSupportedException`).
For XSD and WSDL artifacts, requesting `references=DEREFERENCE` returns HTTP `400`
(`DereferencingNotSupportedException`). For those types, `REWRITE` replaces each mapped `schemaLocation` or
`location` value with the {registry} content URL of the referenced artifact.

.Prerequisites

* {registry} is installed and running in your environment.

.Procedure
. Add the `ItemId` schema artifact that you want to create the nested artifact reference to using the `/groups/\{groupId\}/artifacts` operation:
+
[source,bash]
----
$ curl -X POST MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts \
   -H "Content-Type: application/json" \
   -H "Authorization: Bearer $ACCESS_TOKEN" \
   --data '{"artifactId":"ItemId","artifactType":"AVRO","firstVersion":{"version":"1.0.0","content":{"content":"{\"namespace\":\"com.example.common\",\"name\":\"ItemId\",\"type\":\"record\",\"fields\":[{\"name\":\"id\",\"type\":\"int\"}]}","contentType":"application/json"}}}'
----
+
* This example adds an Avro schema artifact with an artifact ID of `ItemId`. If you do not specify a unique artifact ID, {registry} generates one automatically as a UUID.
* `MY-REGISTRY-URL` is the
hostname on which {registry} is deployed. For example: `\http://localhost:8080`.
* This example specifies a group ID of `my-group` in the API path. If you do not specify a unique group ID, you must specify `../groups/default` in the API path.

. Verify that the response includes the expected JSON body to confirm that the artifact was added. For example:
+
[source,bash]
----
{"artifact":{"owner":"","createdOn":"2024-09-26T16:27:38Z","modifiedBy":"","modifiedOn":"2024-09-26T16:27:38Z","artifactType":"AVRO","groupId":"my-group","artifactId":"ItemId"},"version":{"version":"1.0.0","owner":"","createdOn":"2024-09-26T16:27:38Z","artifactType":"AVRO","globalId":2,"state":"ENABLED","groupId":"my-group","contentId":2,"artifactId":"ItemId"}}
----

. Optional: Before you register the `Item` schema, use the `/content/references` operation to find the reference names that you must map:
+
[source,bash]
----
$ curl -X POST "MY-REGISTRY-URL/apis/registry/v3/content/references?artifactType=AVRO" \
   -H "Content-Type: application/json" \
   -H "Authorization: Bearer $ACCESS_TOKEN" \
   --data '{"content":"{\"namespace\":\"com.example.common\",\"name\":\"Item\",\"type\":\"record\",\"fields\":[{\"name\":\"itemId\",\"type\":\"com.example.common.ItemId\"}]}","contentType":"application/json"}'
----
+
The response lists each reference found in the content, with only the `name` field set. For this schema, the name is `com.example.common.ItemId`. If you omit the `artifactType` parameter, {registry} detects the type from the content.

. Add the `Item` schema artifact that includes the artifact reference to the `ItemId` schema using the `/groups/\{groupId\}/artifacts` operation:
+
[source,bash]
----
$ curl -X POST MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts \
-H 'Content-Type: application/json' \
-H "Authorization: Bearer $ACCESS_TOKEN" \
--data-raw '{
	"artifactId": "Item",
	"artifactType": "AVRO",
	"firstVersion": {
		"version": "1.0.0",
		"content": {
			"content": "{\"namespace\":\"com.example.common\",\"name\":\"Item\",\"type\":\"record\",\"fields\":[{\"name\":\"itemId\",\"type\":\"com.example.common.ItemId\"}]}",
			"contentType": "application/json",
			"references": [
				{
					"name": "com.example.common.ItemId",
					"groupId": "my-group",
					"artifactId": "ItemId",
					"version": "1.0.0"
				}
			]
		}
	}
}'
----

. Verify that the response includes the expected JSON body to confirm that the artifact was created with the reference. For example:
+
[source,bash]
----
{"artifact":{"owner":"","createdOn":"2024-09-26T16:28:45Z","modifiedBy":"","modifiedOn":"2024-09-26T16:28:45Z","artifactType":"AVRO","groupId":"my-group","artifactId":"Item"},"version":{"version":"1.0.0","owner":"","createdOn":"2024-09-26T16:28:45Z","artifactType":"AVRO","globalId":3,"state":"ENABLED","groupId":"my-group","contentId":3,"artifactId":"Item"}}
----

. Retrieve the artifact reference from {registry} by specifying the coordinates of the artifact that includes the reference:
+
[source,bash]
----
$ curl -H "Authorization: Bearer $ACCESS_TOKEN" MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts/Item/versions/1.0.0/references
----

. Verify that the response includes the expected JSON body for this artifact reference. For example:
+
[source,bash]
----
[{"groupId":"my-group","artifactId":"ItemId","version":"1.0.0","name":"com.example.common.ItemId"}]
----

. Optional: To list the versions that reference a version instead, add the `refType=INBOUND` query parameter. The following request lists the versions that reference `ItemId` version `1.0.0`, including the `Item` artifact that you created:
+
[source,bash]
----
$ curl -H "Authorization: Bearer $ACCESS_TOKEN" "MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts/ItemId/versions/1.0.0/references?refType=INBOUND"
----

. Retrieve the dereferenced (inlined) schema content:
+
[source,bash]
----
$ curl -H "Authorization: Bearer $ACCESS_TOKEN" MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts/Item/versions/1.0.0/content?references=DEREFERENCE
----

. Verify that the response includes the expected JSON body for this artifact content with the references inlined. For example:
+
[source,bash]
----
{"type":"record","name":"Item","namespace":"com.example.common","fields":[{"name":"itemId","type":{"type":"record","name":"ItemId","fields":[{"name":"id","type":"int"}]}}]}
----
+
For the artifact types that support `references=DEREFERENCE`, see
ifndef::service-registry-downstream[]
xref:getting-started/assembly-artifact-reference.adoc#registry-artifact-type-reference-support_{context}[Artifact reference support by type].
endif::[]
ifdef::service-registry-downstream[]
xref:registry-artifact-type-reference-support_{context}[].
endif::[]
For XSD and WSDL artifacts, dereferencing returns HTTP `400`.
+
NOTE: For Protobuf artifacts, dereferencing content is supported only when all the schemas belong to the same package.
+
NOTE: {registry} stores circular references between artifact versions. Reference resolution stops at a version that is already in the graph. The reference graph operation reports cycles in the `metadata.hasCycles` field. To reject circular references when you create a version, set the `INTEGRITY` rule to `NO_CIRCULAR_REFERENCES` or `FULL`.

[id="matching-references-using-rest-api_{context}"]
== Matching references to existing artifacts

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Instead of listing every reference mapping yourself, you can ask {registry} to match the references found in
the content to artifacts that already exist. Set `autoReferences` to `true` in the version that you create,
either in `firstVersion` when you create an artifact, or in the request body when you create an artifact
version. The default is `false`. The property applies only to the request and is not stored.

{registry} matches only in the group of the artifact that you create (and, for Avro, in the group named after
the namespace of the reference):

.Reference matching rules
[%header,cols="1,3"]
|===
|Reference in the content
|Matching order

|Avro full name, for example `com.example.common.ItemId`
|. An artifact whose ID is the full name in the target group.
. An artifact in the group named after the namespace (`com.example.common`) whose ID is the simple name
(`ItemId`).
. A single artifact in the target group whose structure index has the same name and namespace (record, enum,
or fixed), confirmed by the full name in the content of its latest version.

|JSON Schema absolute `$id` (for example `https://example.com/address.json`)
|A single JSON Schema artifact in the target group whose latest version has exactly that `$id` (case-sensitive),
found through the structure index. Any `#` fragment is ignored. Absolute URIs are matched only for JSON Schema.

|Relative path (for example `./common/address.json`)
|. An artifact whose ID is the normalized path (`common/address.json`).
. An artifact whose ID is the path exactly as written in the content.
|===

Each matched reference is pinned to the version that is currently the latest on the `latest` branch of the
matched artifact; later versions of that artifact do not change the reference. When matching checks the
content of a candidate, the version whose content was checked is the version that is pinned.
Integrity rules, such as `ALL_REFS_MAPPED`, evaluate the matched references together with the references that
you list explicitly.
References that you list explicitly in `references` take precedence and are not matched again. An explicit
reference also covers every reference in the content to the same resource, ignoring any `#` fragment: for
example, an explicit `money.json` covers both `money.json#/$defs/A` and `money.json#/$defs/B`.
Artifacts that you are not permitted to read are treated as not found.
Matching also works with `dryRun=true` and with the `ifExists` parameter. With
`ifExists=FIND_OR_CREATE_VERSION`, an existing version is returned only if both its content and its references
are the same. If a matched artifact has a new latest version since the existing version was created, the
references differ, so {registry} creates a new version that references the new latest version.

If a structure index search finds more candidates than {registry} can confirm, the reference is reported as
having too many candidates instead of being matched. Provide an explicit reference in that case.

If any reference has no match, or matches more than one artifact, {registry} stores nothing and returns a
rule violation error. The status is `400`, or `409` when `apicurio.rest.legacy-error-codes.enabled` is set to
`true`.

.Prerequisites

* {registry} is installed and running in your environment.
* The `ItemId` schema artifact exists in the `my-group` group, as created in
ifndef::service-registry-downstream[]
xref:getting-started/assembly-managing-registry-artifacts-api.adoc#managing-artifact-references-using-rest-api_{context}[Managing schema and API artifact references using {registry} REST API commands].
endif::[]
ifdef::service-registry-downstream[]
xref:managing-artifact-references-using-rest-api_{context}[].
endif::[]

.Procedure
. Create the `Item` schema artifact without listing its references, and set `autoReferences`:
+
[source,bash]
----
$ curl -X POST MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts \
   -H "Content-Type: application/json" \
   -H "Authorization: Bearer $ACCESS_TOKEN" \
   --data '{"artifactId":"Item","artifactType":"AVRO","firstVersion":{"autoReferences":true,"content":{"content":"{\"namespace\":\"com.example.common\",\"name\":\"Item\",\"type\":\"record\",\"fields\":[{\"name\":\"itemId\",\"type\":\"com.example.common.ItemId\"}]}","contentType":"application/json"}}}'
----

. Verify the stored references:
+
[source,bash]
----
$ curl -H "Authorization: Bearer $ACCESS_TOKEN" MY-REGISTRY-URL/apis/registry/v3/groups/my-group/artifacts/Item/versions/branch=latest/references
----
+
[source,bash]
----
[{"groupId":"my-group","artifactId":"ItemId","version":"1.0.0","name":"com.example.common.ItemId"}]
----

. If a reference cannot be matched, the response lists every problem, sorted by reference name. For example:
+
[source,json]
----
{
  "name": "ReferenceAutoMatchException",
  "title": "Some references could not be matched to existing artifacts.",
  "status": 400,
  "causes": [
    {"context": "com.example.common.ItemId", "description": "No matching artifact found in group 'my-group'."}
  ]
}
----
+
An ambiguous reference has a description such as `Ambiguous: matches my-group/Address, my-group/com.example.Address.`

// proc-inspecting-reference-graphs-using-rest-api
[id="inspecting-reference-graphs-using-rest-api_{context}"]
== Inspecting artifact reference graphs using the REST API

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can retrieve a reference graph to inspect the dependencies of an artifact version and the versions that depend on it.
The graph includes indirect references, node and edge counts, and cycle information.

.Prerequisites
* {registry} is running, and the artifact version exists.
* You have permission to read the artifact.
* The `REGISTRY_URL` environment variable contains the registry URL, and `ACCESS_TOKEN` contains a valid access token if authentication is enabled.

.Procedure
* Request the reference graph for an artifact version:
+
[source,bash]
----
$ curl --fail-with-body \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  "$REGISTRY_URL/apis/registry/v3/groups/my-group/artifacts/Item/versions/1.0.0/references/graph?direction=BOTH&depth=3"
----
+
The `direction` parameter accepts the following values:
+
** `OUTBOUND`: Versions that the requested version references. This is the default.
** `INBOUND`: Versions that reference the requested version.
** `BOTH`: References in both directions.
+
The default `depth` is `3`.
Use `depth=1` for direct references or `depth=0` for unlimited traversal.
A larger graph can take longer to retrieve.

.Verification
* Inspect the response fields:
+
** `root` identifies the requested artifact version.
** `nodes` lists artifact versions, including the root, with their group ID, artifact ID, and version.
** `edges` links `sourceNodeId` to `targetNodeId` and includes the reference `name`.
** `metadata` contains `totalNodes`, `totalEdges`, `maxDepth`, and `hasCycles`.
+
The graph reports the references traversed within the requested depth.
A `hasCycles` value of `false` does not rule out cycles beyond that depth.
Cycle detection compares artifacts, not versions. A chain that passes through two versions of the same artifact also counts as a cycle.

[id="exporting-protobuf-using-rest-api_{context}"]
== Exporting a Protobuf schema with its dependencies

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can download a Protobuf artifact version and its direct and indirect dependencies as a ZIP archive for use with the `protoc` compiler.
{registry} organizes the files by package name and rewrites import statements to match those paths.

.Prerequisites
* {registry} contains the Protobuf artifact version and all its registered references.
* You have permission to read the artifact.
* You have installed `curl` and `unzip`.
* The `REGISTRY_URL` environment variable contains the registry URL, and `ACCESS_TOKEN` contains a valid access token if authentication is enabled.

.Procedure
. Download the schema package:
+
[source,bash]
----
$ curl --fail-with-body \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  "$REGISTRY_URL/apis/registry/v3/groups/my-group/artifacts/my-schema/versions/1.0.0/export" \
  --output my-schema-1.0.0.zip
----
+
This operation supports only `PROTOBUF` artifacts.
For another artifact type, the server returns HTTP `400`.
The registry resolves registered references while it streams the ZIP response.
If a reference cannot be resolved, the download ends early with a truncated or invalid archive rather than an error status, so verify that the archive extracts cleanly.
. Extract the archive:
+
[source,bash]
----
$ unzip my-schema-1.0.0.zip -d my-schema
----
+
For example, a schema with artifact ID `my-schema` and package `com.example` appears at `com/example/my-schema.proto`.
The archive contains separate files for dependencies, including schemas in different packages.

.Verification
* List the archive entries and check that the schema and its dependencies are present:
+
[source,bash]
----
$ unzip -l my-schema-1.0.0.zip
----
+
This archive contains Protobuf source files.
Use the administrative export operation to create an archive for the registry import operation.

== Searching for schema and API artifacts using {registry} REST API commands

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can use the {registry} REST API search endpoints to find artifacts, versions, and groups. Search filters match exactly by default, and you can use the `*` wildcard for pattern matching.

.Procedure
. Search for artifacts with an exact filter value:
+
[source,bash]
----
$ curl "http://localhost:8080/apis/registry/v3/search/artifacts?artifactId=my-artifact"
----
. To match patterns, include the `*` wildcard anywhere in the `groupId`, `artifactId`, or `labels` filter values:
+
[source,bash]
----
$ curl "http://localhost:8080/apis/registry/v3/search/artifacts?artifactId=my-*"
$ curl "http://localhost:8080/apis/registry/v3/search/artifacts?labels=env*:prod*"
----
+
The `*` character is the only supported wildcard.
. To search by name, use an exact value or a leading or trailing `*` wildcard. The `name` filter matches against the artifact name or the artifact ID, and behaves the same on the artifact and version search endpoints:
+
[source,bash]
----
$ curl "http://localhost:8080/apis/registry/v3/search/versions?name=*payment*"
----
+
The `description` filter is different: it always matches substrings.
. To ignore letter case in the `name` filter, set the `nameCaseInsensitive` parameter to `true`. The parameter defaults to `false` and applies to the artifact and version search endpoints:
+
[source,bash]
----
$ curl "http://localhost:8080/apis/registry/v3/search/artifacts?name=*Payment*&nameCaseInsensitive=true"
----
. Optional: To improve performance on large result sets, set the `skipCount` parameter to `true`. The registry then skips the expensive total count query, and the `count` field in the response is `0`:
+
[source,bash]
----
$ curl "http://localhost:8080/apis/registry/v3/search/artifacts?limit=50&skipCount=true"
----
+
The `skipCount` parameter is available on the artifact and version search endpoints, and on the endpoints that list the artifacts of a group and the versions of an artifact.

[id="canonicalizing-content-using-rest-api_{context}"]
== Canonicalizing content using the {registry} REST API

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can use the {registry} REST API to convert schema or API content to its canonical form without storing it. Canonical content is useful for comparing schemas independently of formatting differences.

.Procedure
. Send the content to the canonicalization endpoint. The `artifactType` query parameter is required:
+
[source,bash]
----
$ curl -X POST -H "Content-Type: application/json" --data @schema.json \
  "http://localhost:8080/apis/registry/v3/content/canonicalize?artifactType=AVRO"
----
+
The response body contains the canonicalized content. An empty request body or an unknown artifact type produces a `400` error response.
. To retrieve the canonical form of a stored artifact version with its references resolved, use the `canonical` parameter on the version content endpoint instead:
+
[source,bash]
----
$ curl "http://localhost:8080/apis/registry/v3/groups/my-group/artifacts/my-artifact/versions/1.0.0/content?canonical=true"
----
+
[NOTE]
====
The canonicalization endpoint operates on the content exactly as provided and does not resolve external references. To canonicalize content that uses references, store the content first and use the `canonical` parameter.
====

[id="exporting-importing-using-rest-api_{context}"]
== Exporting and importing registry data using {registry} REST API commands

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
As an administrator, you can use the Core Registry API v3 to export data from one {registry} instance and import into another {registry} instance, so you can migrate data between different instances.

The export operation creates a ZIP archive containing registry data and metadata.
By default, it includes all groups and global rules.
You can limit the export to a single group by specifying the `groupId` query parameter.

.Prerequisites

* {registry} is installed and running in your environment.
* {registry} instances have been created:
** The source instance that you want to export data from contains at least one schema or API artifact.
** The target instance that you want to import data into is empty to preserve unique IDs.

.Procedure
. Export the {registry} data from your existing source {registry} instance:
+
[source,bash]
----
$ curl MY-REGISTRY-URL/apis/registry/v3/admin/export \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --output my-registry-data.zip
----
+
`MY-REGISTRY-URL` is the
hostname on which the source {registry} is deployed. For example: `\http://my-source-registry:8080`.
+
To export only one group, add the `groupId` query parameter instead:
+
[source,bash]
----
$ curl --fail-with-body --get MY-REGISTRY-URL/apis/registry/v3/admin/export \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-urlencode "groupId=my-group" \
  --output my-group-data.zip
----
+
A group export excludes global rules and artifacts in other groups.
If the group's artifacts reference artifacts in another group, include those dependencies in your migration plan.
The specified group must exist.

. Import the registry data into your target {registry} instance:
+
[source,bash]
----
$ curl -X POST "MY-REGISTRY-URL/apis/registry/v3/admin/import" \
  -H "Content-Type: application/zip" -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-binary @my-registry-data.zip
----
+
`MY-REGISTRY-URL` is the
hostname on which the target {registry} is deployed. For example: `\http://my-target-registry:8080`.
+
When importing a group export, use the file name `my-group-data.zip` instead.
By default, the target registry must be empty, and the import preserves global IDs and content IDs.
To import into a nonempty registry, set `requireEmptyRegistry=false` and set both `X-Registry-Preserve-GlobalId` and `X-Registry-Preserve-ContentId` headers to `false` to generate IDs on the target.
These options do not resolve conflicts between existing artifact coordinates.

.Verification
* Retrieve the imported artifacts and versions from the target registry and compare their content with the source.
Check the server log for failed or skipped entities because an import can skip an individual entity without failing the entire request.

.Additional resources

[id="registry-import-archive-format_{context}"]
== Registry import archive format

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The administrative import operation accepts a ZIP archive of registry entities, including metadata and schema content.
An archive of schema files alone does not contain the metadata required for import.
You can use the version 3 archive format to prepare data outside {registry}.

.Archive entries
[cols="2,3",options="header"]
|===
|Entry pattern |Purpose
|`manifest-<timestamp>.Manifest.json`
|Export format and source system metadata. The archive must contain one manifest.
|`content/<hash>.Content.json`
|Content ID, content hash, canonical hash or artifact type, media type, and serialized references.
|`content/<hash>.Content.data`
|Raw schema or API bytes. Each content metadata file has a matching data file with the same name before the extension.
|`groups/<groupId>.Group.json`
|Group metadata.
|`groups/<groupId>/artifacts/<artifactId>/MetaData.Artifact.json`
|Artifact metadata, including the artifact type.
|`groups/<groupId>/artifacts/<artifactId>/versions/<version>.ArtifactVersion.json`
|Version metadata, including its global ID and the content ID that links it to a content entry.
|`groups/<groupId>/artifacts/<artifactId>/branches/<branchId>.Branch.json`
|Branch metadata and an ordered list of version strings.
|`rules/<ruleType>.GlobalRule.json`
|A global rule. Group exports exclude these entries.
|`groups/<groupId>/rules/<ruleType>.GroupRule.json`
|A group rule.
|`groups/<groupId>/artifacts/<artifactId>/rules/<ruleType>.ArtifactRule.json`
|An artifact rule.
|`groups/<groupId>/artifacts/<artifactId>/contract-rules/<name>.ContractRule.json`
|A contract rule. Each entry has a distinct name.
|`comments/<name>.Comment.json`
|A comment associated with a version's global ID.
|===

The entity type suffix, such as `.ArtifactVersion.json`, is case-sensitive.
The importer reads entity fields from the JSON body and processes entities in dependency order, independently of their order in the archive.
The default group uses `default` in archive paths and `null` for the `groupId` field in entity JSON.

.Core entity fields
[cols="1,3",options="header"]
|===
|Entity |Fields and relationships
|Manifest
|`exportVersion` identifies the archive format, for example, `3.0`. `systemVersion` identifies the source registry version, for example, `3.0.0`. Other fields include `systemName`, `systemDescription`, `exportedOn`, `exportedBy`, and `dbVersion`.
|Content
|`contentId` identifies the content entry. `contentType` describes the raw bytes. `contentHash` is the SHA-256 hash of the bytes followed by the UTF-8 `serializedReferences` string when references exist. The registry canonical hash uses canonical content bytes followed by the serialized references when present. For content without references, you can omit `canonicalHash` and supply `artifactType` so that the importer computes the canonical hash.
|Group and artifact
|`groupId` identifies the group. An artifact also has `artifactId` and `artifactType`. Metadata fields include `owner`, `createdOn`, `modifiedBy`, `modifiedOn`, `description`, and `labels`. Artifact metadata can also include `name`.
|Version
|`groupId`, `artifactId`, and `version` identify the version. `globalId` is unique across versions. `contentId` refers to a content entry. `versionOrder` records the numeric creation order within the artifact. `state` contains a version state such as `ENABLED`. Version metadata can also include `name`, `description`, `labels`, ownership, and timestamps.
|Branch
|`groupId`, `artifactId`, and `branchId` identify the branch. `versions` contains version strings in branch order. `systemDefined` identifies system branches, including `latest`. Ownership and timestamps describe the branch.
|===

Entity timestamps such as `createdOn` and `modifiedOn` use milliseconds since the Unix epoch.
The `serializedReferences` field contains a JSON-encoded string, not a JSON array.
Each reference includes `name`, `groupId`, `artifactId`, and `version`.
For content without references, omit this field or use `null`.

For content with references, always supply a `canonicalHash` that matches the registry's canonicalization and reference serialization. Do not rely on the automatic computation: the importer computes the hash from the canonical content bytes only, without appending the serialized references, so the computed value never matches the hash that the registry computes when it registers content with references. A registry export includes the stored canonical hashes.

An import preserves IDs by default.
The archive must use consistent content IDs, global IDs, and artifact coordinates across related entries, even when the import generates new IDs.
Branches require explicit branch entries; importing versions alone does not populate the `latest` branch.

[id="preparing-registry-import-archive_{context}"]
== Preparing a registry import archive from a schema file

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can build a version 3 import archive from a local schema without first exporting data from a registry.
This example creates one Apache Avro artifact, one version, and a `latest` branch.

.Prerequisites
* You have installed Python 3 and `curl`.
* The `schema.json` file contains a valid Apache Avro schema without external references.
* The target registry is empty, and you have administrator access.
* The `REGISTRY_URL` environment variable contains the target registry URL, and `ACCESS_TOKEN` contains a valid access token if authentication is enabled.

.Procedure
. Save the following script as `create-import.py`:
+
[source,python]
----
import hashlib
import json
import time
import zipfile
from pathlib import Path

content = Path("schema.json").read_bytes()
content_hash = hashlib.sha256(content).hexdigest()
timestamp = int(time.time() * 1000)
metadata = {
    "owner": "import-user",
    "createdOn": timestamp,
    "modifiedBy": "import-user",
    "modifiedOn": timestamp,
}
coordinates = {"groupId": "import-example", "artifactId": "my-schema"}
artifact_path = "groups/import-example/artifacts/my-schema"
entries = {
    "manifest.Manifest.json": {
        "exportVersion": "3.0",
        "systemVersion": "3.0.0",
        "systemName": "Offline import",
        "exportedOn": timestamp,
    },
    f"content/{content_hash}.Content.json": {
        "contentId": 1,
        "contentHash": content_hash,
        "contentType": "application/json",
        "artifactType": "AVRO",
    },
    "groups/import-example.Group.json": {
        **metadata, "groupId": "import-example",
    },
    f"{artifact_path}/MetaData.Artifact.json": {
        **metadata, **coordinates, "artifactType": "AVRO",
    },
    f"{artifact_path}/versions/1.0.0.ArtifactVersion.json": {
        **metadata, **coordinates,
        "globalId": 1, "contentId": 1,
        "version": "1.0.0", "versionOrder": 1, "state": "ENABLED",
    },
    f"{artifact_path}/branches/latest.Branch.json": {
        **metadata, **coordinates,
        "branchId": "latest", "systemDefined": True, "versions": ["1.0.0"],
    },
}
with zipfile.ZipFile("registry-import.zip", "w", zipfile.ZIP_DEFLATED) as archive:
    for name, entity in entries.items():
        archive.writestr(name, json.dumps(entity))
    archive.writestr(f"content/{content_hash}.Content.data", content)
----
+
The example uses matching `contentId` values in the content and version entries.
It supplies `artifactType` so that the importer computes the canonical hash.
The manifest identifies version 3 archive data, independently of the target registry's minor version.
. Run the script:
+
[source,bash]
----
$ python3 create-import.py
----
. Import the archive:
+
[source,bash]
----
$ curl --fail-with-body -X POST \
  "$REGISTRY_URL/apis/registry/v3/admin/import" \
  -H "Content-Type: application/zip" \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  --data-binary @registry-import.zip
----

.Verification
* Retrieve the imported version and compare it with `schema.json`:
+
[source,bash]
----
$ curl --fail-with-body \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  "$REGISTRY_URL/apis/registry/v3/groups/import-example/artifacts/my-schema/versions/1.0.0/content"
----
+
Check the server log for import warnings if the artifact, version, or content is missing.
