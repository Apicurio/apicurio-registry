== ApicurioRegistry3 custom resource structure
:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The `ApicurioRegistry3` custom resource defines the desired state of an instance of {registry}. The resource is
organized into three sections under `spec`:

[source,yaml,subs="attributes"]
----
apiVersion: registry.apicur.io/v1
kind: ApicurioRegistry3
metadata:
  name: example-registry
spec:
  app:
    # Configuration for the {registry-app}.
  ui:
    # Configuration for the {registry-ui}.
  consolePlugin:
    # Configuration for the OpenShift Console plugin component.
----

== {registry-app} configuration reference
:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The `spec.app` section configures the backend component, which provides the REST API.

The following fields are available for both `spec.app` and `spec.ui` components:

.Common component fields

[cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`replicas`
|Number of pod replicas for the component
|Integer
|`1`

|`env`
|List of environment variables to pass to the component's container
|Array of EnvVar
|`[]`

|`ingress`
|Ingress configuration for the component
|xref:ingress-spec_{context}[IngressSpec]
|See Ingress configuration reference

|`podTemplateSpec`
|Custom PodTemplateSpec for advanced pod configuration
|PodTemplateSpec
|Operator-generated defaults

|`podDisruptionBudget`
|PodDisruptionBudget configuration
|PodDisruptionSpec
|`{ enabled: true }`

|`autoscaling`
|Horizontal pod autoscaling configuration for the component
|AutoscalingSpec
|`{ enabled: false }`

|`networkPolicy`
|NetworkPolicy configuration
|NetworkPolicySpec
|`{ enabled: true }`

|`host` _(deprecated)_
|Use `ingress.host` instead
|String
|`""`
|===

The top-level `spec.consolePlugin.enabled` field (Boolean, default `false`) controls whether the {operator} deploys the OpenShift Console plugin component.

The following fields are specific to `spec.app`:

.Application-specific fields

[cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`storage`
|Storage configuration for the backend
|xref:storage-spec_{context}[StorageSpec]
|See Storage configuration reference

|`features`
|Feature flags for the backend
|xref:app-features-spec_{context}[AppFeaturesSpec]
|See below

|`auth`
|Authentication and authorization configuration
|xref:auth-spec_{context}[AuthSpec]
|See Authentication and authorization configuration reference

|`tls`
|TLS configuration for the application
|xref:tls-spec_{context}[TLSSpec]
|See below

|`otel`
|OpenTelemetry observability configuration
|xref:otel-spec_{context}[OTelSpec]
|See below

|`searchIndex`
|Elasticsearch-based content search indexing (experimental)
|xref:search-index-spec_{context}[SearchIndexSpec]
|See below

|`sql` _(deprecated)_
|Use `storage.type` and `storage.sql` instead. When this field is set, the operator attempts to move the values to `storage` and updates the custom resource automatically
|DeprecatedSqlSpec
|None

|`kafkasql` _(deprecated)_
|Use `storage.type` and `storage.kafkasql` instead. When this field is set, the operator attempts to move the values to `storage` and updates the custom resource automatically
|DeprecatedKafkasqlSpec
|None
|===

Configure optional features for {registry}:

.AppFeaturesSpec
[id="app-features-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`resourceDeleteEnabled`
|Allow deletion of groups, artifacts, and artifact versions. By default, resources in {registry} are
immutable.
|Boolean
|`false`

|`versionMutabilityEnabled`
|Allow artifact versions in DRAFT state to be mutable. Enabling this also unlocks Studio functionality in the UI.
|Boolean
|`false`
|===

Example:
[source,yaml]
----
spec:
  app:
    features:
      resourceDeleteEnabled: true
      versionMutabilityEnabled: true
----

Configure TLS certificates for the application:

.TLSSpec
[id="tls-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`insecureRequests`
|Controls the plain HTTP port when TLS is configured. `enabled` keeps the HTTP port open, `redirect` keeps the port open but redirects all requests to HTTPS, and `disabled` does not open the HTTP port
|String (`enabled`, `redirect`, `disabled`)
|`enabled`

|`keystoreSecretRef`
|Reference to a Secret containing the keystore (PKCS12 format). Default key: `user.p12`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`keystorePasswordSecretRef`
|Reference to a Secret containing the keystore password. Default key: `user.password`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`truststoreSecretRef`
|Reference to a Secret containing the truststore (PKCS12 format). Default key: `ca.p12`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`truststorePasswordSecretRef`
|Reference to a Secret containing the truststore password. Default key: `ca.password`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None
|===

NOTE: The default keys match the layout of the Secrets that the {kafka-streams} Operator creates for a `KafkaUser` (`user.p12` and `user.password`) and for the cluster CA (`ca.p12` and `ca.password`). With other Secrets, set the `key` explicitly.

Example:
[source,yaml]
----
spec:
  app:
    tls:
      insecureRequests: redirect
      keystoreSecretRef:
        name: registry-tls
        key: keystore.p12
      keystorePasswordSecretRef:
        name: registry-tls
        key: keystore.password
----

Configure OpenTelemetry observability for the application:

.OTelSpec
[id="otel-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`enabled`
|Enable OpenTelemetry. When enabled, the operator sets `QUARKUS_OTEL_SDK_DISABLED=false` so that {registry} exports traces and metrics to an OpenTelemetry collector and correlates logs with traces
|Boolean
|`false`

|`endpoint`
|Endpoint URL of the OpenTelemetry collector, for example `http://otel-collector:4317` for gRPC or `http://otel-collector:4318` for HTTP
|String
|None (application default `http://localhost:4317`)

|`protocol`
|Protocol of the OTLP exporter: `grpc` or `http/protobuf`
|String
|`grpc` (application default)

|`traceSamplingRatio`
|Ratio of traces to sample, between `0.0` and `1.0`. When set, the operator configures the `parentbased_traceidratio` sampler with this ratio. Otherwise, the application default applies: `parentbased_traceidratio` with ratio `0.1`
|Double
|None
|===

Example:
[source,yaml]
----
spec:
  app:
    otel:
      enabled: true
      endpoint: http://otel-collector:4317
      protocol: grpc
      traceSamplingRatio: 0.1
----

== Storage configuration reference
:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The `spec.app.storage` section configures the storage backend for {registry}.

.StorageSpec
[id="storage-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`type`
|Storage type: `<empty>` (embedded H2 database), `postgresql`, `mysql`, `kafkasql`, `kubernetesops`, or `gitops`. When left empty, {registry} uses SQL storage with an embedded H2 database.
|String
|`""` (embedded H2, development only)

|`sql`
|SQL database configuration. Required when `type` is `postgresql` or `mysql`
|xref:sql-spec_{context}[SqlSpec]
|None

|`kafkasql`
|KafkaSQL storage configuration. Required when `type` is `kafkasql`
|xref:kafka-sql-spec_{context}[KafkaSqlSpec]
|None

|`kubernetesops`
|KubernetesOps storage configuration (read-only, experimental). Required when `type` is `kubernetesops`
|xref:kubernetes-ops-spec_{context}[KubernetesOpsSpec]
|None

|`gitops`
|GitOps storage configuration (read-only, experimental). Used when `type` is `gitops`
|xref:git-ops-spec_{context}[GitOpsSpec]
|None
|===

IMPORTANT: The default embedded H2 configuration is not suitable for production environments. Specify a storage type for production use.

Configure SQL database storage (PostgreSQL or MySQL):

.SqlSpec
[id="sql-spec_{context}",cols="1,2,1",options="header"]
|===
|Field
|Description
|Type

|`dataSource`
|Data source configuration
|xref:data-source-spec_{context}[DataSourceSpec]
|===

.DataSourceSpec
[id="data-source-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`url`
|JDBC connection URL. Example: `jdbc:postgresql://postgresql.my-ns.svc:5432/registry`
|String
|None

|`username`
|Database username
|String
|None

|`password`
|Reference to a Secret containing the database password. Default key: `password`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None
|===

Example for PostgreSQL:
[source,yaml]
----
spec:
  app:
    storage:
      type: postgresql
      sql:
        dataSource:
          url: jdbc:postgresql://postgresql.my-project.svc:5432/registry
          username: registry_user
          password:
            name: postgresql-credentials
            key: password
----

Example for MySQL:
[source,yaml]
----
spec:
  app:
    storage:
      type: mysql
      sql:
        dataSource:
          url: jdbc:mysql://mysql.my-project.svc:3306/registry
          username: registry_user
          password:
            name: mysql-credentials
            key: password
----

Configure KafkaSQL storage:

.KafkaSqlSpec
[id="kafka-sql-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`kafkaAccessSecretName`
|Name of a Kubernetes Secret produced by the Strimzi Kafka Access Operator (type `servicebinding.io/kafka`). When set, the operator reads connection details (bootstrap servers, TLS certificates, SASL credentials) from this secret instead of requiring manual configuration. Available starting with {registry} version 3.2.0.
|String
|None

|`bootstrapServers`
|Kafka bootstrap servers address. Required if `kafkaAccessSecretName` is not set.
|String
|None

|`tls`
|TLS configuration for connecting to Kafka
|xref:kafka-sql-tls-spec_{context}[KafkaSqlTLSSpec]
|None

|`auth`
|Authentication configuration for connecting to Kafka
|xref:kafka-sql-auth-spec_{context}[KafkaSqlAuthSpec]
|None
|===

Example:
[source,yaml]
----
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        bootstrapServers: my-cluster-kafka-bootstrap.my-project.svc:9092
----

Example using the Kafka Access Operator (available starting with version 3.2.0):
[source,yaml]
----
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        kafkaAccessSecretName: my-kafka-access
----

.KafkaSqlTLSSpec

|===
|Field
|Description
|Type
|Default

|`keystoreSecretRef`
|Reference to a Secret containing the TLS keystore (PKCS12 format). Default key: `user.p12`
|xref:secret-key-ref_{context}[SecretKeyRef]

|`keystorePasswordSecretRef`
|Reference to a Secret containing the TLS keystore password. Default key: `user.password`

Example with mutual TLS (client certificate authentication):
[source,yaml]
----
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        bootstrapServers: my-cluster-kafka-bootstrap.my-project.svc:9093
        tls:
          keystoreSecretRef:
            name: my-user
          keystorePasswordSecretRef:
            name: my-user
          truststoreSecretRef:
            name: kafka-cluster-ca-cert
          truststorePasswordSecretRef:
            name: kafka-cluster-ca-cert
----

NOTE: Default keys match the secret structure produced by the {kafka-streams} Operator, so you typically only need to specify the secret `name`.

Configure SASL OAuth authentication for KafkaSQL storage:

.KafkaSqlAuthSpec
[id="kafka-sql-auth-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`enabled`
|Enables SASL OAuth authentication. Must be set to `true` for other auth fields to have effect.
|Boolean
|`false`

|`mechanism`
|SASL mechanism. Use `OAUTHBEARER` for OAuth authentication.
|String
|None

|`clientIdRef`
|Reference to a Secret containing the OAuth client ID. Default key: `clientId`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`clientSecretRef`
|Reference to a Secret containing the OAuth client secret. Default key: `clientSecret`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`tokenEndpoint`
|OAuth token endpoint URI
|String
|None

|`loginHandlerClass`
|The login callback handler class for OAuth authentication
|String
|None
|===

Example with OAuth:
[source,yaml]
----
spec:
  app:
    storage:
      type: kafkasql
      kafkasql:
        bootstrapServers: my-cluster-kafka-bootstrap.my-project.svc:9093
        auth:
          enabled: true
          mechanism: OAUTHBEARER
          clientIdRef:
            name: kafka-oauth-credentials
            key: clientId
          clientSecretRef:
            name: kafka-oauth-credentials
            key: clientSecret
          tokenEndpoint: https://identity-server.example.com/token
          loginHandlerClass: io.strimzi.kafka.oauth.client.JaasClientOauthLoginCallbackHandler
----

NOTE: The operator provides first-class support for OAuth (OAUTHBEARER) authentication through the `auth` field. For other SASL mechanisms such as SCRAM-SHA-512, the recommended approach is to use the Strimzi Kafka Access Operator through the `kafkaAccessSecretName` field (available starting with {registry} version 3.2.0). Alternatively, you can use custom environment variables through the `spec.app.env` field to configure the Kafka client properties directly. See the additional resources for available `apicurio.kafkasql.*` configuration properties.

Configure KubernetesOps storage (read-only, experimental). Loads registry data from Kubernetes ConfigMaps:

.KubernetesOpsSpec
[id="kubernetes-ops-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`registryId`
|Unique identifier for this registry instance. Only ConfigMaps with a matching label will be loaded. Required.
|String
|None

|`namespace`
|Kubernetes namespace to watch for ConfigMaps.
|String
|Current namespace

|`refreshEvery`
|Minimum period between polls for ConfigMap changes. Supports duration formats such as `10s`, `1m`, or ISO 8601 `PT10S`. When omitted, the operator does not set the property and the application default applies.
|String
|`10s` (application default `PT10S`)

|`labelRegistryId`
|Label key used to identify ConfigMaps belonging to this registry.
|String
|`apicurio.io/registry-id`

|`watchEnabled`
|Enable Watch API for real-time ConfigMap change detection. Set to `false` to use polling only.
|Boolean
|`true`

|`watchReconnectDelay`
|Base delay before reconnecting after watch failure. Uses exponential backoff up to 5 minutes.
|String
|`10s`
|===

IMPORTANT: KubernetesOps storage is an experimental feature. The operator automatically enables the experimental features gate when this storage type is configured.

Example:
[source,yaml]
----
spec:
  app:
    storage:
      type: kubernetesops
      kubernetesops:
        registryId: my-registry
        namespace: apicurio
----

Example with custom polling and watch settings:
[source,yaml]
----
spec:
  app:
    storage:
      type: kubernetesops
      kubernetesops:
        registryId: my-registry
        namespace: apicurio
        refreshEvery: 10s
        watchEnabled: true
        watchReconnectDelay: 5s
----

NOTE: KubernetesOps storage is read-only. All changes must be made by creating or updating ConfigMaps. For more details on ConfigMap format and RBAC requirements, see the additional resources.

Configure GitOps storage (read-only, experimental). Loads registry data from Git repositories through a sync sidecar container:

.GitOpsSpec
[id="git-ops-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`mode`
|Sync mode. `pull` periodically fetches from the remote repositories. `push` starts an SSH server in the sidecar that accepts `git push`. The operator then creates a Service named `<cr-name>-gitops-ssh-service` on port `2222` and allows that port in the NetworkPolicy of the app component
|String (`pull`, `push`)
|`pull`

|`repos`
|List of Git repositories to sync from. For a single repository, provide a list with one entry
|Array of xref:git-ops-repo-spec_{context}[GitOpsRepoSpec]
|`[]`

|`registryId`
|Registry instance identifier. Only data files that reference this identifier are loaded. When omitted, the operator does not set the property and the application default `main` applies
|String
|None

|`pull`
|SSH Secrets for pull mode
|xref:git-ops-pull-spec_{context}[GitOpsPullSpec]
|None

|`push`
|SSH Secrets for push mode
|xref:git-ops-push-spec_{context}[GitOpsPushSpec]
|None
|===

.GitOpsRepoSpec
[id="git-ops-repo-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`url`
|URL of the remote Git repository, over HTTPS or SSH, for example `https://github.com/my-org/my-schemas.git` or `git@github.com:my-org/my-schemas.git`
|String
|None

|`branch`
|Branch to track
|String
|`main` (application default)

|`dir`
|Directory under the shared `/repos` workspace where the repository is cloned. Required when you configure more than one repository
|String
|`default`
|===

.GitOpsPullSpec
[id="git-ops-pull-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`sshKeys`
|Reference to a Secret containing the SSH private key for authenticating to remote Git servers. Default key: `id_ed25519`. The operator mounts the key with file mode `0400`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`knownHosts`
|Reference to a Secret containing a `known_hosts` file for verifying the host keys of remote Git servers. Default key: `known_hosts`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None
|===

.GitOpsPushSpec
[id="git-ops-push-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`authorizedKeys`
|Reference to a Secret containing the `authorized_keys` file that controls which SSH public keys can push. Default key: `authorized_keys`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None

|`hostKey`
|Reference to a Secret containing a persistent SSH host key for the SSH server of the sidecar, so that the host fingerprint stays stable across pod restarts. Default key: `ssh_host_key`. The operator mounts the key with file mode `0400`
|xref:secret-key-ref_{context}[SecretKeyRef]
|None
|===

IMPORTANT: GitOps storage is an experimental feature. The operator enables the experimental features gate when you configure this storage type.

Example with pull mode over HTTPS:
[source,yaml]
----
spec:
  app:
    storage:
      type: gitops
      gitops:
        registryId: prod
        repos:
          - url: https://github.com/my-org/my-registry-data.git
            branch: main
----

Example with push mode:
[source,yaml]
----
spec:
  app:
    storage:
      type: gitops
      gitops:
        mode: push
        registryId: prod
        push:
          authorizedKeys:
            name: gitops-push-authorized-keys
          hostKey:
            name: gitops-push-host-key
----

NOTE: GitOps storage is read-only. Make all changes through Git. The operator adds the sync sidecar container `apicurio-registry-gitops-sync` and a shared `emptyDir` volume mounted at `/repos` in both containers. To override the sidecar image or add environment variables to the sidecar, use `spec.app.podTemplateSpec` with the container name `apicurio-registry-gitops-sync`. For the repository data format and the sync container, see the additional resources.

The `spec.app.auth` section configures OIDC or Kubernetes-native authentication and role-based authorization.

.AuthSpec
[id="auth-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`enabled`
|Enable authentication
|Boolean
|`false`

|`appClientId`
|OIDC client ID for the backend application
|String
|None

|`uiClientId`
|OIDC client ID for the UI application
|String
|None

|`authServerUrl`
|URL of the identity server (OIDC issuer)
|String
|None

|`redirectUri`
|Redirect URI after successful authentication
|String
|None

|`logoutUrl`
|Redirect URI after logout
|String
|None

|`anonymousReadsEnabled`
|Allow anonymous users to make read-only calls to the REST API
|Boolean
|`false`

|`authz`
|Authorization configuration
|xref:authz-spec_{context}[AuthzSpec]
|See below

|`basicAuth`
|Client credentials basic authentication configuration
|xref:basic-auth-spec_{context}[BasicAuthSpec]
|See below

|`kubernetesAuth`
|Kubernetes-native authentication configuration (experimental). {registry} validates bearer tokens with the Kubernetes TokenReview API
|xref:kubernetes-auth-spec_{context}[KubernetesAuthSpec]
|See below

|xref:auth-tls-spec_{context}[AuthTLSSpec]

[IMPORTANT]
====
Kubernetes-native authentication is an experimental feature. The operator does not enable the experimental features gate for it. Add the `APICURIO_FEATURES_EXPERIMENTAL_ENABLED` environment variable with the value `true` to `spec.app.env`, or the {registry} pod fails at startup.         enabled: true
        apiAudiences: https://kubernetes.default.svc

          adminGroups: cluster-admins
          developerGroups: developers
          readOnlyGroups: viewers

        enabled: true

== Ingress configuration reference
:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The `ingress` section is available for both `spec.app` and `spec.ui` components.

.IngressSpec
[id="ingress-spec_{context}",cols="1,2,1,2",options="header"]
|===
|Field
|Description
|Type
|Default

|`enabled`
|Whether the operator should manage an Ingress resource. Set to `false` to create your own Ingress
|Boolean
|`true`

|`host`
|Hostname for the Ingress. If empty, the operator will not create an Ingress resource
|String
|`""`

|`ingressClassName`
|IngressClass to use for the Ingress resource
|String
|None

|`annotations`
|Additional annotations for the Ingress resource
|Map[String]String
|`{}`

|`tlsSecretName`
|Name of a Secret of type `kubernetes.io/tls` to use for TLS on the operator-managed Ingress. When set, the operator adds a `tls` section that references this Secret and the configured host. For edge-terminated TLS, set this field and do not configure application TLS (`spec.app.tls`). For TLS passthrough, configure both this field and application TLS
|String
|None

|`tlsTermination`
|TLS termination type for the operator-managed Ingress. The operator also sets the `route.openshift.io/termination` annotation, which on OpenShift controls the termination of the Route that OpenShift generates from the Ingress. Use `edge` to terminate TLS at the router or Ingress. On OpenShift, you can then omit `tlsSecretName` to use the default router certificate. Use `passthrough` when you configure application TLS and {registry} handles HTTPS itself
|String (`edge`, `passthrough`, `reencrypt`)
|None
|===

Example:
[source,yaml]
----
spec:
  app:
    ingress:
      host: registry-api.example.com
      ingressClassName: nginx
      annotations:
        nginx.org/proxy-connect-timeout: "30s"
  ui:
    ingress:
      host: registry-ui.example.com
      ingressClassName: nginx
      annotations:
        nginx.org/proxy-connect-timeout: "30s"
----

Example with edge-terminated TLS:
[source,yaml]
----
spec:
  app:
    ingress:
      host: registry-api.example.com
      tlsTermination: edge
      tlsSecretName: registry-tls-cert
  ui:
    ingress:
      host: registry-ui.example.com
      tlsTermination: edge
      tlsSecretName: registry-tls-cert
    env:
      - name: REGISTRY_API_URL
        value: https://registry-api.example.com/apis/registry/v3
----

== Custom resource status
:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The {operator} reports the state of each `ApicurioRegistry3` resource in `status.conditions`. Each condition has a `type`, a `status` of `True`, `False`, or `Unknown`, a `reason`, a human-readable `message`, a `lastTransitionTime`, and a `lastUpdateTime`. The `status.observedGeneration` field records the generation of the resource that the status describes.

.Status conditions
[id="operator-status-conditions_{context}",cols="1,3",options="header"]
|===
|Condition type
|Meaning

|`Ready`
|Always reported. `True` with reason `ActiveDeploymentsAvailable` when all active Deployments of the instance are available. `False` with reason `ActiveDeploymentUnavailable` when at least one Deployment is not available. The message names the unavailable Deployments.

|`ValidationError`
|Reported only while it is `True`, with reason `Error`. The custom resource contains an invalid combination of fields. For example, the custom resource sets both `replicas` and `autoscaling` on one component, has a container without a name in `podTemplateSpec`, or sets environment variables on the component container in `podTemplateSpec` instead of in `env`. The message lists the validation errors.

|`OperatorError`
|Reported only while it is `True`. The {operator} encountered an unexpected error while reconciling the resource. The reason is the name of the exception class, and the message contains the error details.
|===

To inspect the conditions of an instance, display the resource and read its `status.conditions` field. The resource is also available under the short name `registry3`:

[source,bash,subs="attributes"]
----
{kubernetes-client} get apicurioregistries3 example-registry -o yaml
----
