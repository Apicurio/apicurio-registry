[id="registry-rule-types_{context}"]
== {registry} content rule types

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
You can specify `VALIDITY`, `COMPATIBILITY`, and `INTEGRITY` rule types to govern content evolution in {registry}. These rule types apply to both global rules and artifact-specific rules.

.{registry} content rule types
[%header,cols=2*]
|===
|Type
|Description
|`VALIDITY`
a| Validates content before adding it to {registry}. The possible configuration values for this rule are as follows:

* `FULL`: The validation is both syntax and semantic.
* `SYNTAX_ONLY`: The validation is syntax only.
* `NONE`: All validation checks are disabled.

|`COMPATIBILITY`
a| Enforces a compatibility level when updating artifacts (for example, `BACKWARD` for backward compatibility). This rule ensures that new artifacts are compatible with previously added artifact versions or clients. The possible configuration values for this rule are as follows:

* `FULL`: The new artifact is forward and backward compatible with the most recently added artifact.
* `FULL_TRANSITIVE`: The new artifact is forward and backward compatible with all previously added artifacts.
* `BACKWARD`: Clients using the new artifact can read data written using the most recently added artifact.
* `BACKWARD_TRANSITIVE`: Clients using the new artifact can read data written using all previously added artifacts.
* `FORWARD`: Clients using the most recently added artifact can read data written using the new artifact.
* `FORWARD_TRANSITIVE`: Clients using all previously added artifacts can read data written using the new artifact.
* `NONE`: All backward and forward compatibility checks are disabled.

|`INTEGRITY`
a| Enforces artifact reference integrity when creating or updating artifacts. This rule ensures that artifact references are correct. The possible configuration values for this rule are as follows:

* `FULL`: All artifact reference integrity checks are enabled.
* `NO_DUPLICATES`: Detect if there are any duplicate artifact references.
* `NO_CIRCULAR_REFERENCES`: Detect circular reference chains among artifacts.
* `REFS_EXIST`: Detect if there are any references to non-existent artifacts.
* `ALL_REFS_MAPPED`: Ensure that all artifact references are mapped.
* `NONE`: All artifact reference integrity checks are disabled.
|===

// ref-registry-rule-json-schema-validity
[id="registry-rule-json-schema-validity_{context}"]
== JSON Schema validity

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
With the `FULL` level, the `VALIDITY` rule checks that a JSON Schema artifact is a valid schema in JSON Schema draft 4, 6, 7, 2019-09, or 2020-12.

* *Draft*: the draft is the one that `$schema` declares. A schema without `$schema` is validated as draft 7, as the compatibility rule reads it. A schema whose `$schema` names no draft, such as a custom meta-schema, is also validated as draft 7, but the compatibility rule can't compare it yet and fails with HTTP status 422.
* *Meta-schema*: the schema must be valid against the meta-schema of its draft.
* *References*: a reference within the schema must point at something that exists, such as a definition. A reference to another document is resolved against the artifact references recorded for the version. If {registry} has no content for it, the reference is accepted, because the validity of a schema doesn't depend on what an external reference points to. No document is fetched over the network. To require that every external reference is recorded, use the `INTEGRITY` rule.
* *Unused references*: an artifact reference that the content doesn't use is rejected, because it's most likely a typo in the reference name.

Each rule violation has a JSON Pointer to the problem as its `context`, for example `/items/properties/price/exclusiveMinimum`. More than one problem can be reported at once.

The `SYNTAX_ONLY` level checks only that the content is well-formed JSON.
