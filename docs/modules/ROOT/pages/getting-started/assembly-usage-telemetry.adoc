[id="assembly-usage-telemetry_{context}"]
= Usage Telemetry and API Lifecycle Governance

:_mod-docs-content-type: ASSEMBLY

[role="_abstract"]
Apicurio Registry provides usage telemetry capabilities that track which client applications fetch which schema versions. This enables API lifecycle governance features including dead schema detection, consumer version drift alerts, and deprecation readiness analysis.

[id="con-usage-telemetry-overview_{context}"]
== Overview

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
Usage telemetry tracks which client applications fetch which schema versions, enabling governance decisions such as dead schema detection, version drift alerts, and deprecation readiness.

Usage telemetry answers key governance questions:

* **Is anyone actually using this schema?** Active/Stale/Dead classification based on actual fetch patterns.
* **Who uses which version?** Consumer version heatmap showing adoption across client applications.
* **Is it safe to deprecate this version?** Deprecation readiness reports listing affected consumers.
* **Are consumers falling behind?** Version drift alerts when clients use outdated versions.

Usage tracking is **server-side** and **zero-configuration for the client**. The registry records usage events automatically when it serves schema content. Clients opt in by setting an HTTP header that identifies the application:

`X-Registry-Client-Id`:: Identifies the client application (for example, `payments-svc`). Must contain only letters, digits, dots, hyphens, and underscores. Maximum 256 characters.
`X-Registry-Operation`:: Optional. The operation type: `SERIALIZE` or `DESERIALIZE`.

If no `X-Registry-Client-Id` header is present, the request is not tracked.

Both `globalId` and `contentId` based schema fetches are tracked. Clients configured with `IdOption.contentId` are fully supported.

Referenced schemas (shared types, base schemas) inherit liveness from the schemas that directly reference them in the global usage summary. If `UserEvent v3` is Active and references `SharedTypes v1`, then `SharedTypes v1` is counted as Active in `GET /admin/usage/summary`, even if nobody ever fetched `SharedTypes v1` itself. The per-artifact endpoints do not apply this rule, so check the schemas that reference a version before you deprecate it.

NOTE: Usage telemetry is an **experimental** feature and is disabled by default. It requires `apicurio.features.experimental.enabled=true` in addition to `apicurio.usage.telemetry.enabled=true`. It is tested with the H2, PostgreSQL, MySQL, SQL Server and KafkaSQL storage types; the tests do not check how client identifiers compare under each database collation (see below). It does nothing on the read-only GitOps and KubernetesOps storage types: events are dropped and the usage endpoints return empty results.

[id="con-usage-telemetry-classification_{context}"]
== How versions are classified

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
Each schema version is classified by the age of its most recent recorded fetch.

Active:: The last fetch is no older than `apicurio.usage.active-threshold-days` (default 7 days).
Stale:: The last fetch is older than the active threshold but no older than `apicurio.usage.stale-threshold-days` (default 30 days).
Dead:: The last fetch is older than the stale threshold, so with the defaults a version whose last recorded fetch is more than 30 days old is Dead.

A version inherits the most recent fetch of any schema that directly references it, but only in the global usage summary counts. The per-artifact metrics, the heatmap and the deprecation readiness list the fetches recorded for that version itself.

IMPORTANT: The classification uses only the active and stale thresholds. `apicurio.usage.dead-threshold-days` is deprecated, has no effect, and will be removed in 4.0.0. It is still accepted, and the registry logs a warning at startup if it is set. The usage summary and the Active, Stale and Dead labels cover only versions that have at least one recorded fetch within the retention period, or that are referenced by a version that has one. A version with no recorded fetch and no such referrer, for example one that was never fetched or whose events were all removed by retention, is not counted in the summary and has no label. A version that was never fetched but is referenced by a fetched version is counted in the summary and takes the classification of its most recent referrer. The per-artifact metrics, heatmap and deprecation readiness never list a version without a recorded fetch of its own.

On KafkaSQL, every usage event is one record in the journal topic, and retention removes database rows but never shrinks the journal. A journal written by an earlier release with telemetry enabled can hold usage records that were skipped until now. The first start of this release applies them all, including events older than the retention period, and the next retention run deletes the expired ones. During a rolling upgrade, nodes that still run the earlier release log an error for every usage record they cannot read.

Events older than `apicurio.usage.retention-days` (default 180 days) are deleted on every aggregation run, which happens hourly by default (`apicurio.usage.aggregation.every`). Setting `apicurio.usage.retention-days` to `0` or less turns the cleanup off, and the events then accumulate without bound. Because events are deleted, a version whose last fetch is older than the retention period drops out of the counts instead of becoming Dead. Keep the retention period longer than the stale threshold, or Dead versions disappear.

A fetch by `contentId` counts for every version that has the same content, in any artifact or group, because the identifier does not say which version was meant. Identical content registered in several artifacts therefore shares its fetches.

Client identifiers are compared with the collation of the database column. On MySQL the default comparison is case-insensitive, so `Payments` and `payments` count as one client; on PostgreSQL they are two clients. SQL Server follows its database collation, which is usually case-insensitive; this was not checked.

[id="con-usage-telemetry-reading-the-heatmap_{context}"]
== Reading the consumer heatmap

:_mod-docs-content-type: CONCEPT

[role="_abstract"]
The consumer version heatmap answers which client applications fetch which versions of one artifact.

* Each row is a client application, identified by its `X-Registry-Client-Id`.
* Each column is a version that at least one client fetched. The number in a cell is how many fetches that client made of that version within the retention period.
* `versionsBehind` compares the newest version the client fetched with the newest version that any client fetched. A client on the newest version shows `0`.
* `driftAlert` is `true` when `versionsBehind` is at least `apicurio.usage.drift-alert-threshold` (default 2).

The heatmap lists only versions that were fetched. A newer version that nobody fetched yet does not count towards `versionsBehind`.

Fetch counts are not exact request counts. The server drops a fetch when the same client fetched the same schema less than 60 seconds earlier. The schema is identified by the identifier of the request, so a schema that a client fetches once by `globalId` and once by `contentId` produces two events in that period. The record of recent fetches that implements this is held in the memory of each registry instance, so with several instances behind a load balancer each instance counts separately. While that record holds 10,000 entries, the instance records no new events at all. The record is pruned only during a flush that has buffered events, and a full record buffers none, so by reading the code an instance in that state may not recover until it restarts. A busy deployment can therefore show lower counts than the real traffic, or stop counting.

[id="ref-usage-telemetry-server-configuration_{context}"]
== Server configuration

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The registry server exposes the following properties to configure usage telemetry.

.{registry} server properties for usage telemetry
[cols="3,1,1,4"]
|===
|Property |Type |Default |Description

|`apicurio.usage.telemetry.enabled`
|boolean
|`false`
|Primary switch for usage telemetry. Must be `true` for the server to record usage events.

|`apicurio.usage.active-threshold-days`
|int
|`7`
|A schema version fetched within this many days is classified as **Active**.

|`apicurio.usage.stale-threshold-days`
|int
|`30`
|A schema version whose last fetch is older than the active threshold but no older than this many days is classified as **Stale**. A version whose last fetch is older than this is classified as **Dead**.

|`apicurio.usage.dead-threshold-days`
|int
|`90`
|Deprecated since 3.4.0, has no effect, and will be removed in 4.0.0. The Dead classification starts where the Stale classification ends.

|`apicurio.usage.drift-alert-threshold`
|int
|`2`
|Number of versions behind the newest fetched version before a consumer is flagged with a drift alert.

|`apicurio.usage.retention-days`
|int
|`180`
|Number of days to retain raw usage events. Older events are cleaned up automatically.

|`apicurio.usage.aggregation.every`
|duration
|`1h`
|How often the usage metrics are refreshed and old events are cleaned up. Uses Quarkus scheduler expression syntax (for example, `1h`, `30m`, or `10s`).

|`apicurio.usage.flush.every`
|duration
|`10s`
|How often buffered usage events are written to storage. Uses Quarkus scheduler expression syntax.

|`apicurio.usage.metrics.enabled`
|boolean
|`false`
|Export the `apicurio.usage.schema.fetches` OpenTelemetry counter described in <<ref-usage-telemetry-schema-fetch-metric_{context}>>. Experimental, and independent of `apicurio.usage.telemetry.enabled`: it stores nothing in the registry. It has no effect while the OpenTelemetry SDK is disabled.

|`apicurio.usage.metrics.max-series`
|int
|`2000`
|Threshold for the number of distinct series (combinations of client, identifier type, identifier value and operation) that the OpenTelemetry SDK keeps for the schema fetch counter in each registry process. It is not a hard ceiling: see <<ref-usage-telemetry-schema-fetch-metric_{context}>>. Must be positive. The registry does not start if the usage metric is enabled and this value is not positive.
|===

[id="proc-usage-telemetry-enabling-telemetry-example_{context}"]
== Enabling usage telemetry

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
You can enable usage telemetry on the registry server and configure a client to report its schema fetches.

.Prerequisites
* Experimental features are enabled (`apicurio.features.experimental.enabled=true`), because usage telemetry is an experimental feature.

.Procedure
. Enable usage telemetry on the server by adding the following properties to its `application.properties`:
+
[source,properties]
----
apicurio.features.experimental.enabled=true
apicurio.usage.telemetry.enabled=true
----

. Configure the Kafka SerDes client with the registry URL and a client identifier:
+
[source,properties]
----
apicurio.registry.url=http://registry:8080/apis/registry/v3
apicurio.registry.usage-telemetry.client-id=payments-svc
----
+
No additional endpoints to call and no buffers to configure are required.
+
All usage endpoints are under `/admin/usage/` and require `apicurio.usage.telemetry.enabled=true`. Endpoints return HTTP 409 (Conflict) when telemetry is not enabled.

[id="proc-usage-telemetry-deprecation-workflow_{context}"]
== Transitioning a version through the deprecation workflow

:_mod-docs-content-type: PROCEDURE

[role="_abstract"]
Apicurio Registry supports a version lifecycle state machine for controlled deprecation.

[source,text]
----
  ENABLED ──────▶ DEPRECATED ──────▶ SUNSET ──────▶ (delete)
     ▲                │                  │
     │                ▼                  │
     └──────── DISABLED                  │
     ◀───────────────────────────────────┘
----

`ENABLED`:: Version is active and available for use.
`DEPRECATED`:: Version still works but consumers should migrate. A warning is logged on access.
`SUNSET`:: Migration deadline has passed. The version will be removed soon. Requires transitioning through `DEPRECATED` first.
`DISABLED`:: Version is blocked from use.

.Prerequisites
* No active consumers depend on the version, verified by using the deprecation readiness endpoint.

.Procedure
. Deprecate the version:
+
[source,bash]
----
curl -X PUT http://localhost:8080/apis/registry/v3/groups/default/artifacts/UserEvent/versions/1.0.0/state \
  -H "Content-Type: application/json" \
  -d '{"state":"DEPRECATED"}'
----

. Sunset the version:
+
[source,bash]
----
curl -X PUT http://localhost:8080/apis/registry/v3/groups/default/artifacts/UserEvent/versions/1.0.0/state \
  -H "Content-Type: application/json" \
  -d '{"state":"SUNSET"}'
----

[id="ref-usage-telemetry-schema-fetch-metric_{context}"]
== Schema fetch metric for external dashboards

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
The registry can export one OpenTelemetry counter that records which client fetched which schema identifier, without storing anything in the registry. Use it to chart schema usage in a system that reads OpenTelemetry metrics, such as a Collector with Prometheus and Grafana.

The counter is experimental and disabled by default. It is switched on by `apicurio.usage.metrics.enabled=true`, which needs `apicurio.features.experimental.enabled=true` and an enabled OpenTelemetry SDK (`quarkus.otel.sdk.disabled=false`). It is independent of `apicurio.usage.telemetry.enabled`: with only the metric enabled, the registry does not buffer usage events, write usage rows to the database, publish usage records to the KafkaSQL journal, or query any monitoring backend while it serves a request. The usage endpoints under `/admin/usage/` stay disabled in that case.

.OpenTelemetry counter for observed schema fetches
[cols="2,1,3"]
|===
|Name |Type |Description

|`apicurio.usage.schema.fetches`
|counter, unit `1`
|One count for every successful schema fetch request that carries a valid client identifier, recorded before any deduplication.
|===

.Attributes of the counter
[cols="2,3"]
|===
|Attribute |Value

|`apicurio.registry.client_id`
|The value of the `X-Registry-Client-Id` request header. It is self-reported by the caller.

|`apicurio.registry.identifier_type`
|`global_id` or `content_id`, depending on the route the schema was fetched by.

|`apicurio.registry.identifier_value`
|The global ID or content ID from the request path, as a decimal number without leading zeros.

|`apicurio.registry.operation`
|`SERIALIZE` or `DESERIALIZE` from the `X-Registry-Operation` header, compared without regard to case. Any other value, or no header, is exported as `UNKNOWN`. The SQL usage records keep the header value unchanged.
|===

A request is counted only when all of the following hold:

* It is a `GET` on `/apis/registry/v3/ids/globalIds/{globalId}` or `/apis/registry/v3/ids/contentIds/{contentId}` for a positive ID, with or without a trailing slash. Query parameters do not affect counting. The counter accepts ASCII decimal digits with an optional leading `+`. Requests with other ID spellings or with matrix parameters in the path (such as `;source=client`) are excluded even when the server serves them successfully. Other routes, including `/references` and the v2 API, are not counted, even where the SQL usage recording accepts them.
* The response status is `200`.
* `X-Registry-Client-Id` is present, at most 256 characters, and contains only letters, digits, dots, hyphens and underscores.

Requests that fail these rules produce no detailed observation.

.Procedure
. For a custom build, make sure OpenTelemetry metrics are enabled at build time (`quarkus.otel.metrics.enabled=true`). The standard Registry build already enables them.
. Enable the metric and the OpenTelemetry SDK, and point the exporter at your Collector:
+
[source,properties]
----
apicurio.features.experimental.enabled=true
apicurio.usage.metrics.enabled=true
quarkus.otel.sdk.disabled=false
quarkus.otel.exporter.otlp.endpoint=http://otel-collector:4317
----

. For SerDes applications that already use global IDs, set `apicurio.registry.usage-telemetry.client-id` as described in <<ref-usage-telemetry-client-configuration_{context}>>. The current v3 resolver adds these headers to global-ID fetches only. It does not add them to content-ID fetches, which the deserializer uses by default. Direct HTTP clients can supply the headers on either route. Do not change the ID mode of an existing deployment solely to enable this metric.

.How to read the counter
* An observed fetch is one HTTP request for a schema. It is not a count of Kafka messages: SerDes clients cache schemas, so one fetch can stand for any number of messages, and a client whose cache is long-lived can fetch rarely while it is in constant use. The counter shows that a client fetched a schema, never that it stopped using it, and it is not a basis for deleting a schema.
* It is also not the SQL usage record. The SQL path keeps one event per client and identifier in a 60 second window, while the counter counts every request.
* A content ID is shared by every version with the same content, so `content_id` series do not identify one schema version. A global ID identifies one version, but the registry does not look up its artifact, group or version to add labels.
* The client identifier is chosen by the caller and can be spoofed. It is not an authenticated identity and must not be used for access decisions or billing.
* The values are counts per registry process. Add the series of all processes to get the total of a deployment.

.Process identity
Global IDs and content IDs come from the registry database. A registry that uses an in-memory database starts counting again from 1 after a restart, so the same identifier can then stand for a different schema. To keep such series apart, the registry adds a random `service.instance.id` to the shared OpenTelemetry resource (metrics, traces and logs), but only while the usage metric is enabled and only when neither Quarkus nor you provided one, for example through `quarkus.otel.resource.attributes` or `OTEL_RESOURCE_ATTRIBUTES`. An identity that you set is exported unchanged and must be unique for every registry process. Select and group by it in your dashboards, together with `service.name`. How these resource attributes appear as labels depends on your OpenTelemetry pipeline. The process identity does not change when storage data is replaced within that process. If a replacement snapshot reassigns an ID, the counter cannot distinguish fetches before and after that change; preserve IDs when relying on historical attribution.

.Bounded detail and overflow
The number of series is limited by a threshold, `apicurio.usage.metrics.max-series` (default `2000`), that the OpenTelemetry SDK applies to this one counter in each registry process. When requests for new combinations arrive one at a time, the overflow series takes one of the slots, so at most `max-series - 1` combinations keep their labels. When the threshold is reached, a measurement for a combination that has no series yet is added to a single series that carries only `otel.metric.overflow=true`, with no client or identifier labels. The total over all series, overflow included, still equals the number of counted requests, but the aggregated series cannot identify the folded requests. A rising overflow series means that the threshold is too low for the number of clients and identifiers in use.

The threshold limits series, not the information in an OTLP export. When metric exemplars are enabled, a sampled overflow measurement can still carry the original client and schema identifier as exemplar attributes. Do not rely on the series threshold to remove those attributes from exported data.

The threshold is not a strict ceiling. The SDK checks the number of series and adds a new one in two separate steps without locking, so requests for new combinations that arrive at the same moment can each pass the check and create a few series more than the configured value. How many extra series appear depends on how many such requests race at that moment, and no count is lost. Plan memory and backend limits with this in mind, and do not depend on the exact number of series.

With cumulative temporality, which is the default of the OTLP exporter, a series stays for the life of the process, so the threshold is reached once and stays reached until the registry restarts. An overflow series is not a zero: do not read a missing client as unused while the overflow series is non-zero.

.Export and outages
Counting only updates an in-memory aggregate, and the OpenTelemetry SDK exports it periodically from its own threads, so no call to the Collector happens on the request path. This removes the storage and query work of the SQL usage recording from the registry; it does not remove the CPU and memory used to count and export. If the Collector is unreachable, refuses the export or does not answer, schema fetches continue to succeed and the SDK continues to collect periodically. It can skip a collection while an export is still in flight. Later cumulative exports from the same process include the fetches counted during the outage; delta exports do not necessarily recover failed intervals, but nothing guarantees lossless telemetry: counts held by a registry process that stops before it can export again are lost, and a restart begins a new series. Treat missing data as unknown, not as zero use.

[id="ref-usage-telemetry-privacy-and-data-collection_{context}"]
== Privacy and data collection

:_mod-docs-content-type: REFERENCE

[role="_abstract"]
Usage telemetry is designed to minimize data collection and give operators and clients control over what is recorded.

Opt-in only:: Disabled by default on both server and client.
No message content:: Only schema coordinates and the client identifier are recorded.
No user identity:: The `clientId` is a configured application name, not a user or personal identifier.
Client-controlled:: Each client application decides whether to set the `X-Registry-Client-Id` header.
Zero overhead when disabled:: No headers are sent, no events are recorded, and no database writes occur.
Retention:: Registry deletes SQL usage events according to `apicurio.usage.retention-days`. This setting does not delete exported metrics or exemplars. Set retention for those records in the monitoring backend.
