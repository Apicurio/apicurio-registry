Apicurio Registry — PostgreSQL Sizing Dashboard

Topology: single-replica registry, operator-deployed, PostgreSQL storage behind Toxiproxy (~15ms ± 5ms injected latency), Keycloak OAuth2 client-credentials. Resources: 1 CPU / 1Gi (operator defaults). Traffic: 95% reads / 5% writes against a 200-artifact pre-seeded pool (RegistryApiSimulation, read-heavy default). Load model: closed injection (constantConcurrentUsers) — N genuinely concurrent virtual users sustained for the full 45s run, not an arrival-rate model.
Methodology note: this data was collected after fixing a real bug in the load generator: it previously used Gatling's open injection model (rampUsers + constantUsersPerSec(USERS/2)), which controls arrival rate, not concurrency — by Little's Law, true concurrency was only a fraction of the configured PERF_USERS value. All numbers on this dashboard use the corrected closed model (constantConcurrentUsers), so N users here means N genuinely concurrent, continuously-active clients for the whole run.

Note on 200/300: raw OK-throughput keeps climbing past 150 users, but that's misleading in isolation — an increasing share of total traffic is failing outright (4.75% at 200, 12.82% at 300) and p50/p99 latency for the requests that do succeed has already blown up by 10–100x. 150 concurrent users is the last point with both 0% failures and stable latency.

Sizing recommendation (this topology only)

For a single registry replica on 1 CPU / 1Gi, SQL storage, ~15ms DB latency: keep sustained concurrent client load at or below ~150 for zero-failure operation. Between 150–200 concurrent users, expect the first restarts and failures to appear. Beyond 200, failure rate and tail latency both degrade sharply. To serve more concurrent clients, scale horizontally (more replicas) rather than assuming a single instance will linearly absorb more load — see extreme-case-and-realism-report.md for how much worse this gets under degraded network conditions, and prod-like-vt-comparison-report.md / prod-like-vt-multirun-report.md for how virtual threads change this specific picture (those runs pre-date this dashboard's closed-model fix and should be treated as directionally indicative, not exact numbers, until re-validated under the corrected model).
